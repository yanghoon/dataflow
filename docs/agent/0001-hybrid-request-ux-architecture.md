# 하이브리드 신청 UX 아키텍처 (JSON Schema 폼 + Agent Chat)

2026-11-02 · @Hoon

## 상태와 요약

**상태:** Proposed (확정 전, 검토용)

> 백엔드 MCP 서버(Spring)와 인가는 [0002](0002-spring-mcp-server-design.md)가 구체화한다. 인가는 OPA 대신 Casbin을 쓴다(이 문서의 OPA 서술은 0002 기준으로 정리했다). 토큰 교환(RFC 8693)과 `act`는 외부 사용자를 여는 5단계의 설계이며, 그 전 관리자 단계는 토큰 교환 없이 0002를 따른다(감사 로그에는 `client_id`를 남긴다).

**결정:** 신청은 JSON Schema 폼(SPA)이 책임지고, LLM 채팅은 폼을 찾아 값을 미리 채워 주는 보조 경로로 둔다.

- 메인 화면: Refine(React) 하나의 SPA
- 신청 폼: RJSF (JSON Schema 렌더러)
- 채팅: assistant-ui, 에이전트 런타임: Flue
- 입구(BFF, 화면·에이전트 앞단 서버): 둘로 나눈다. 웹 BFF(Spring, Refine용)와 에이전트 BFF(Flue: 채팅 UI 백엔드, MCP, A2A)다. 업무 규칙과 최종 권한 판정은 공통 백엔드 API가 맡는다.
- 인증: 웹은 Spring BFF가 OIDC로 로그인한다. 에이전트 입구(MCP, A2A)는 Flue가 JWT를 직접 검증한다. 채팅 UI는 웹 BFF가 인증해 준 토큰을 Flue로 보내 검증한다.
- 배포: SPA는 Spring 앱에 포함하고, Flue는 따로 배포한다.

**방향:** 지금 구조는 "채팅이 화면으로 안내하는" 중간 단계다. 최종적으로는 사용자의 AI 에이전트가 우리 도구를 직접 호출하고, 사용자는 맡기고 확인만 하는 방식으로 논의된다. 그래서 도구·정책·이력은 한 벌로 두고 입구만 늘리는 구조로 만든다. (부록 G, H)

**도입 순서:** 백엔드 API·감사 로그 → MCP 서버(관리자, 읽기 전용) → 웹 GUI 최소판(확인·감독 화면) → 쓰기 도구 + 폼 링크 → 사용자 알파·베타 → 채팅 UI·A2A. 첫 유저 에이전트는 Claude Code다. (부록 I)

**검증:** Flue·MCP·A2A·Hono·Spring AI 주장은 공식 문서로 확인했고, 고칠 곳은 본문에 반영했다. (부록 J)

## 배경과 문제

AI 에이전트 시대에 일반 사용자의 신청 UX를 어떻게 구성할지 정해야 한다. 사용자 VOC(고객 의견)를 LLM과 연동해 처리하는 화면도 필요하다. 대상은 일반 사용자이며, 셀프 서비스 포털로 제공한다.

**전제**

- 온프레미스 망분리 Kubernetes 환경이다.
- 백엔드는 Spring Boot, DB는 PostgreSQL(CNPG)이다.
- 사용자마다 권한이 달라 인증(OIDC)과 인가가 필요하다.
- 개발 속도가 중요하다.
- Flue를 통해 사용자가 신청·설정할 수 있는 업무 목록과 신청 이력을 MCP 서버, A2A 에이전트, 채팅 UI로 단계적으로 제공하려 한다.
- 지난 채팅 내용과 신청 이력은 이후 신청이나 설정 화면으로 안내할 때 도움이 된다. 상담 채팅을 넓힌 것이며, 사용자가 채팅의 안내로 기존 웹 기능을 쓰는 새로운 이용 방식이다.

**풀어야 할 문제**

1. 신청 데이터는 틀리면 안 된다. 같은 입력은 같은 결과가 나와야 한다.
2. 사용자는 말로 설명하며 신청하고 싶어 할 수 있다. 이때 LLM은 확률적으로 동작한다.
3. 이 둘을 한 화면 구조에서 어떻게 함께 다룰지 정해야 한다.
4. 사용자의 AI 에이전트(MCP, A2A)가 같은 기능을 부를 때도 같은 규칙과 권한이 적용되어야 한다.
5. 채팅과 화면이 같은 작업을 서로 차지하면 사용자가 혼란스러워진다(하이브리드 함정). 역할을 나눠야 한다.

**이 문서가 정하는 것:** 신청 UX 방식, 화면·채팅 프레임워크, 인증·인가 구조, 입구(BFF) 구분과 도구·권한 배치, 빌드·배포 구조.

## 결정 기준

모든 대안에 아래 기준을 같은 순서로 적용했다.

| 기준 | 묻는 것 |
| --- | --- |
| 개발·유지보수 비용 | 처음 만들 때와 운영할 때 드는 인력·시간. 배우는 시간 포함 |
| 개발 속도 | 첫 화면과 새 신청 유형을 추가하는 속도 |
| 정확성 | 사용자의 의도가 틀리지 않고 데이터에 담기는가 |
| 결정성 | 같은 입력이 항상 같은 결과를 내는가 |
| 확장성 | 신청 유형·화면·사용자가 늘어도 버티는가 |
| 표준 | 에이전트 UI 표준을 따르는가, 표준이 바뀌어도 교체가 쉬운가 |
| 엔터프라이즈 기능 | SSO, 권한 체크, 동적 메뉴, 테마 변경을 나중에 붙일 수 있는가 |
| 일반 사용자 UX | 개발자가 아닌 사용자가 쓰기 쉬운가 |
| 에이전트 입구 대응 | 사용자의 AI 에이전트(MCP, A2A)도 같은 기능을 같은 규칙으로 쓸 수 있는가 |
| 신뢰 | 맡긴 일을 확인하고, 내역을 보고, 되돌릴 수 있는가 |

**제약:** 망분리 환경에서 동작해야 하고, 사용자별 채팅 분리와 권한 검사가 필요하다.

## 검토한 대안

세 가지 방식을 비교했고, 채택안은 C다.

- **A. 백엔드 주도 JSON Schema SPA:** 서버가 스키마를 내려주고, 프론트엔드가 폼을 그린다.
- **B. LLM 채팅 + MCP 중심:** 사용자가 채팅으로 말하면 에이전트가 도구(MCP)로 신청을 진행하고 화면을 동적으로 만든다.
- **C. 하이브리드:** 제출은 A의 폼이 맡고, B의 채팅은 폼 선택과 값 채우기를 돕는다.

| 기준 | A. 스키마 SPA | B. 채팅 + MCP | C. 하이브리드 |
| --- | --- | --- | --- |
| 개발 속도 | 렌더러를 한 번 만들면 이후엔 스키마만 추가. 예측하기 쉬움 | 처음 구축이 큼(BFF, 소유권, SSE, 어댑터). 신청 유형 추가는 프롬프트·스킬로 빠름 | A의 속도에 채팅 구축 비용이 더해짐 |
| 유지보수 | 낮음. 스키마 버전과 검증만 관리 | 높음. 모델을 바꾸면 회귀 평가, 프롬프트 관리, 토큰 비용, 프레임워크 변경 대응 | 채팅 쪽에만 B의 비용이 생김 |
| 정확성 | 스키마 검증이 정답 기준 | 확률적. 확인 단계가 필수 | 제출 전에 사용자가 폼에서 확인하므로 A 수준 |
| 결정성 | 높음 | 낮음 | 제출 경로는 높음 |
| 확장성 | 정형 신청에 강함. 유형이 폭증하면 사용자가 신청서를 찾기 어려움 | 정해지지 않은 모호한 요청, 여러 시스템에 걸친 처리에 강함 | 두 장점을 모두 가짐 |
| 표준 | JSON Schema(안정된 표준). MCP elicitation도 JSON Schema를 쓰지만 평면 객체·원시 타입 일부만 허용 | 에이전트 UI 표준은 아직 유동적. Flue는 지원하지 않음 | 안정된 표준 위에 두고 채팅은 교체 가능하게 둠 |
| 장애 시 | 폼 경로만 있으면 됨 | 채팅이 죽으면 신청 불가 | 채팅이 죽어도 폼으로 신청 가능 |

스키마 하나를 폼과 MCP 도구 입력 스키마에서 함께 쓰면 같은 신청서를 두 번 만들지 않는다. 다만 MCP elicitation(form 모드)은 평면 객체와 원시 타입만 허용하므로, 중첩이 있는 신청서는 elicitation 대신 폼 URL로 안내(URL 모드 또는 링크)해야 한다.

**최종 UX와의 관계:** 대안 B(채팅 + MCP 중심)는 논의되는 최종 UX(사용자가 맡기고 확인하는 방식)에 더 가깝다. 다만 지금은 정확성과 신뢰 장치, 표준이 덜 갖추어졌다. 그래서 C로 시작하고, 같은 도구 위에 입구를 늘려 B 쪽으로 넓히는 방향이다. (부록 G)

## 결정

신청 정답 기준은 JSON Schema 하나로 두고, 아래 구성으로 간다.

| 영역 | 결정 |
| --- | --- |
| 신청 방식 | 하이브리드. 정답 기준은 JSON Schema 하나 |
| 채팅의 역할 | 신청서 선택, 값 미리 채우기. 제출은 사용자가 폼에서 확인한 뒤 직접 한다 |
| 메인 SPA | Refine (React, 헤드리스: 화면 부품이 없는 틀) |
| UI 컴포넌트 | shadcn/Tailwind 계열로 통일 (assistant-ui와 맞추기 위함) |
| 신청 폼 | RJSF |
| 채팅 UI | assistant-ui (ExternalStoreRuntime으로 Flue 메시지 연결) |
| 에이전트 런타임 | Flue (Node 타깃) |
| 입구(BFF) | 웹 BFF(Spring: Security OIDC, Cloud Gateway, Refine용)와 에이전트 BFF(Flue: 채팅 UI 백엔드, MCP, A2A) 둘로 나눈다. BFF는 얇게 두고, 업무 규칙은 넣지 않는다 |
| 공통 백엔드 API | 업무 로직, 최종 권한 판정, 스키마 검증, 감사 로그를 맡는다. 같은 업무 기능을 REST(웹 BFF)와 MCP(에이전트 BFF) 두 모양으로 연다 |
| 도구 배치 | 도구의 실제 구현과 권한 검사는 백엔드에 한 벌만 둔다. Flue는 이를 MCP 클라이언트(`useMcpConnection`)로 쓴다. Flue가 자기 MCP 서버를 다시 호출하는 self 등록은 하지 않는다. Flue 안에서만 쓰는 도구는 `useTool`로 만든다 |
| 인증 (웹) | 웹 BFF가 OIDC Authorization Code + PKCE로 로그인하고 세션을 관리한다 |
| 인증 (에이전트 입구) | Flue `app.ts`에서 Hono `jwk` 미들웨어(JWKS, `iss`·`aud` 검증)로 JWT를 직접 검증한다(MCP, A2A). 채팅 UI도 웹 BFF가 인증해 준 토큰을 assistant-ui가 Flue로 보내 같은 방식으로 검증한다 |
| 인가 | 최종 판정은 백엔드 API(Casbin)가 한다. BFF의 검사는 화면 편의용이다. 대화 소유권은 Flue 미들웨어에서 확인한다 |
| 대리 호출 | 에이전트가 사용자를 대신한 호출은 사용자 신원으로 실행한다. 입구 토큰을 그대로 넘기지 않고 토큰 교환(RFC 8693)으로 백엔드용 토큰(`aud`=백엔드)을 받으며, 대리 주체(`act`)와 위임 범위를 남긴다 |
| 메뉴 | 메뉴 API가 권한별로 걸러서 내려주고, Refine이 resources로 구성한다 |
| 배포 | Spring 앱에 SPA를 포함(web jar)하고, Flue는 별도 Deployment로 둔다 |
| 빌드 | Gradle 멀티모듈 + Jib + Skaffold |
| 채택하지 않음 | 마이크로 프론트엔드, Backstage 신규 도입, Vue |

**조건부 결정:** 사내에 Backstage가 이미 운영 중이고 사용자가 개발자라면 Backstage 중심안을 다시 검토한다(후속 과제 참고).

**변경 이력:** 처음 안은 모든 요청을 Spring BFF가 중계하고, Flue 앞에서 인증·소유권을 확인하는 구조였다. 논의 끝에 에이전트 입구(MCP, A2A, 채팅 UI)는 Flue가 JWT를 직접 검증하는 구조로 바꿨다.

- 이유 1: 외부 사용자 에이전트가 Flue에 직접 붙으므로 Flue가 어차피 JWT를 검증해야 한다.
- 이유 2: 채팅 UI도 같은 검증 경로를 쓰면 입구마다 규칙이 달라지지 않는다.
- 이유 3: SSE 스트림을 Spring이 중계할 필요가 없어진다.
- 대가: 토큰이 브라우저 메모리에 들어온다(기존안은 HttpOnly 쿠키만). 수명을 짧게, 대상(`aud`)을 에이전트로 제한하고, 메모리에만 두며, 갱신은 웹 BFF가 맡는다. (부록 E)

## 결정의 근거

아래 순서로 한 단계씩 결론에 이른다.

1. **신청 데이터는 틀리면 안 된다.** 그래서 같은 입력이 같은 결과를 내는 결정성이 필요하다. JSON Schema 검증이 이 기준을 가장 단순하게 만족한다. (대안 A)
2. **LLM은 확률적이다.** 같은 말도 다르게 해석할 수 있어, 채팅만으로 제출하는 경로는 정확성을 보장하지 못한다. 반면 신청서를 찾고 값을 채우는 일에는 강하다. 그래서 채팅은 제출이 아니라 보조 역할로 둔다. (대안 B)
3. **보조 경로로 두면 장애에 강하다.** 채팅이나 모델이 멈춰도 사용자는 폼으로 직접 신청할 수 있다.
4. **에이전트 UI 표준은 아직 하나로 모이지 않았다.** MCP Apps는 가장 넓게 지원되지만 샌드박스 iframe의 HTML이라 자유도가 높고 결정성은 낮다. A2UI는 클라이언트가 가진 부품 목록 안에서만 그리는 방식이라 안전하지만 1.0 정식 전 단계다. AG-UI는 이 둘 아래의 런타임 계층이다. Flue가 이 셋을 지원한다는 자료는 찾지 못했다. 그래서 안정된 JSON Schema에 정답 기준을 두고, 표준은 나중에 어댑터로 붙인다. (부록 A, B)
5. **Flue는 에이전트 런타임이지 채팅 화면이 아니다.** 화면은 따로 필요하다. 이미 만들어진 채팅 앱(Open WebUI, Chainlit)은 단독 앱이라, 신청 폼·메뉴·권한이 있는 우리 SPA 안에 넣기 어렵다. 그래서 앱에 내장하는 라이브러리 assistant-ui를 쓰고, `@flue/react`가 주는 메시지 상태를 연결한다. (부록 C)
6. **Flue에는 사용자별 채팅 분리 기능이 없고, 라우터에도 인증이 없다.** 인증은 호스트 앱(`app.ts`, Hono)에서 미들웨어로 붙인다. 그래서 에이전트 입구의 JWT 검증과 대화 소유권 확인은 Flue에서 직접 하고, 웹 쪽 로그인·세션은 핵심 스택인 Spring Boot의 Spring Security로 한다. (부록 B, E)
7. **SSO, 권한, 메뉴, 테마가 나중에 필요하다.** 순수 SPA로 직접 만들면 작은 Backstage를 다시 만드는 셈이다. Backstage는 새로 도입하면 배우는 시간과 업그레이드 비용이 크고 개발자 포털 성격이라 일반 사용자 UX에 맞추기 어렵다. Refine은 인증·권한·데이터·i18n을 provider로 분리하고, resources로 메뉴를 구성하며, UI 라이브러리를 고를 수 있다. (부록 D)
8. **판정은 프론트엔드가 아니라 백엔드에 둔다.** 업무 규칙과 최종 권한 판정을 백엔드 API(Casbin)에 두면, 나중에 화면 프레임워크를 바꿔도 보안 계층은 그대로 남는다. BFF의 검사는 화면 편의용이라 BFF가 뚫리더라도 백엔드가 막는다.
9. **React로 통일한다.** Refine, assistant-ui, `@flue/react`가 모두 React 기반이다. Vue에서는 Refine 같은 헤드리스 프레임워크와 성숙한 채팅 라이브러리를 찾지 못했다. (부록 D)
10. **마이크로 프론트엔드는 하지 않는다.** 여러 팀이 화면을 따로 배포해야 할 필요가 지금은 없다. 동적 메뉴는 SPA 하나로 충분하고, 신청 유형은 스키마 추가만으로 늘어난다.
11. **배포는 가장 단순한 형태로 시작한다.** 웹 BFF와 SPA를 하나의 Spring 앱으로 묶으면 컨테이너가 하나이고 CORS·CSRF 구성이 단순하다. Flue는 LLM 부하로 따로 늘릴 가능성이 커서 별도 Deployment로 둔다. (부록 F)
12. **고전 웹 화면은 계속 필요하다.** 정확하고 반복되는 작업, 승인 확인, 이력 조회, 에이전트가 실패했을 때의 우회로는 화면이 맡는다. 2026년 자료도 채팅은 기존 UI를 대체하지 못하고 옆에 자리를 잡았다고 본다. 다만 화면의 중심이 입력 화면에서 확인·감독 화면으로 옮겨 간다. (부록 G)
13. **도구·정책·이력은 한 벌로 두고 입구만 나눠야 한다.** 채팅 UI, MCP, A2A가 같은 도구를 쓰면 결과가 같다. 입구마다 달라지는 것은 응답 방식과 승인 방식뿐이다. 권한 검사는 에이전트가 아니라 도구 층에 둔다. (부록 G, H)
14. **도구 서버는 하나만 둔다.** Flue가 자기 MCP 서버를 다시 호출하면 네트워크 단계와 인증이 두 번 생긴다. 도구는 백엔드에 두고 MCP로 열며, Flue는 일반 MCP 클라이언트로 쓴다. (부록 H)
15. **같은 업무 기능에 입구별 BFF를 붙인다.** 웹 BFF와 에이전트 BFF가 같은 백엔드 API를 부르면 업무 규칙이 갈라지지 않는다. 최종 권한 판정은 백엔드 API가 한다. (부록 H)
16. **에이전트 입구는 Flue가 JWT를 직접 검증한다.** Flue가 MCP·A2A 서버를 제공하지 않는다는 것은 공식 문서로 확인했지만, `app.ts`가 fetch 호환 앱(기본 Hono)이라 직접 올릴 길은 열려 있다(MCP는 Hono 어댑터가 있고 A2A JS SDK는 Express 기반). 채팅 UI도 같은 경로로 맞춰, 웹 BFF가 인증한 토큰을 보내 검증한다. (부록 B, E)
17. **최종 UX는 맡기고 확인하는 방식으로 논의된다.** 지금의 하이브리드는 그 중간 단계이며, 같은 도구 구조 위에서 입구만 늘리면 된다. (부록 G)

## 아키텍처 개요

```text
  브라우저 SPA (Refine + RJSF + assistant-ui)        외부 사용자 에이전트 (MCP · A2A)
     │ 세션(OIDC) /api/*, /login     │ Bearer JWT /agents/*       │ Bearer JWT /mcp, /a2a
     ▼                               └──────────────┐             │
  웹 BFF (Spring, SPA 포함)                          ▼             ▼
     │                                      에이전트 BFF (Flue: JWT 검증, 대화 소유권)
     │ 사용자 토큰                                    │ 사용자 토큰 (MCP 클라이언트)
     └──────────────────────┬───────────────────────┘      ├─→ 사내 LLM
                            ▼                              └─→ 세션 저장 (CNPG)
              공통 백엔드 API (업무 로직 · Casbin 판정 · 스키마 검증 · 감사 로그)
                            │
                      PostgreSQL (CNPG)
```

화면과 로그인은 웹 BFF를 쓰고, 에이전트 입구(채팅 UI, MCP, A2A)는 Flue로 간다. 두 BFF는 같은 공통 백엔드 API를 부르고, 업무 규칙과 최종 권한 판정은 그곳에서 한다. 백엔드 API는 NetworkPolicy로 두 BFF에서 오는 요청만 받는다. Flue는 세션을 CNPG에 저장하고 사내 LLM을 호출한다. 웹 BFF와 SPA는 이미지 하나, Flue는 별도 Deployment다.

**신청 흐름 (하이브리드)**

1. 사용자가 채팅으로 요청하면 에이전트가 맞는 스키마를 고르고 값을 미리 채운다(`useDataWriter` 데이터 또는 도구 결과로 전달).
2. 미리 채운 폼을 채팅 안(도구 결과 UI)에 띄우거나, `/requests/:type` 폼 화면으로 연다.
3. 사용자가 값을 확인하고 제출한다. 클라이언트가 검증하고, BFF를 거쳐 서버가 스키마로 다시 검증한다.
4. 채팅을 쓰지 않는 사용자는 같은 폼 화면에서 직접 신청한다.

**인증·인가 흐름 (웹·채팅 UI)**

1. Refine의 `authProvider`가 웹 BFF `/login`을 부르면, 웹 BFF가 OIDC(Authorization Code + PKCE)로 로그인한다.
2. 웹 BFF가 로그인 세션을 서버에 보관하고, SPA에는 수명이 짧은 접근 토큰을 준다(메모리에만 보관).
3. Refine은 웹 BFF의 `/api/*`를, assistant-ui는 Flue의 `/agents/*`를 부른다. 채팅은 접근 토큰을 Bearer로 보낸다.
4. 웹 BFF는 세션을 검증하고, Flue는 IdP 공개키로 JWT를 검증한 뒤 대화 소유권을 확인한다.
5. 업무 API 호출은 사용자 신원으로 실행되고(백엔드용 토큰은 토큰 교환으로 받는다), 백엔드 API가 Casbin으로 최종 판정한다. 에이전트의 도구 호출도 같은 권한으로 실행된다.

**인증·인가 흐름 (외부 사용자 에이전트)**

1. 사용자의 에이전트가 공개된 agent card를 읽고 인증 방식을 확인한다.
2. IdP에서 OAuth로 받은 토큰을 Bearer로 MCP·A2A 입구에 보낸다.
3. Flue가 JWT를 검증하고 위임 범위(scope)를 확인한다.
4. Flue가 토큰 교환으로 백엔드용 토큰을 받아 백엔드를 부르고, 백엔드 API가 대리 주체(`act`)를 기록하고 Casbin으로 판정한다.
5. 승인이 필요한 작업은 작업 상태를 '입력 필요'(`TASK_STATE_INPUT_REQUIRED`)로 돌려, 상대 에이전트가 사용자에게 다시 묻게 한다. 상대는 같은 `taskId`·`contextId`로 새 메시지를 보내 이어간다.

자세한 내용은 부록 E(인증·인가), 부록 F(빌드·배포), 부록 G(최종 UX 방향), 부록 H(입구·레이어·도구 배치).

## 결과와 위험

제출 데이터의 정확성은 지키고, 그 대가로 신청 경로 두 개를 유지하는 비용을 감수한다.

**좋아지는 점**

- 제출 데이터의 정확성과 결정성을 스키마 검증으로 지킨다.
- 채팅이 실패해도 폼으로 신청할 수 있다.
- 신청 유형은 스키마를 추가해 늘리고, 같은 스키마를 폼과 MCP 도구 입력에서 함께 쓴다. 평면 스키마만 elicitation으로 쓸 수 있다.
- 업무 규칙과 최종 권한 판정이 백엔드 한 곳에 모여, 어느 입구로 들어와도 같은 규칙이 적용된다.
- 표준이 정해져도 정답 기준(JSON Schema)과 보안 계층은 그대로 유지된다.
- 사용자 에이전트가 직접 호출하는 구조(최종 UX)로 넓힐 때도 입구만 추가하면 된다.

**감수하는 점**

- 신청 경로가 폼과 채팅 두 개라 둘 다 유지해야 한다.
- 처음 구축 비용이 있다(BFF, 소유권 관리, SSE, 어댑터).
- 직접 만들어야 하는 연결부가 있다: Flue 메시지를 assistant-ui 형식으로 바꾸는 `convertMessage`, `data` 파트를 폼 컴포넌트에 연결하는 매핑, `/threads` 대화 목록 API.
- 입구가 둘(웹 BFF, 에이전트 BFF)이라 인증 방식이 두 가지로 나뉜다(세션과 JWT). 같은 사용자가 두 경로로 들어오므로 대리 호출 표기와 감사가 필요하다.
- Flue의 MCP·A2A 입구를 직접 구현해야 한다(공식 문서로 미지원 확인).
- 채팅과 화면이 같은 작업을 서로 차지하면 혼란스럽다. 채팅은 찾기와 값 채우기, 제출과 확인은 폼으로 역할을 나눈다.
- 토큰이 브라우저 메모리에 들어오므로(기존안은 HttpOnly 쿠키만) 토큰 관리 책임이 늘어난다.

**위험과 완화**

| 위험 | 완화 |
| --- | --- |
| Flue 2.0에서 호환이 깨진 이력이 있다(현재 2.3.0, pre-1.0 영속 스키마는 마이그레이션 불가였음) | 버전을 고정하고, 에이전트 호출을 에이전트 BFF(Flue) 한 곳으로 모아 교체 가능하게 둔다 |
| Flue에 사용자 분리가 없다 | Flue `app.ts`의 JWT 미들웨어가 세션 ID를 서버에서 만들고, 소유권 테이블로 매 요청(스트림 재연결 포함)을 검증한다 |
| 채팅이 권한 우회 경로가 된다 | 도구 호출을 사용자 토큰으로 실행하고, 채팅 안의 폼도 같은 권한 검사를 거친다. 최종 판정은 백엔드 API가 한다 |
| LLM이 잘못 해석해 틀린 값이 채워진다 | 미리 채운 값은 항상 폼에서 사용자가 확인하고, 제출할 때 서버가 스키마로 다시 검증한다 |
| SSE가 Flue 앞단(Ingress 등)에서 끊기거나 버퍼링된다 | 버퍼링을 끄고 타임아웃을 길게 잡는다. 재연결 헤더를 그대로 전달한다 |
| Refine 메이저 업그레이드에서 호환이 깨진다 | 버전을 고정하고, 인증·권한은 BFF에 두어 화면 교체의 영향을 줄인다 |
| Refine이 관리 화면 중심이라 일반 사용자 화면이 어색하다 | 사용자용 레이아웃은 직접 구성한다. 헤드리스라 가능하다 |
| 웹 BFF와 SPA를 함께 배포해 화면만 고쳐도 BFF를 다시 배포한다 | web jar를 Jib 레이어로 분리해 푸시 비용을 줄이고, 필요하면 SPA를 분리한다 |
| 망분리에서 Node·npm을 받을 수 없다 | Nexus에 Node 배포판과 npm 레지스트리 미러를 둔다 |
| 에이전트 부하가 BFF 확장에 묶인다 | Flue를 별도 Deployment로 분리한다 |
| 토큰이 브라우저에 있어 탈취될 수 있다 | 수명을 짧게, 대상(`aud`)을 에이전트 전용으로 제한하고, 메모리에만 보관한다(로컬 저장소 금지). 갱신은 웹 BFF가 맡는다 |
| 접수 후에는 원래 요청 헤더가 에이전트에 없다(Cloudflare 문서 명시, Node는 문서에 없어 PoC로 확인). 입구 토큰을 백엔드에 그대로 넘기면 `aud` 불일치와 token passthrough 금지 위반이 된다 | 미들웨어에서 JWT를 검증한 뒤 토큰 교환으로 백엔드용 토큰을 받아 앱 저장소(키: 대화 id 또는 `sub`)에 보관하고, `useMcpConnection`의 `auth` 함수가 그 저장소에서 요청마다 꺼낸다. 에이전트는 `{ id }`만 받으므로 대화 id를 사용자에서 만들어 낸다(`{sub}:{uuid}`) |
| Flue는 MCP 서버·A2A 입구를 제공하지 않는다(공식 문서로 확인) | MCP는 `@modelcontextprotocol/hono`로 `app.ts`에 올린다. A2A 공식 JS SDK는 Express 기반이라 Hono에 올리기 어려울 수 있다. 그 경우 Express 어댑터를 별도 프로세스나 Flue 앞 얇은 서비스로 둔다 |
| 외부 에이전트의 프롬프트 주입 | 외부 입력은 검증되지 않은 입력으로 보고, 권한 검사는 도구 층(백엔드)에서 한다 |
| 대리 호출의 책임 소재가 흐려진다 | 토큰에 대리 주체(`act`)와 위임 범위를 담고, 백엔드가 감사 로그에 남긴다 |
| 채팅과 화면이 같은 작업을 서로 차지한다(하이브리드 함정) | 역할을 나눠 채팅은 찾기와 값 채우기, 제출과 확인은 폼으로 한다 |

## 후속 과제와 재검토 조건

채택 전에 PoC(작은 시험 구현)로 아래를 확인하고, 아직 정해지지 않은 항목을 확정한다.

**PoC로 확인할 것**

- [ ] Flue의 `useDataWriter` 데이터와 `dynamic-tool` 파트 → assistant-ui 도구 결과 UI → RJSF 폼이 한 흐름으로 이어지는지
- [ ] `@flue/react` 메시지를 assistant-ui로 바꾸는 어댑터 (`convertMessage`)
- [ ] Flue 앞단의 SSE 경로(Ingress, 버퍼링, 타임아웃, 재연결)
- [ ] Flue 미들웨어의 JWT 검증·대화 소유권 테이블, `/threads` 목록 API, 세션 ID 서버 생성
- [ ] 도구를 호출할 때 요청마다 토큰을 넣는 경로(앱 저장소 + MCP `auth` 함수)가 Node 타깃에서 동작하는지, 샌드박스·파일의 사용자별 분리
- [ ] 사내 LLM 엔드포인트 연결과 Flue 빌드(Node 타깃)
- [ ] Nexus의 Node·npm 미러, Gradle web jar + Jib + Skaffold 빌드
- [x] Flue 라이선스: Apache-2.0 확인(2026-11-02). 버전 고정은 남음(현재 2.3.0)
- [ ] 토큰 교환(RFC 8693)을 IdP가 지원하는지, 백엔드용 `aud`와 `act` 발급
- [ ] Hono `hono/jwk`로 IdP JWKS 검증(`alg`, `iss`, `aud`)과 대화 id 소유권 검사를 `/agents/*`에 적용
- [ ] 신청 스키마를 elicitation 부분집합(평면, 원시 타입)으로 줄일 수 있는지, 아니면 폼 링크로 안내할지

## 부록 A. 에이전트 UI 표준 현황

화면을 그리는 확정된 단일 표준은 없다. 역할이 다른 표준이 함께 쓰인다.

| 표준 | 역할 | 화면을 그리는 방식 | 상태 | 결정성 |
| --- | --- | --- | --- | --- |
| MCP elicitation | 도구 실행 중 사용자에게 입력 요청 | form 모드는 JSON Schema의 제한된 부분집합(평면 객체, 문자열·숫자·불리언·enum)으로 폼 구성(비민감 정보). URL 모드는 외부 페이지(민감 정보·OAuth) | MCP 사양에 포함(2025-11-25 사양) | 높음 |
| MCP Apps (SEP-1865) | 도구 응답에 대화형 UI 포함 | `ui://` 리소스의 HTML을 샌드박스 iframe에 표시 | 2026-01-26 안정판, 2026-07-28 사양의 확장 프레임워크에 포함. Claude, ChatGPT, VS Code Copilot, M365 Copilot, Cursor, Goose 등이 지원 | 낮음(자유도 높음) |
| A2UI (Google) | 에이전트가 UI를 선언적 JSON으로 전달 | 클라이언트가 가진 신뢰 컴포넌트 카탈로그 안에서만 렌더링. 실행 코드를 받지 않음 | 2025년 공개, v0.9.1, 1.0은 후보. 렌더러: Angular, Flutter, Lit, React, Markdown | 높음 |
| AG-UI (CopilotKit) | 에이전트와 앱 사이 양방향 런타임 | message, state, tool call 같은 이벤트를 SSE 등으로 전달 | 위 표준들 아래의 계층. 프레임워크 간 교체가 쉬움 | 해당 없음 |
| Open-JSON-UI (OpenAI) | 선언적 생성형 UI 사양 | JSON으로 UI 구조 기술 | CopilotKit이 지원 | 높음 |

**생성형 UI 세 가지 패턴 (CopilotKit 분류)**

- Controlled: 통제 높음, 자유 낮음 → AG-UI
- Declarative: 공유된 통제 → A2UI, Open-JSON-UI
- Open-ended: 통제 낮음, 자유 높음 → MCP Apps, 직접 만든 UI

**이 ADR에서의 위치:** 신청 제출은 정확성이 중요하므로 Controlled·Declarative 쪽, 즉 스키마와 카탈로그 방식에 가깝게 설계했다. 자유로운 UI(MCP Apps)는 필요할 때 추가한다.

**에이전트끼리의 통신 표준 (화면이 아니라 연결)**

MCP는 AI 앱과 도구를 잇고, A2A는 에이전트끼리 잇는다. 둘은 경쟁이 아니라 함께 쓴다.

| 구분 | MCP | A2A |
| --- | --- | --- |
| 연결 대상 | AI 앱 ↔ 도구·데이터 | 에이전트 ↔ 에이전트 |
| 발견 방법 | 서버가 도구·리소스 목록을 공개 | agent card(`/.well-known/agent-card.json`)로 능력과 연결 정보를 공개. 인증이 필요한 확장 카드도 가능 |
| 호출 내용 | 도구 호출, 리소스 읽기 | 메시지, 작업(task) |
| 인증 | OAuth 기반. 서버가 401과 보호 리소스 메타데이터로 인증 정보를 안내 | agent card에 인증 방식(OAuth 2.0, OIDC, API 키, mTLS) 선언. card는 공개, 호출은 인증 |

- A2A는 1.0.0이 최신이며(0.3과는 `A2A-Version` 헤더로 구분), card 버전 관리에 운영 규율이 필요하다는 보고가 있다.
- 에이전트가 다른 에이전트를 신뢰하면 공격 표면이 넓어진다. 모르는 card를 그대로 믿지 않는다.

## 부록 B. Flue 검토

**한 줄 정의:** Astro 팀이 만든 TypeScript 에이전트 프레임워크. Claude Code처럼 동작하지만 완전히 헤드리스이고 코드로 제어한다. 채팅 화면은 포함하지 않는다.

| 항목 | 내용 |
| --- | --- |
| 핵심 개념 | Agent = Model + Harness. 에이전트를 React 훅과 비슷한 `use...` 훅 함수로 정의(2.0) |
| 주요 훅 | `useModel`, `useSandbox`, `useTool`, `useMcpConnection`(MCP 도구), `useSkill`, `useSubagent`, `usePersistentState`, `useDataWriter`(구조화 데이터를 클라이언트 UI로) |
| 호출 방식 | CLI(`flue run`), HTTP/webhook 엔드포인트, Channels(Slack, Teams, Discord, GitHub 이벤트), 클라이언트 SDK |
| 패키지 | `@flue/runtime`, `@flue/vite`, `@flue/cli`, `@flue/sdk`, `@flue/react`, `@flue/postgres`, `@flue/opentelemetry` |
| 빌드·배포 | Vite 플러그인. Node 타깃은 `dist/server.mjs`(PORT 기본 3000)와 기존 Node 앱에 넣는 `dist/app.mjs`. Cloudflare 타깃도 있음 |
| 영속화 | `src/db.ts`에서 PersistenceAdapter 설정(PostgreSQL, SQLite). `@flue/postgres` |
| React 연동 | `@flue/react`의 `useFlueAgent`가 내구성 있는 이벤트 스트림을 React 상태로 변환. 메시지는 Flue 고유 타입이며 파트는 `text`·`reasoning`·`dynamic-tool`·`file`. 인증 토큰은 `createFlueClient({ url, token })`로 전달. 서버 쪽 `useDataWriter`로 쓴 데이터 파트의 클라이언트 표현은 PoC로 확인 |
| 사례 | Cloudflare 내부 에이전트 도구에 사용됨(발표 자료) |

**우리 결정에 영향을 주는 점**

- 채팅 화면이 없다 → 화면은 따로 만든다(assistant-ui).
- 사용자 인증·대화 소유권 기능을 찾지 못했다 → Flue의 app.ts에서 JWT 미들웨어로 직접 처리한다.
- A2UI, AG-UI, MCP Apps를 지원한다는 자료를 찾지 못했다 → 표준은 어댑터로 붙인다.
- 2.0에서 호환이 깨졌고(`app.ts` 필수, 영속 스키마 v5→v8 초기화) 현재 2.3.0이다 → 버전을 고정한다. README에서 실험 단계 경고 문구는 확인하지 못했다.
- 라이선스는 Apache-2.0이다(GitHub API, npm, README 일치).
- 망분리에서는 Node 타깃만 현실적이다.

**B-2. MCP·A2A·라우팅·인증 (추가 조사)**

| 항목 | 내용 |
| --- | --- |
| MCP | 클라이언트만 제공(공식 문서 확인). `useMcpConnection({ name, url, auth, headers, tools, transport, optional })`로 원격 서버의 도구를 `mcp__<서버>__<도구>` 이름으로 붙인다. `auth`는 문자열 또는 요청마다 평가되는 함수, `headers`는 고정값(자격 증명은 `auth` 권장), `tools`는 허용 목록(없는 이름을 쓰면 오류), `optional: true`면 연결 실패 시 도구 없이 진행. 전송은 streamable-http(기본)와 sse. 연결은 제출마다 읽고 인스턴스 메모리 수명 동안 재사용하며 `auth`만 요청마다 해석 |
| MCP 서버·A2A 노출 | 제공하지 않음. 공식 문서는 앱이 직접 MCP 서버를 만들 수 있다고만 언급 |
| 라우팅 | `src/app.ts`가 라우트 지도다. Hono는 기본일 뿐 fetch 호환 앱이면 된다. 에이전트는 `createAgentRouter(Agent)`로 직접 마운트한다(자동 마운트 없음). 경로는 `POST /:id`(202), `GET /:id`, `HEAD /:id`, `POST /:id/abort`, `GET /:id/attachments/:attachmentId`. 마운트 위치는 자유롭고 대화는 에이전트 정체성으로 키가 정해진다 |
| 인증 | 라우터에는 인증이 없다("URL에 닿는 누구나 그 대화와 이야기할 수 있다"). 마운트 앞에 Hono 미들웨어를 붙이고, `/*` 패턴으로 첨부 경로까지 덮는다. 인증(누구인가)과 인가(이 대화 id에 접근 가능한가)를 모두 해야 한다. CORS 헤더도 없어 교차 출처면 직접 추가하고 `Stream-Next-Offset`, `Stream-Up-To-Date`, `Location`을 노출해야 하며, 같은 출처면 불필요 |
| 커스텀 라우트 | `app.ts`에 일반 Hono 라우트를 추가할 수 있다(예: 헬스 체크는 기본 제공 없음). 서버 코드에서 `dispatch(agent, { id, message })`로 에이전트를 호출할 수 있다(접수 시점에 반환, 마운트하지 않은 내부 에이전트도 가능) |
| 요청 헤더 보존 | Cloudflare 문서: 접수 후에는 원래 헤더·쿠키·쿼리·본문을 보존하지 않는다(접수 전 미들웨어만 원본 요청을 본다). Node 문서에는 언급이 없다. 에이전트는 `{ id }`와 `useInitialData()`(비밀 채널 아님)를 받을 뿐 호출자 신원 API는 문서에 없다 |
| 클라이언트 SDK | `createFlueClient({ url, token })`의 `send`, `wait`, `observe`, `history` |

**결론:** Flue 자체에는 MCP 서버·A2A 입구가 없다. `app.ts`가 fetch 호환 앱이라 MCP는 `@modelcontextprotocol/hono`로 올릴 길이 있지만, A2A 공식 JS SDK는 Express 기반이라 Hono에 바로 올리기는 어렵다. 이 조합은 PoC로 확인해야 한다.

| 인프라 | 연 12,000~24,000달러 (K8s, PostgreSQL, 관측) |
| 인력 | 플랫폼 엔지니어 1.5~3명 규모가 필요하다고 봄 |
| 플러그인 유지보수 | 커뮤니티 플러그인 300개 중 새 릴리스 후 6개월 안에 업데이트되는 것은 40% 미만. 커스텀 플러그인은 릴리스당 2~5일 점검 |
| 업그레이드 사례 | 새 백엔드 시스템 전환에 일주일, 한 팀이 메이저 버전 업그레이드에 6주를 썼다는 보고 |
| 현황 | 신규 프론트엔드 시스템이 2026년 3월 기본값이 됨. 사내 사용률이 평균 10%라는 글도 있음 |

**D-3. Refine 설명과 우리 구조에의 매핑**

Refine은 내부 도구, 관리 화면, 대시보드, B2B 앱을 만드는 헤드리스 React 메타 프레임워크(MIT)다. 비즈니스 로직을 UI·라우팅과 분리하고, 데이터·인증·권한·i18n·실시간·감사 로그를 provider로 교체한다.

| Refine 구성 | 우리 구조 |
| --- | --- |
| `authProvider` | BFF의 OIDC 세션 |
| `accessControlProvider` | 권한 판정 API(Casbin) |
| `dataProvider` | Spring REST |
| resources | 메뉴 API가 내려주는 권한별 목록으로 동적 구성 |
| 신청 화면 | RJSF |
| 채팅 | assistant-ui |

**D-4. 폼 라이브러리**

| 영역 | 후보 | 메모 |
| --- | --- | --- |
| React | RJSF | schema와 uiSchema 2개를 입력으로 받고, 조건부 필드·검증·테마 통합을 지원. Backstage Scaffolder도 내부에서 사용. **채택** |
| Vue | JSON Forms (`@jsonforms/vue`) | 커스텀 렌더러 등록 가능. Vuetify 렌더러는 프리뷰 상태 |
| Vue | vue3-form-render | Ant Design Vue에 의존 |
| 기타 | Formily, amis, DivKit, React-admin | 이름만 후보. 조사하지 않았다 |

**D-5. Vue 대안 (채택하지 않음)**

- Refine 같은 헤드리스 메타 프레임워크는 찾지 못했다.
- Vue Vben Admin v5: 동적 메뉴, 권한 검증(버튼 단위 포함), 다중 테마, 다크 모드. Ant Design Vue, Element Plus, Naive UI, TDesign 중 선택. 백엔드가 라우트 테이블을 내려주는 BACK 모드 지원. MIT.
- Vben은 템플릿을 복제해 시작하는 방식이라 업스트림을 따라가기 어렵다(v2에서 v5는 호환 안 됨). 커뮤니티와 문서는 중국어권 중심이다.
- Vue용 성숙한 채팅 라이브러리를 확인하지 못했고, Flue도 React 바인딩만 있어 `@flue/sdk`를 Vue composable로 감싸야 한다.

**D-6. 마이크로 프론트엔드는 지금 과설계다**

- 필요한 경우는 여러 팀이 화면을 독립 배포해야 할 때뿐이다.
- 동적 메뉴는 SPA 하나로 충분하다: 메뉴 API(권한 필터링) → 라우트 레지스트리 → lazy import.
- 신청 유형이 늘어도 스키마만 추가하면 되므로 화면 코드를 나눠 배포할 이유가 거의 없다.
- 팀 단위 분리가 생기면 그때 Module Federation을 도입해도 늦지 않다.

## 부록 E. 인증·인가 상세

**E-1. 앞단이 맡는 일 (웹 BFF, Flue, 백엔드)**

Flue는 대화를 세션 ID 단위로 저장할 뿐이고, 라우터에 인증이 없다. 사용자·인증·소유권 기능은 찾지 못했다. 아래는 맡는 곳을 나눈 것이다. 웹은 Spring BFF, 에이전트 입구는 Flue, 최종 판정은 백엔드 API다.

| 할 일 | 맡는 곳 | 방법 |
| --- | --- | --- |
| 웹 로그인 | 웹 BFF | OIDC Authorization Code + PKCE. 로그인 세션은 서버에 보관하고, SPA에는 짧은 수명의 접근 토큰을 전달 |
| 에이전트 입구 인증 | Flue (`app.ts`) | Hono `hono/jwk` 미들웨어로 JWT를 IdP 공개키(JWKS, `jwks_uri`)로 직접 검증. `alg` 허용 목록(비대칭만), `verification.iss`·`aud` 설정, 위임 범위(scope)는 `c.get('jwtPayload')`로 확인. `/agents/*`처럼 `/*` 패턴으로 첨부 경로까지 덮음 |
| 세션 ID | Flue | 서버가 생성(예: `{sub}:{uuid}`). 대화 id는 URL 경로에서 호출자가 정하므로, 미들웨어가 경로의 id를 꺼내 소유권을 검사한다. Flue 문서도 id를 사용자에서 유도하거나 서버가 발급하라고 안내 |
| 소유권 | Flue | CNPG에 `(conversation_id, user_id, created_at)` 테이블. 스트림 재연결·이력 조회를 포함해 모든 요청에서 확인 |
| 대화 목록 | Flue | `GET /threads`가 내 대화만 반환. assistant-ui의 thread list adapter를 이 API에 연결 |
| 업무 호출 권한 | 백엔드 API | 사용자 토큰으로 실행하고 최종 판정은 Casbin. 서비스 계정을 공용으로 쓰는 것은 권한을 우회하므로 금지 |
| 대리 호출 기록 | 백엔드 API | 토큰에 대리 주체(`act`)와 위임 범위를 담고 감사 로그에 남김 |
| 샌드박스·파일 | Flue | 세션별 격리 여부를 확인. 공유 볼륨이면 경로를 사용자별로 분리 |
| 직접 접근 차단 | 인프라 | 백엔드 API는 웹 BFF·Flue에서 오는 요청만 허용(NetworkPolicy, 가능하면 mTLS). Flue는 외부에 노출되므로 JWT 검증이 방어선 |
| CSRF | 웹 BFF | 웹 BFF가 토큰을 발급. Bearer 토큰을 헤더로 보내는 채팅·MCP·A2A 호출은 쿠키를 쓰지 않아 CSRF 대상이 아니다 |

**E-2. 인증을 둘 위치**

|  | Flue 서버(Hono 등)에 내장 | 별도 BFF(게이트웨이) |
| --- | --- | --- |
| 인증·인가 위치 | Flue 프로세스 안 | BFF. Flue는 실행만 담당 |
| 장점 | 단계가 적고 구성이 단순. 외부 에이전트가 직접 호출할 수 있음 | Spring Security 사용, 다른 서비스와 정책 통일, 게이트웨이 재사용 |
| 단점 | 인증 로직이 TypeScript 쪽에 흩어짐 | 홉이 하나 늘고 SSE 설정 필요 |
| 선택 | **에이전트 입구(채팅 UI, MCP, A2A)에 채택** | **웹(Refine)에 채택** (웹 BFF) |

Flue 앞단(Ingress나 게이트웨이)을 지날 때 SSE를 지키는 설정은 응답 버퍼링 끄기, 응답 타임아웃 늘리기, 재연결 헤더(`Last-Event-ID`) 전달이다. 웹 BFF는 SSE를 중계하지 않으므로 이 부담이 사라진다.

**E-3. 권한 판정 위치**

- 업무 규칙과 최종 권한 판정은 백엔드 API(Casbin)에 둔다. BFF의 검사는 화면 편의용이며, BFF가 뚫리더라도 백엔드가 막는다. 프론트엔드는 결과만 받는다. 메뉴 API가 권한별로 필터링한 목록을 내려준다.
- Refine의 `authProvider`는 웹 BFF 세션에, `accessControlProvider`는 권한 판정 API에 연결한다.
- 채팅 안에서 띄우는 폼도 같은 권한 검사를 거친다. 채팅이 권한 우회 경로가 되면 안 된다.

**E-4. 토큰 구조 (웹·채팅 UI)**

- 웹 BFF가 OIDC 로그인 후 짧은 수명의 접근 토큰을 SPA에 준다. assistant-ui가 이를 Bearer로 Flue에 보낸다.
- 초기안(쿠키만 브라우저에 둔 방식)에서 바뀔 점: 토큰이 브라우저 메모리에 들어온다. 그래서 수명을 짧게, 대상(`aud`)을 에이전트 전용으로 제한하고, 메모리에만 두며 로컬 저장소에는 두지 않는다. 갱신은 웹 BFF가 맡는다.
- Flue는 IdP 공개키(JWKS)로 서명, 만료, 대상(`aud`), 발급자를 검증한다(Hono `jwk`: `alg`는 비대칭 허용 목록, `exp`·`nbf`·`iat`는 기본 검증, `iss`·`aud`는 설정해야 검증).
- 이 토큰의 `aud`는 에이전트 입구다. 백엔드에는 그대로 넘기지 않는다. MCP 인가 문서는 서버가 자신을 대상으로 하지 않는 토큰을 받지 말고 token passthrough를 하지 말라고 한다. Flue가 토큰 교환(RFC 8693)으로 `aud`=백엔드이고 `act`를 가진 토큰을 새로 받는다.
- 접수 후 에이전트에는 원래 헤더가 없으므로, 교환한 토큰은 앱 저장소(암호화, 짧은 TTL)에 대화 id(또는 `sub`) 키로 두고 `useMcpConnection`의 `auth` 함수가 요청마다 꺼낸다. 메시지 본문이나 `useInitialData`(비밀 채널 아님)에는 넣지 않는다.

**E-5. 외부 사용자 에이전트와 대리 호출**

- agent card는 공개해야 한다(호출자가 인증 방식을 알아야 하므로). 호출은 항상 인증한다.
- 사용자를 대신한 호출은 사용자 신원으로 실행한다. 토큰 교환으로 받은 토큰에 대리 주체(`act`)와 위임 범위를 담는다. 백엔드가 "에이전트가 사용자를 대신했다"는 사실을 감사 로그에 남긴다.
- 위험한 작업은 사용자의 재확인이 필요하다. A2A에서는 작업 상태를 '입력 필요'(`TASK_STATE_INPUT_REQUIRED`, 인증이면 `TASK_STATE_AUTH_REQUIRED`)로 돌려 상대 에이전트가 사용자에게 다시 묻게 하고, MCP에서는 elicitation으로 요청한다. 단 form 모드는 평면 스키마만 되고 민감 정보는 URL 모드를 써야 한다.
- MCP 입구를 직접 노출하면 사양대로 401 + `WWW-Authenticate`의 `resource_metadata`로 보호 리소스 메타데이터(RFC 9728)를 안내하고, 토큰 `aud`가 자기 자신인지 검증해야 한다.
- 외부 입력은 검증되지 않은 입력으로 본다(프롬프트 주입). 권한 검사는 에이전트가 아니라 도구 층에 둔다.
- 토큰을 업무 API까지 넘기는 방법: 접수 후 원래 헤더가 없다는 것은 Cloudflare 문서에 명시돼 있고 Node는 문서에 없다. MCP 연결의 `auth`는 요청마다 평가되는 함수이므로 저장소 조회 방식으로 주입한다(위 참고). 저장소 방식이 Node 타깃에서 동작하는지 PoC에서 확인한다.

## 부록 F. 빌드·컨테이너·배포 상세

**F-1. 빌드: web jar**

Jib은 Node를 실행할 수 없다. 그래서 Gradle이 SPA를 먼저 빌드해 jar에 담고, Jib은 그 결과를 이미지로 만든다. SPA는 Gradle 모듈(`web`)에서 jar로 만들고 BFF(`portal`)가 의존한다. Spring Boot가 `META-INF/resources/`를 정적 경로로 자동 인식하므로 별도 설정이 없다. 아래는 요지 예시다.

```kotlin
// settings.gradle.kts
include("web", "portal")

// web/build.gradle.kts
plugins { java; id("com.github.node-gradle.node") version "7.1.0" }
node { download = true; nodeProjectDir = file("frontend") }  // 망분리: distBaseUrl을 내부 미러로
val pnpmBuild by tasks.registering(com.github.gradle.node.pnpm.task.PnpmTask::class) {
    dependsOn(tasks.pnpmInstall); args = listOf("build")
    inputs.dir("frontend/src"); outputs.dir("frontend/dist")
}
tasks.jar { dependsOn(pnpmBuild); from("frontend/dist") { into("META-INF/resources") } }

// portal/build.gradle.kts
dependencies { implementation(project(":web")) }
jib {
    from.image = "registry.internal/eclipse-temurin:21-jre"
    to.image = "registry.internal/voc/portal"
    container { ports = listOf("8080"); jvmFlags = listOf("-XX:MaxRAMPercentage=75") }
}
```

Jib이 의존 jar를 별도 레이어로 넣기 때문에, 프론트엔드만 바뀔 때는 그 레이어만 다시 푸시된다.

**F-2. Skaffold: 두 이미지를 함께 관리**

Flue는 Jib으로 빌드할 수 없으므로 Dockerfile로 따로 빌드한다.

```yaml
build:
  artifacts:
    - image: registry.internal/voc/portal
      jib: { type: gradle, project: portal }
      sync: { auto: true }
    - image: registry.internal/voc/agent
      docker: { dockerfile: agent/Dockerfile }
  local: { push: false }
```

**F-3. 배포 구성 옵션**

| 구성 | 장점 | 단점 |
| --- | --- | --- |
| 단일 앱(SPA 포함) | 컨테이너 1개, CORS·CSRF 단순 | 화면만 고쳐도 BFF 재배포. 정적 캐시 헤더를 직접 설정(해시 에셋은 장기 캐시, index.html은 no-cache). **채택** |
| nginx 사이드카로 SPA 분리 | 이미지 분리 | BFF가 localhost로 한 번 더 프록시. 이득이 작음 |
| initContainer + emptyDir | 이미지는 분리하고 서빙은 Spring | Spring이 `file:` 경로를 서빙하도록 설정 필요 |
| Flue를 같은 Pod 사이드카로 | localhost 호출로 노출 없음. NetworkPolicy·mTLS 불필요 | BFF와 Flue가 함께 확장됨. 부하 특성이 다름. PoC에 적합 |
| Flue 별도 Deployment | 따로 확장 | NetworkPolicy·mTLS로 직접 접근 차단 필요. **채택** |

**F-4. 개발 루프**

- 프론트엔드: 로컬에서 `pnpm dev`(Vite)를 띄우고 `/api`, `/agents`, `/login`을 `localhost:8080`(포트포워딩)으로 프록시한다. HMR이 되므로 Jib을 다시 돌릴 필요가 없다.
- 백엔드: `skaffold dev`로 Java 변경을 자동 재빌드·배포한다.
- CI: `skaffold build` 한 번으로 SPA 빌드, jar, 이미지까지 처리된다.

**F-5. 주의**

- 망분리에서는 Nexus에 Node 배포판 미러와 npm 레지스트리(`.npmrc`) 두 가지가 모두 필요하다.
- `node_modules`가 이미지에 들어가지 않도록 `dist`만 jar에 담는다.
- SSE는 Flue로 직접 가므로 Spring 웹 BFF는 중계하지 않는다. Flue 앞단(Ingress)에서 버퍼링을 끄고 타임아웃을 길게 설정한다.
- Flue의 빌드 타깃은 Node로 고정하고, 배포 전에 `flue dev --target`으로 로컬에서 확인한다(런타임을 잘못 고르면 에이전트가 조용히 깨진다는 주의가 있다).

**F-6. Ingress 경로와 접근 제한**

| 경로(예시) | 대상 |
| --- | --- |
| `/`, `/api/*`, `/login` | Spring 웹 BFF (SPA 포함) |
| `/agents/*` | Flue (채팅 UI) |
| `/mcp`, `/a2a`, `/.well-known/agent-card.json` | Flue (MCP·A2A 입구). 경로 이름은 예시이며 확정하지 않았다 |

- 같은 도메인이면 CORS가 필요 없다.
- 백엔드 API는 NetworkPolicy로 웹 BFF와 Flue에서 오는 요청만 받는다(가능하면 mTLS).
- Flue는 Ingress를 통해 브라우저와 외부 에이전트의 직접 호출을 받는다. 이 구조에서는 Spring Pod의 사이드카 배치(localhost 호출)가 맞지 않고, JWT 검증이 방어선이 된다.

## 부록 G. 최종 UX 방향 (멘탈 모델)

**G-1. 우리 가정의 점검**

가정: Flue가 사용자가 신청·설정할 수 있는 업무 목록과 이력을 MCP 서버, A2A, 채팅 UI로 단계적으로 제공한다. 지난 채팅 세션과 신청 이력은 이후 신청·설정 화면 이동에 도움이 되고, 사용자는 채팅의 안내로 고전 웹 기능을 수행한다.

점검 결과: 대체로 최신 흐름과 맞다. 다만 "안내받아 웹에서 수행"하는 단계는 중간 단계이고, 논의는 그보다 더 나아가 있다.

- 맞는 부분: 2026년의 일반적인 패턴은 기존 UI 위에 대화 계층을 얹는 것이다. 사용자는 클릭으로도, 말로도 같은 결과에 닿는다.
- 셀프 서비스 포털 시장도 같은 방향이다. ServiceNow는 지식·카탈로그를 담은 AI 네이티브 서비스 경험으로 서비스 포털을 대체하는 제품(Employee Slate)을 내놓았다.
- 사용자의 개인 에이전트가 우리 MCP 서버를 호출하는 구조도 맞다. 이를 AX(Agent Experience)라 부른다. 앱의 사용자가 사람뿐 아니라 프로토콜로 상호작용하는 AI 에이전트이기도 하다는 관점이다.
- 더 나아간 논의: 의도 기반 위임(사용자가 결과를 말하면 시스템이 절차를 정한다)과, 사용자의 역할이 조작자에서 감독자로 바뀐다는 관점이다.

**G-2. 세 단계 비교**

핵심은 "누가 일을 하는가"가 바뀐다는 점이다.

|  | 고전 웹 | 과도기 (이 ADR의 시작점) | 최종 |
| --- | --- | --- | --- |
| 일하는 주체 | 사용자 | 사용자(안내를 받음) | 에이전트 |
| 사용자가 하는 일 | 찾기·입력·제출 | 말하기·확인·제출 | 맡기기·승인·확인 |
| 화면의 역할 | 작업 공간 | 작업 공간 + 안내 | 지시·감독 공간 |
| 우리 시스템이 내놓는 것 | 웹 화면 | 화면 + 채팅 | 기능 목록(MCP) + 확인 화면 |

"개발 서버 권한 신청"으로 풀어 보면 다음과 같다.

1. **고전 웹: 내가 직접 서류를 쓴다.** 메뉴를 찾고, 화면을 열고, 칸을 채워 제출한다. 어디로 가서 무엇을 쓸지는 사용자가 알아야 한다. 화면은 일하는 곳이다.
2. **과도기: 안내원이 서류를 찾아 준다.** "권한 신청하고 싶어"라고 말하면 채팅이 맞는 신청서를 찾아 미리 채워 준다. 확인과 제출은 여전히 내가 고전 화면에서 한다. 길 찾기와 입력은 줄었지만 일하는 방식은 그대로다.
3. **최종: 비서에게 맡긴다.** 사용자는 원하는 결과와 허락 범위만 말한다. 예: "다음 주까지 개발 서버 쓸 수 있게 해 줘, 승인 필요하면 물어봐." 계획을 세우고, 신청하고, 진행을 지켜보는 일은 에이전트가 한다. 사용자는 중요한 순간에 승인하고 끝나면 결과만 확인한다. 화면은 맡기고 확인하는 곳이다.

**한 줄 정리:** 고전 웹은 "내가 한다", 과도기는 "도움 받아 내가 한다", 최종은 "맡기고 내가 확인한다".

**G-3. 최종 단계에서 중요해지는 것**

- 시스템의 문 앞 손님이 바뀐다. 포털에 사람만 오는 게 아니라 사용자의 개인 비서(사내 에이전트, Claude 등)가 찾아온다. 그래서 화면보다 "할 수 있는 일 목록"(MCP)을 잘 내주는 쪽이 된다.
- 화면은 필요할 때만 잠깐 만들어진다. 승인 카드나 선택지처럼 그 순간에 필요한 화면만 뜨는 생성형 UI가 논의된다.
- 믿고 맡기기 위한 장치가 핵심 화면이 된다: 허락 범위, 승인 지점, 진행 상황, 처리 내역(영수증), 되돌리기, 사람에게 넘기기. 실행 이력은 채팅과 분리해 따로 보여 주는 편이 좋다는 주장도 있다.
- 기억도 화면의 일부가 된다. 지난 대화와 신청 이력을 바탕으로 비서가 판단하므로, 사용자가 그 기억을 보고 고칠 수 있어야 한다.

**G-4. 주의할 점**

- 하이브리드 함정: 채팅과 화면이 같은 작업을 서로 차지하면 사용자가 혼란스러워한다. 화면과 대화 사이의 조율(넘기는 방식)이 핵심이다. 그래서 채팅은 찾기와 값 채우기, 제출과 확인은 폼으로 역할을 나눠 둔다.
- 검토 피로: AI가 한 일을 확인하는 것이 직접 하는 것보다 어려울 수 있어 형식적인 승인에 그칠 수 있다. 확인 화면은 요약과 변경점을 또렷하게 보여 줘야 한다.
- 시장 전망은 엇갈린다. Gartner는 2026년 말까지 엔터프라이즈 앱의 40%에 작업 특화 에이전트가 들어간다고 보지만, 비용·가치·위험 통제 부족으로 2027년 말까지 에이전트 프로젝트의 40% 이상이 취소될 수 있다는 전망도 함께 내놓았다.

**G-5. 이 ADR에 주는 시사점**

- 지금의 하이브리드 결정은 유효하다. 정확한 제출은 폼이 맡고, 채팅은 찾아 주는 역할이다.
- 다음 단계는 두 가지다. 하나는 에이전트용 입구(MCP, A2A)를 열어 사용자 에이전트가 직접 쓰게 하는 것이고, 다른 하나는 실행 이력·확인·되돌리기를 보여 주는 화면을 따로 만드는 것이다.
- 화면(GUI)의 중심이 "입력 화면"에서 "확인·감독 화면"으로 옮겨 간다.

## 부록 H. 입구, 레이어, 도구 배치

**H-1. 입구 세 개는 같은 도구를 쓴다**

채팅 UI, MCP, A2A가 같은 도구·정책·이력을 쓰면 결과는 같다. 다만 에이전트의 응답 방식은 입구마다 달라야 한다.

| 구분 | 직접 채팅 UI | 사용자 에이전트(MCP·A2A) |
| --- | --- | --- |
| 대화와 기억의 주인 | 우리 | 사용자 에이전트. 우리는 요청 한 조각만 봄 |
| 화면과 승인 UX | 우리가 그림 | 상대 앱이 그림. 승인은 elicitation이나 Apps로 요청 |
| 들어오는 입력 | 자연어 프롬프트 | 주로 MCP 도구 호출(스키마로 정해진 인자). A2A는 작업 단위 메시지 |
| 여러 시스템 조합 | 우리 범위 안에서만 | 사용자 쪽에서 우리와 다른 서비스를 엮음 |
| 응답 형식 | 사람이 읽는 글과 화면 조각 | 기계가 읽는 구조화된 결과 |
| 승인 방식 | 그 자리에서 승인 카드 | 작업 상태를 '입력 필요'로 돌려 상대 에이전트가 다시 묻게 함 |
| 신원 | 사용자 본인 | 대리 요청. 위임 범위와 감사 기록이 필요 |

- 입력이 프롬프트보다 구조화된 호출에 가까워지므로 결정성은 오히려 좋아진다.
- 직접 채팅 UI는 사용자 에이전트가 없거나 약한 사용자를 위한 기본 입구로 남는다.
- 같은 MCP 도구와 같은 JSON Schema를 쓰면 차이는 입구에만 생긴다.
- 권한 검사는 에이전트가 아니라 도구 층에 둔다(Casbin 판정, 소유권 확인). 어느 입구로 들어와도 같은 규칙을 지킨다.

**H-2. 도구는 한 곳에 두고, self 등록은 하지 않는다**

```text
백엔드(Spring) 도구 서버: 도구 + JSON Schema + Casbin 검사 + 감사 로그
      ▲                              ▲
  Flue (useMcpConnection)      외부 사용자 에이전트 (MCP · A2A 입구)
```

- 도구의 실제 구현과 권한 검사는 백엔드에 한 벌만 두고, Flue와 외부 에이전트 입구가 그것을 부른다.
- self 등록(Flue가 자기 자신의 MCP 서버를 네트워크로 다시 호출)을 하지 않는 이유: 같은 프로세스 안에서 네트워크를 한 번 더 돌고, 인증을 두 번 거치고, 토큰을 한 번 더 넘겨야 하며, 오류와 지연이 늘어 추적하기 어렵다.
- Flue 안에서만 쓰는 도구(대화 요약, 폼 값 채우기 등)는 `useTool`로 직접 만든다. 업무 실행·권한이 걸린 도구는 모두 백엔드에 둔다.
- 백엔드 MCP 서버는 Spring AI의 MCP 서버 스타터(`spring-ai-starter-mcp-server-webmvc`, `spring.ai.mcp.server.protocol=STREAMABLE`)로 만들 수 있다. OAuth2 보호는 커뮤니티 모듈(`org.springaicommunity:mcp-server-security`)을 쓰며 WebMVC·JWT 전용이다. 이 모듈은 Spring AI가 공식 보증하지 않고 버전 매트릭스가 문서마다 달라(공식 문서는 Spring AI 2.0.2 기준) 도입 시 Spring AI 버전과 맞춰 고정한다. `validateAudienceClaim(true)`로 `aud` 검증을 켠다.
- 외부 에이전트의 MCP 입구를 Flue에 둘지, 백엔드 MCP 서버에 직접 연결할지는 확정하지 않았다(후속 과제).

**H-3. 레이어 구분**

| 계층 | 맡는 일 | 위치 |
| --- | --- | --- |
| 입구 | Refine(REST), MCP 도구, A2A. 모양만 다름 | 웹 BFF, 에이전트 BFF |
| BFF | 로그인(OIDC)·세션, 사용자 신원 전달, 응답 모양 바꾸기, 묶어 호출하기 | 웹 BFF(Spring), Flue |
| 정책 | 권한 판정(Casbin), 대화·신청 소유권, 감사 로그 | 백엔드 API (대화 소유권은 Flue 미들웨어) |
| 업무 | 애플리케이션 서비스(신청·승인·실행), 스키마 검증 | 백엔드 API |
| 데이터 | 업무 데이터, 세션 | PostgreSQL(CNPG) |

- 핵심 업무 규칙과 권한 판정은 업무·정책 층에 둔다. 입구나 에이전트에 두면 입구마다 규칙이 갈라진다.
- Flue는 입구 중 하나이며, 판단은 하되 권한은 갖지 않는다. 에이전트가 만든 값도 서버가 같은 스키마로 다시 검증한다.

**H-4. 웹 BFF와 에이전트 BFF**

```text
웹 BFF(Spring) ─┐
                ├→ 백엔드 API: 업무 로직 + 권한 + 스키마 검증 + 감사
에이전트 BFF ───┘
(Flue: MCP · A2A · 채팅 UI 백엔드)
```

- 권한은 백엔드에서 최종 강제한다. BFF의 검사는 화면 편의용이다. 어느 BFF가 뚫리더라도 백엔드가 막아야 한다.
- 사용자 신원을 끝까지 전달한다. 서비스 계정을 공용으로 쓰지 않는다.
- 에이전트 호출은 대리로 표시한다. 토큰에 대리 주체(`act`)와 위임 범위를 담고 백엔드가 감사 로그에 남긴다.
- BFF는 얇게 둔다. 응답 모양 바꾸기, 세션, 묶어 호출하기만 하고 업무 규칙은 넣지 않는다.
- Flue의 MCP·A2A 입구는 직접 구현해야 한다(공식 제공 없음). MCP는 `@modelcontextprotocol/hono`, A2A는 `@a2a-js/sdk`(Express 기반)로 구현하되 Hono 마운트가 안 되면 앞에 얇은 어댑터를 둔다.
- 채팅 UI의 인증 경로는 웹 BFF가 인증해 준 토큰을 Flue가 검증하는 방식으로 확정했다. A2A까지는 Flue가 JWT를 직접 검증한다.

**H-5. 고전 GUI와 API 노출**

- 고전 GUI는 계속 필요하다. 정확하고 반복되는 작업, 승인 확인, 이력 조회, 에이전트 실패 시의 우회로가 GUI의 몫이다.
- 같은 업무 기능을 REST(Refine)와 MCP(에이전트) 두 모양으로 노출하고, 요청·응답 스키마는 JSON Schema 하나에서 만든다. 그러면 둘이 어긋날 일이 없다.

## 부록 I. 도입 순서와 단계별 기술 (1인 개발 기준)

백엔드 MCP 서버의 모듈 구조와 인가 상세는 [0002](0002-spring-mcp-server-design.md)를 따른다.

**원칙:** 도구·권한·감사 로그는 1단계에 한 벌만 만들고, 이후 단계는 입구만 추가한다. 1인 개발이면 2~3단계까지를 첫 목표로 한다.

**첫 유저 에이전트:** Claude Code(MCP 클라이언트). 사용자가 이미 갖고 있어 UI를 만들 필요가 없고, 입구는 백엔드 MCP 서버 하나면 된다. 채팅 UI와 A2A는 구축 비용과 SDK 마찰 때문에 가장 나중에 둔다.

**개방 순서:** 관리자(VOC 처리 등) → 알파(일부 사용자, 읽기 도구) → 베타. 관리자 단계에서 읽기 전용 도구로 도구·스키마·감사 로그를 먼저 검증하고, 쓰기 도구는 승인 지점을 두고 연다. 위험 작업은 도구가 직접 실행하지 않고 폼 링크를 돌려준다.

| 단계 | 활용 기술 | 핵심 구현과 역할 |
| --- | --- | --- |
| 1. 백엔드 API | Spring Boot, PostgreSQL(CNPG), JSON Schema 검증, Casbin | 업무 로직, 스키마 검증, 권한 최종 판정, 감사 로그 테이블(컬럼은 아래 "감사 로그 스키마"). 이후 모든 입구가 재사용 |
| 2. MCP 서버 (관리자, 읽기 전용) | Spring AI MCP(WebMVC, Streamable HTTP), 커뮤니티 `mcp-server-security`(JWT), IdP | VOC 조회·요약·분류 도구. `aud` 검증을 켜고 도구마다 권한 검사와 감사 기록. Claude Code가 직접 접속 |
| 3. 웹 GUI 최소판 (관리자) | Spring Security OIDC(웹 BFF), Refine, shadcn/Tailwind, RJSF | 로그인, VOC 목록·상세, 처리 내역·승인·되돌리기 화면. 입력 화면보다 에이전트가 한 일을 확인하는 감독 화면이 먼저 |
| 4. 쓰기 도구 + 폼 링크 | MCP 도구 + RJSF 폼 URL | 도구는 값을 채워 폼 링크만 반환하고 제출은 사용자가 폼에서 확인 후 실행. 서버가 스키마로 재검증 |
| 5. 사용자 알파·베타 | 토큰 교환(RFC 8693), `act` 클레임, 사용자용 신청 화면 | 사용자별 권한 적용, 대리 호출 기록, 일반 사용자 신청 화면 개방 |
| 6. 채팅 UI·A2A (후순위) | Flue(`app.ts`, Hono `jwk`), assistant-ui, `@flue/react`, `@modelcontextprotocol/hono`, `@a2a-js/sdk` | Claude Code가 없는 사용자용 채팅. Flue는 2단계 MCP 서버의 클라이언트로 붙고 JWT 검증과 대화 소유권을 담당 |

**감사 로그:** DB에 기록한다. 3단계의 승인·되돌리기 화면이 이 기록을 읽어 만들어진다. 백엔드 API가 업무 트랜잭션 안에서 기록하므로 웹 BFF 경로도 빠지지 않는다. 읽기 전용 단계부터 넣는다. 컬럼과 규칙은 아래 "감사 로그 스키마"를 따른다.

**MCP 서버 구현 위치:** Flue가 아니라 백엔드(Spring AI MCP)다. Flue의 MCP 지원은 클라이언트 기능뿐이다(메인 페이지의 "MCP Servers"는 Flue가 붙는 대상 서버를 뜻하며, 공식 문서에 서버 노출 기능은 없다). 그래서 Flue 없이 1단계부터 열 수 있고, Flue는 6단계에서 같은 서버에 클라이언트로 붙는다.

**주의:** 사용자가 쓰는 Claude Code에 MCP 연결 안내와 권한 범위(scope) 문서가 필요하다. 인증은 관리자 단계에서 IdP 클라이언트 하나로 시작하고, 토큰 교환과 `act` 기록은 외부 사용자를 열기 전(5단계)까지 미룬다.

**작업 분류와 승인 원칙 (2026-11-03 결정)**

사람이 직접 하는 일은 바로 실행한다. AI(MCP)가 하는 쓰기는 세 가지로 나눈다.

1. 원래 승인이 필요한 작업: AI든 사람이든 승인을 거친다.
2. 사람이 바로 하던 중요한 작업: AI는 초안만 만들고, 사람이 확인해 승인한다(HIL, 사람이 중간에 확인하는 방식).
3. 사람이 바로 하던 사소한 작업: AI도 바로 실행한다. 되돌릴 수 있게 `before_values`를 남긴다.

- 작업마다 중요/사소를 표시한다. 표시가 없으면 중요(초안)로 본다. 사소 표시는 쓰기 도구를 여는 때 작업별로 정한다.
- 읽기는 승인 없이 연다.
- "AI가 개입했는가"는 사람이 최종 값을 보고 직접 제출했는지로 가른다. 채팅이 채운 값을 사람이 폼에서 제출하면, 그 제출이 승인이다.
- 사소한 작업까지 매번 승인하면 내용을 안 보고 누르게 되므로(검토 피로) 3번을 둔다.

**승인 규칙**은 비즈니스가 정한다.

- 승인자: 관리자, 특정 등급 이상의 상급자. 둘을 함께 요구할 수도 있다.
- 순서: 사용자 간 승인이 1차, 관리자가 2차다. 순서는 승인 목록의 순서를 따른다.
- 관리자 승인이 필요한지는 관리자가 런타임 설정으로 관리한다. 필수 체크 항목도 비즈니스가 정한다.
- 감사 로그에는 승인 한 번마다 한 줄(`decision`, `approved_by`)을 시간순으로 쌓는다. 단계 컬럼은 두지 않는다. 설정을 바꾼 사실도 한 줄로 남긴다.

**신청서(proposal) 상태 모델 (제안, 1·2번 작업에만 적용)**

에이전트(MCP)든 화면이든 신청은 먼저 `DRAFT`(임시저장)로 등록한다. 등록된 `proposal_id`의 값은 바꾸지 않고, 수정은 새 버전(`proposal_version`)으로 만든다. 사용자가 승인하면 `APPROVED`가 되고, 실행은 승인된 버전에 저장된 값만 쓴다. 승인 뒤에 LLM이나 호출자가 보낸 값은 무시한다. 상태는 `DRAFT` → `APPROVED` → `EXECUTED` / `REJECTED` / `EXPIRED`다. 상태 이름 확정과 만료 정책은 쓰기 도구를 열 때 정한다(후속 항목).

**알파 전환 지표 (초안, 수치 미정)**

- 용도: 알파를 열어도 되는지 정하는 통과 기준(게이트)이다. 개방 후에는 같은 쿼리를 주기로 돌려 상시 감시에도 쓴다. 응답 지연, 토큰 비용 같은 시스템 성능 지표는 범위 밖이다.
- 임계값: 관리자 단계 첫 2주의 기준선을 잰 뒤 정한다.
- 수집: 감사 로그 테이블의 SQL 뷰로 주간 집계한다. OpenTelemetry는 알파 이후 운영 관측이 필요할 때 따로 검토한다.

| 지표 | 의미 |
| --- | --- |
| 도구 호출 성공·실패율, 권한 거부 건수 | 도구 안정성과 권한 설정 오류 |
| 승인 거절률, 수정률 | 제안값과 최종 제출값의 차이(diff) |
| 재분류율 | 에이전트 분류와 사람 최종 분류의 불일치 |
| 건당 처리 시간 | 에이전트 사용 전후 비교 |
| 사고 0건 유지 기간 | 오발송, 권한 우회, 개인정보 노출 |

- 읽기 전용 알파에서 잴 수 있는 것: 호출 성공·실패율, 권한 거부, 활성화, 사고 0건.
- 승인 거절률, 수정률, 재분류율: 승인 단계가 있는 쓰기 도구를 연 뒤(4단계)부터 잰다.
- 활성화(실제로 쓰이는 정도) 지표는 위 5개와 따로 둔다: 주간 활성 사용자 수, 도구별 호출 수(읽기 포함), 재사용 사용자 비율. 정의와 수치는 미정이다.

**감사 로그 스키마 (2026-11-03 결정)**

감사 로그는 작업 단위의 공통 테이블 하나다. 웹 화면 요청과 MCP 도구 호출이 같은 표에 한 줄씩 쌓인다. 줄은 추가만 하고 고치거나 지우지 않는다. 신청서는 승인이 필요한 작업의 한 종류일 뿐이고, 휴면 활성화나 이관 같은 즉시 실행 작업도 같은 표에 기록한다. 컬럼 이름은 약어 없이 쓴다.

| 컬럼 | 설명 | 필수 | 비고 (관련 스펙) |
| --- | --- | --- | --- |
| `id` | 로그 한 줄의 고유 번호 | 필수 | 자체 정의 |
| `occurred_at` | 작업이 일어난 시각 | 필수 | OCSF `time` |
| `user_id` | 권한의 주인인 사용자 | 필수 | JWT `sub`. OCSF `actor` |
| `client_id` | 어떤 앱으로 왔는지(Claude Code, 웹 등) | 필수 | JWT `azp`. 0002가 대리 구분용으로 채택 |
| `action` | 작업 이름(웹, 도구 공통) | 필수 | OTel `gen_ai.tool.name`, `mcp.method.name`. OCSF `api` |
| `resource_type`, `resource_id` | 작업 대상의 종류와 원본 ID | 필수 | OCSF `resources`. MCP `mcp.resource.uri` |
| `result_status` | 성공, 실패, 권한거부 | 필수 | OTel 스팬 상태. OCSF `status` |
| `before_values`, `after_values` | 구조화 필드의 변경 전후. 본문 제외 | 조건부(변경 작업만, 읽기는 NULL) | 자체 정의 |
| `failure_reason` | 실패·거부의 실제 사유. 사용자에게는 404로 숨긴다(0002) | 선택 | OCSF `status_detail` |
| `proposal_id`, `proposal_version` | 신청서 번호와 버전. 신청이 아닌 작업은 NULL | 선택 | 자체 정의 |
| `decision` | 승인, 거절, 수정 | 선택 | 자체 정의 |
| `approved_by` | 승인한 사람. 본인 확인이면 `user_id`와 같다 | 선택 | 자체 정의 |
| `content_hash` | 본문의 SHA-256. 본문 자체는 저장하지 않는다 | 선택 | 자체 정의 |
| `trace_id` | 요청에 있을 때만 저장(NULL 허용) | 선택 | W3C Trace Context. OTel 트레이스 ID |
| `delegated_by` | 대신 행동한 주체. 지금은 NULL로 예약하고 토큰 교환(5단계) 도입 시 사용 | 선택 | RFC 8693 `act` |

**기록 규칙**

- 필수의 뜻: 누가(`user_id`), 언제(`occurred_at`), 무엇을(`action`), 무엇에(`resource_*`), 어떤 앱으로(`client_id`), 결과(`result_status`), 바뀐 것(`before_values`, `after_values`)이다. 실패와 권한거부도 반드시 한 줄을 남긴다. 거부가 반복되면 오사용이나 공격의 신호이고, 실패율은 알파 지표의 재료다.
- 기록 책임: 스키마는 어떤 리소스든 담게 범용으로 둔다. 기록은 자동 일괄 처리가 아니라, 감사가 필요한 서비스가 코드에서 직접 쌓는다. 어떤 서비스가 기록할지는 서비스를 열 때 정한다.
- 읽기: 기록하는 서비스에서는 읽기도 남긴다. 읽기 성공 기록은 런타임 설정으로 켜고 끈다(기본 켬). 쓰기, 실패, 권한거부는 설정과 상관없이 항상 남긴다. 설정을 바꾼 사실도 한 줄로 남겨 읽기 기록이 빈 구간을 설명할 수 있게 한다. 읽기 호출 수는 활성화 지표의 재료다.
- `act` 대신 `azp`: 0002가 토큰 교환을 미룬 것에 맞춘다. 토큰 교환을 도입할 때 0001의 해당 서술을 정리한다.
- 본문: 저장하지 않는다. 변경 전후는 분류, 상태 같은 구조화 필드만 복사하고, 자유 텍스트(VOC 본문)는 원본 ID와 해시만 남긴다. 그래서 마스킹 규칙은 만들지 않는다. 감수하는 점: 원본이 바뀌면 승인 당시 본문은 복원하지 못한다. 해시는 "승인 당시와 같은가"만 알려 준다. 복원이 필요해지면 본문을 별도 표에 두는 방식으로 다시 검토한다.
- 테스트 데이터: 감사 로그와 분리한 별도 표에 모은다. 실제 고객 본문을 써도 되는지는 보안 정책을 확인한 뒤 정하며, 안 되면 마스킹한다.
- 변조 방지: 해시만으로는 DB 직접 수정을 막지 못한다. 최소선으로 애플리케이션 계정에 감사 테이블 `INSERT`만 허용한다(`UPDATE`, `DELETE` 금지).
- 대량 패치: 건별 줄 대신 배치 한 줄(대상 조건, 건수, 스크립트 버전, 전후 체크섬)로 남기고, 필요하면 건별 구조화 필드 변경을 덧붙인다. SQL 직접 패치는 감사를 우회하므로, 감사 줄을 함께 남기는 스크립트로만 실행한다.

**표준과의 관계**

- 컬럼 이름은 우리 것을 유지한다. 비고의 표준은 나중에 로그를 내보낼 때의 변환 기준이다.
- OpenTelemetry GenAI 시맨틱 컨벤션은 Development 상태라 이름이 바뀔 수 있다. 도구 인자와 결과(`gen_ai.tool.call.arguments`, `result`)는 Opt-In(기본 꺼짐)이다.
- MCP 사양은 로그에 자격증명과 개인정보를 넣지 말라고 한다.
- OCSF `API Activity [6003]`는 필수 항목이 많아 알파에는 과하다.
- 조사하지 않은 것: A2A 사양, ECS. W3C Trace Context와 JWT 클레임 설명은 원문을 열어 확인하지 않았다.

**사용 시나리오**

1. 추적: 특정 대상의 줄을 시간순으로 보고 누가, 언제, 어떤 앱으로 무엇을 바꿨는지 되짚는다.
2. 분석: 기간 내 `result_status`와 `decision`을 집계해 알파 게이트 지표를 구하고, 자주 수정되는 필드를 찾아 프롬프트나 업무 규칙을 손볼 단서로 삼는다.

**별도 확인 필요 (담당자 확인 대상, 설계 논의 밖)**

관리자 단계 시작 전에 담당자에게 확인할 내용만 적는다.

- 사내 감사 규정: 로그 보존 기간, 조회 권한, 장기 보관 방식
- 보안 정책: VOC 본문을 외부 LLM(Claude Code)에 보내도 되는지, 테스트 데이터에 실제 본문을 써도 되는지

**후속 항목 (검토 완료, 추후 결정)**

아래는 논의를 마쳤고, 필요한 시점에 결정한다. 이 문서의 설계 범위에서는 제외한다.

| 항목 | 정할 시점 |
| --- | --- |
| 활성화 지표 수치, 알파 게이트 임계값 | 관리자 단계 첫 2주 측정 후 |

## 부록 J. 공식 문서 검증 기록 (2026-11-02)
Flue 공식 문서·GitHub·npm, Hono·MCP·A2A·Spring AI 공식 문서로 이 ADR의 주장을 다시 확인했다. 수정이 필요한 항목은 본문에 반영했다.

| 주장 | 결과 | 근거 |
| --- | --- | --- |
| Flue 라우터에는 인증이 없고, Hono 미들웨어를 마운트 앞에 붙여 처리한다 | **확인** | Routing 가이드. `app.use('/agents/x/*', ...)` 후 `app.route(...)`. 인증과 인가(대화 id 소유권)를 모두 하라고 안내 |
| 대화 id는 호출자가 정하고, 서버가 발급하거나 사용자에서 유도하는 편이 안전하다 | **확인** | 같은 가이드 |
| Hono에서 IdP JWT를 JWKS로 검증한다 | **확인, 방법 보정** | `hono/jwt`는 정적 `secret` 방식이다. JWKS는 `hono/jwk`(`jwks_uri`, `alg` 허용 목록, `verification.iss/aud`)를 쓴다. 검증된 클레임은 `c.get('jwtPayload')` |
| Flue는 MCP **클라이언트**만 제공하고 MCP 서버·A2A 입구는 없다 | **확인** | MCP 가이드, README, 마이그레이션 가이드 어디에도 서버·A2A 언급 없음 |
| `useMcpConnection`의 `auth`를 함수로 주면 요청마다 토큰을 주입한다 | **확인** | "resolved on every request". 단 "Flue never stores or manages your tokens"라 토큰 저장은 앱이 맡는다 |
| 요청 헤더가 에이전트까지 전달되는가 | **부분 확인(Cloudflare만)** | Cloudflare 문서: 접수 후 원래 헤더·쿠키·본문을 보존하지 않는다. "접수 전에 인증하고, 필요한 비밀이 아닌 상관 정보는 앱 입력이나 저장소로 넘겨라". Node 문서에는 언급이 없다. 에이전트 안에서 호출자 신원을 읽는 API도 문서에 없고, 에이전트가 받는 것은 `{ id }`다 |
| Flue 메시지가 AI SDK v5 UIMessage와 호환된다 | **수정** | 현재 React 가이드는 Flue 고유 타입(`text`, `reasoning`, `dynamic-tool`, `file`)이라고 한다. 호환 주장은 2차 자료(DeepWiki) 기반이었다. 변환 어댑터를 더 많이 써야 할 수 있다 |
| `@flue/react`로 Bearer 토큰을 보낸다 | **확인** | `createFlueClient({ url, token })`을 만들어 `useFlueAgent({ client })`에 전달 |
| Flue는 실험 단계이고 라이선스가 불명확하다 | **수정** | 라이선스는 Apache-2.0(GitHub API, npm, README 일치). 현재 npm 버전은 2.3.0이며 README에 실험 단계 경고는 보이지 않는다. 다만 2.0이 "breaking version upgrade"였고 pre-1.0 영속 스키마는 마이그레이션 없이 초기화만 가능했다. 버전 고정은 그대로 필요하다 |
| MCP elicitation으로 폼과 같은 JSON Schema를 쓴다 | **수정** | 사양(2025-11-25)상 form 모드 스키마는 "평면 객체 + 원시 타입(문자열·숫자·불리언·enum)"만 허용한다. 중첩 객체와 객체 배열은 의도적으로 제외된다. RJSF 스키마를 그대로 쓸 수 없다 |
| 사용자 토큰을 그대로 백엔드까지 넘긴다 | **위험 발견** | MCP 인가 문서는 토큰의 `aud`를 서버 자신으로 제한하고 token passthrough를 금지한다. 이 ADR은 `aud`를 에이전트 전용으로 두면서 같은 토큰을 백엔드에 넘기는 모순이 있다. 토큰 교환(RFC 8693)으로 백엔드용 토큰을 새로 받는 쪽이 맞다 |
| Spring AI로 백엔드 MCP 서버를 만든다 | **확인(조건부)** | WebMVC 전용, Streamable HTTP, JWT 전용(불투명 토큰 불가). OAuth2 보안은 커뮤니티 모듈(`org.springaicommunity:mcp-server-security`)이고 Spring AI가 공식 보증하지 않는다. 오디언스 검증 `validateAudienceClaim`의 기본값이 `false`라 켜야 한다 |
| A2A 입구를 Hono(`app.ts`)에 올린다 | **난이도 상향** | 공식 JS SDK `@a2a-js/sdk`(1.x, A2A 1.0.0 구현)는 Express 어댑터 기반이고 Hono 어댑터는 문서에 없다. MCP는 `@modelcontextprotocol/hono`(2.x) 어댑터가 있다 |
| A2A '입력 필요' 상태와 인증 | **확인, 용어 보정** | 1.0 사양의 상태 이름은 `TASK_STATE_INPUT_REQUIRED`, `TASK_STATE_AUTH_REQUIRED`다. 같은 `taskId`·`contextId`로 새 메시지를 보내 이어간다. 카드의 `securitySchemes`로 OAuth 2.0·OIDC·mTLS 등을 선언하고, 인증이 필요한 확장 카드(extended agent card)도 지원한다 |

부록 K의 링크도 점검했다. 404였던 3건은 교체·삭제했고, 봇 차단(403)·요청 제한(429)으로 확인하지 못한 링크는 부록 K 끝에 따로 적었다.

**링크 점검 (2026-11-02)**

- 200 응답을 확인한 링크가 대부분이다. 단, 응답 코드는 페이지 내용의 정확성을 보장하지 않는다.

- 404여서 교체·삭제한 링크: assistant-ui 구 경로(교체), Backstage ScaffolderRJSFFormProps(Software Templates로 교체), SourcePulse(삭제).
