# 데이터 분석 시스템, 한 칸씩 더해 가며 만들기 (5분 판)

*처음부터 크게 짓지도, 나중에 버리지도 않는 방법*

> 10분 판: [transform-layer-medium.md](transform-layer-medium.md) · 원문: [transform-layer-article.md](transform-layer-article.md)

---

데이터가 적을 때는 DB에 쿼리 하나면 됩니다. 하지만 데이터가 서버 디스크를 압박하고, 만드는 사람과 운영하는 사람이 나뉘면 저장소, 수집 도구, 스케줄러, 운영자 화면이 필요해집니다.

처음부터 크게 지으면 쓰지 않는 서비스에 비용이 들고, 편한 도구로 시작했다가 버리면 같은 일을 두 번 합니다. 그래서 답은 하나입니다. **레이어는 요구가 생길 때 하나씩 더하고, 도구는 최종 구성에서도 쓰일 것으로 고른다.**

## 샘플 시스템과 규칙

개발 조직이 쓰는 플랫폼입니다. 로그가 주 4.2억 건(피크 시간당 530만 건) 쌓이고, 코드 리뷰 시스템·코드 호스팅 서버·사용자 DB(약 5만 건)에 데이터가 흩어져 있습니다. 코드를 쓰지 않는 운영자가 웹 화면으로 운영합니다.

데이터는 메달리온 구조로 쌓습니다. **브론즈**(원본 그대로), **실버**(정리된 데이터), **골드**(바로 보여 줄 집계)입니다.

고르는 규칙은 넷입니다.

1. 레이어는 요구가 생겼을 때만 더한다.
2. 도구는 최종 구성에서도 쓰일 것을 고른다.
3. 검증된 도구가 있으면 직접 만들지 않는다.
4. 확인하지 못한 것은 확정하지 않는다.

## 1단계 · 수집

**저장소는 S3.** 디스크를 늘리면 흩어진 문제가 남고, DB는 쌓이기만 하는 로그에 비쌉니다. 원본은 권한으로 지킵니다. 브론즈 경로는 수집 도구만, 항상 새 파일로 씁니다.

로그는 이미 있는 수집기의 목적지만 S3로 바꾸고, 나머지는 **Airbyte**가 가져옵니다. 운영자가 코드 없이 소스와 일정을 다룰 수 있기 때문입니다. 사용자 이력은 지금부터 쌓습니다. 쌓기 전의 과거는 다시 만들 수 없으니까요.

## 2단계 · 변환

휴면 대상 찾기, 집계, 이력, 부서별 격리는 모두 SQL로 충분합니다. 엔진은 서버 없이 Java 앱 안에서 도는 **DuckDB**입니다. 운영자가 PR로 SQL을 고치게 되면 **dbt**로 옮깁니다.

실행 도구는 요구에 맞춥니다. 보고 다시 돌리기만 하면 내장 스케줄러, 화면에서 설정까지 바꿔야 하면 **Kestra**, 사람별 권한까지 필요하면 Airflow입니다. 샘플 시스템은 Kestra를 고릅니다.

로그는 30분마다 돌리고, 정각 5분 실행이 지난 한 시간을 최종 결과로 다시 계산합니다. **휴면 판정은 최종 결과만 읽습니다.** 빠진 기록으로 메일을 보내면 되돌릴 수 없으니까요.

## 3단계 · 분석 조회

바깥 시스템이 집계를 읽어 가야 할 때입니다. 예를 들어 바깥 작업이 쿼터 변화를 읽어 직접 보정합니다. 골드는 작으니 **PostgreSQL**에 두고, 바깥 시스템마다 읽기 전용 계정과 뷰를 줍니다. API를 따로 만들 필요가 없습니다.

## 4단계 · 내보내기

메일은 한 번 나가면 끝입니다. 그래서 SQL이 대상을 골라 PostgreSQL **대기 표**에 넣고, **Spring Batch** 워커가 한 건씩 보냅니다. 잠금은 `FOR UPDATE SKIP LOCKED`, 중복은 고유 제약과 요청 ID가 막습니다. 대상 수가 기준을 넘으면 멈추고 운영자가 승인합니다.

3단계와 4단계는 서로 독립이라 필요한 쪽만 해도 됩니다.

## 확장과 최종 구성

데이터 자체를 서비스로 내놓을 때만 **Trino**(사람이 직접 SQL로 조회)와 **Iceberg**(S3 표를 여럿이 읽거나 행을 고칠 때)를 더합니다. 권한은 그때도 저장소에서 주고, 골드는 PostgreSQL 한 곳에 둡니다.

다 갖춘 뒤에는 **새 분석은 SQL 추가로, 새 소스는 커넥터 추가로** 받습니다. 컴포넌트는 단계마다 정해 둔 교체 조건이 실제로 왔을 때만 바뀝니다. 조건별 대안은 10분 판과 원문에 있습니다.
