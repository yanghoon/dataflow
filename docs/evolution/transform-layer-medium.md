# 데이터 분석 시스템, 한 칸씩 더해 가며 만들기

*처음부터 크게 짓지도, 나중에 버리지도 않는 방법*

> 원문: [transform-layer-article.md](transform-layer-article.md) · 근거: [transform-layer.md](transform-layer.md)

---

서비스를 운영하다 보면 데이터로 답해야 하는 질문이 생깁니다.

사용자는 얼마나 늘고 있을까? 오래 쓰지 않은 계정은 누구이고, 언제 정리해야 할까? 각 부서는 자기 데이터만 보고 있을까?

데이터가 적고 개발자가 직접 운영한다면 DB에 쿼리 하나면 충분합니다. 하지만 데이터가 서버 디스크를 압박할 만큼 늘고, 만드는 사람과 운영하는 사람이 나뉘면 이야기가 달라집니다. 저장소, 수집 도구, 스케줄러, 운영자 화면이 필요해지죠.

여기서 두 가지 함정이 있습니다.

- **처음부터 크게 지으면** 쓰지 않는 서비스를 운영하느라 비용이 듭니다.
- **지금 편한 도구로 시작했다가 버리면** 같은 일을 두 번 합니다.

그래서 이 글의 답은 하나입니다. **레이어는 요구가 생길 때 하나씩 더하고, 도구는 최종 구성에서도 쓰일 것으로 고른다.**

샘플 시스템 하나를 따라가며 단계마다 무엇을 왜 골랐는지, 어떤 상황에서 다른 길로 가는지 살펴보겠습니다.

## 먼저, 두 가지 지도

**메달리온 구조**는 데이터를 세 층으로 쌓습니다.

- **브론즈** — 받은 원본 그대로. 가공 규칙이 틀렸을 때 다시 만들 수 있어야 하니까요.
- **실버** — 합치고 거르고 정리한 데이터. 업무 규칙은 여기서부터.
- **골드** — 바로 보여 줄 수 있게 집계한 데이터.

**모던 데이터 아키텍처**는 데이터가 흐르는 길을 레이어로 나눕니다. 수집 → 저장 → 변환 → 사용. 사용은 다시 둘로 갈립니다. 결과를 *읽기만* 하는 **분석 조회**와, 메일 발송처럼 *되돌릴 수 없는 행동*을 하는 **내보내기(Reverse ETL)**입니다. 그리고 모든 레이어에 걸치는 **오케스트레이션**(언제, 어떤 순서로 돌릴지)과 **거버넌스**(누가 무엇을 볼 수 있는지)가 있습니다.

이 글의 단계는 이 레이어를 하나씩 채워 가는 과정입니다.

## 샘플 시스템

개발 조직이 쓰는 플랫폼입니다.

- **로그**: 주 4.2억 건, 피크 시간당 530만 건. 서버마다 로그 수집기가 이미 깔려 있습니다.
- **코드 리뷰 시스템**: API로 레코드를 줍니다.
- **코드 호스팅 서버**: 사용자 목록을 CSV로 줍니다.
- **사용자 DB**: PostgreSQL, 약 5만 건.

개발자가 파이프라인을 만들고, **코드를 쓰지 않는 운영자**가 웹 화면으로 설정하고, 상태를 보고, 다시 돌립니다.

해야 할 일은 이렇습니다. 흩어진 데이터를 모으고, 원본을 보관하고, 사용자 이력을 쌓고, 휴면 사용자를 찾고, 바깥 시스템이 집계를 읽게 하고, 안내 메일을 보낸 뒤 유예가 지나면 처리하고, 부서별로 접근을 나눕니다.

## 네 가지 선택 규칙

모든 단계에서 같은 기준으로 고릅니다.

1. **레이어는 요구가 생겼을 때만 더한다.**
2. **도구는 최종 구성에서도 쓰일 것을 고른다.** 지금 규모에 과하면 차선을 고르되, 바꿀 조건을 적어 두고 SQL과 데이터는 남게 한다.
3. **검증된 도구가 있으면 직접 만들지 않는다.**
4. **확인하지 못한 것은 확정하지 않는다.**

---

## 1단계 · 수집: 데이터를 모은다

데이터가 흩어져 함께 볼 수 없고, 서버 디스크로는 감당이 안 될 때 필요합니다.

**저장소는 S3입니다.** 디스크를 늘리면 흩어진 문제가 남고, DB에 넣으면 쌓이기만 하는 로그에 비싼 기능 값을 냅니다. S3는 둘 다 풀고, 밀어 넣는 길(push)과 가져오는 길(pull)을 모두 받으며, 뒤에 나올 DuckDB·Trino·Iceberg가 모두 바로 읽습니다.

다만 S3도 덮어쓰고 지울 수 있습니다. 그래서 브론즈 경로는 수집 도구만 쓰고, 항상 새 파일로 쓰게 권한으로 막습니다.

**수집 도구는 둘로 나눕니다.** 로그는 이미 있는 수집기의 목적지만 S3로 바꿉니다. 나머지는 **Airbyte**가 가져옵니다.

- 흔한 소스는 오픈소스 커넥터, 없는 소스는 Connector Builder나 CDK로 만듭니다.
- 운영자가 웹 화면에서 소스, 일정, 재실행을 직접 다룹니다.
- 레코드마다 추적 정보를 자동으로 붙입니다.

Airbyte는 이 글에서 가장 무거운 도구입니다. 그래도 운영자가 코드 없이 수집을 운영해야 하니 고릅니다.

**파일 형식은 소스마다 다르게 둡니다.** 하나로 맞추려면 변환을 거쳐야 하고, 변환하면 원본이 아니니까요.

**사용자 이력은 지금부터 쌓습니다.** 5만 건이라 주기마다 통째로 받아도 부담이 작고, 쌓기 전의 과거는 다시 만들 수 없습니다.

> **🔀 다른 길로 가는 때**
> - 소스가 더 늘지 않고, 화면 설정이 필요 없고, Airbyte 운영 부담이 한도를 넘으면 → Kestra 수집 작업이나 dlt. 세 조건이 모두 맞아야 합니다.
> - 주기 사이의 변경·삭제 시점까지 알아야 하면 → 변경분만 받기(CDC).

---

## 2단계 · 변환: 데이터를 가공한다

원본에 업무 규칙을 적용해야 할 때입니다. 작은 로그 파일을 시간 단위로 합치고, 휴면 대상을 찾고, 바깥에 줄 집계를 만들고, 사용자 이력을 쌓고, 부서별로 로그를 걸러 부서 경로에 복사합니다.

**로직은 SQL, 엔진은 DuckDB.** 전부 합치고 거르고 세는 일이라 SQL이면 됩니다. DuckDB는 서버 없이 Java 앱 안에서 돌고, S3의 압축 JSONL을 바로 읽고, 나중에 dbt와 Iceberg로 이어집니다.

SQL이 많아지거나 운영자가 PR로 SQL을 고치게 되면 **dbt**로 옮깁니다. 실행 순서와 결과 시험을 맡아 줘서, 개발자가 아닌 사람이 SQL을 고칠 때 안전장치가 됩니다. Kestra도 Airflow도 dbt를 잘 받아 줍니다. 대신 변환이 Java 앱을 떠나 dbt 컨테이너에서 돌게 됩니다.

**실행 도구는 요구에 따라 고릅니다.**

- 보고 다시 돌리기만 하면 된다 → 앱 안의 **내장 스케줄러**
- 작업 순서, 구간 재실행, 화면에서 설정 바꾸기가 필요하다 → **Kestra + oauth2-proxy**
- 사람별 권한과 변경 기록까지 필요하다 → **Airflow**

샘플 시스템은 운영자가 휴면 기준일이나 유예 기간을 화면에서 바꿔야 하므로 Kestra를 고릅니다.

**규모가 커지면** 사양을 먼저 올리고, 그래도 부족하면 같은 SQL을 범위만 나눠 Kestra로 동시에 돌린 뒤 SQL 한 단계로 합칩니다. 나누고 합치는 코드를 따로 짜지 않습니다.

**로그는 30분마다 돌립니다.** 수집기가 밀어 넣는 로그는 한 시간 분량이 다 왔는지 알 수 없습니다. 그래서 :35에는 임시 결과를 만들고, :05에는 지난 한 시간을 처음부터 다시 계산해 최종 결과로 덮어씁니다. **휴면 판정은 최종 결과만 읽습니다.** 빠진 기록 때문에 멀쩡한 사용자에게 메일이 나가면 되돌릴 수 없으니까요.

> **🔀 다른 길로 가는 때**
> - 피크 한 시간 분량이 15분을 넘으면 → 사양 올리기 → 나눠 돌리기 → 분산 엔진, 이 순서로.
> - 부서가 파일 대신 조회로 받기를 원하면 → 조회할 때 권한으로 거르기.
> - 결과를 15분 안팎으로 빨리 봐야 하면 → 새 파일만 이어 붙이는 방식.

## 3단계 · 분석 조회: 바깥 시스템이 읽게 한다

바깥 시스템이 집계 결과를 읽어 자기 기능에 써야 할 때입니다. 예를 들어 활동 로그에서 쿼터에 영향을 주는 변화를 골드로 만들면, 바깥의 별도 작업이 그걸 읽어 쿼터를 직접 보정합니다. 읽은 결과로 무엇을 할지는 바깥 시스템이 정합니다.

**골드는 PostgreSQL에 둡니다.** 골드는 작고, 실버에서 언제든 다시 만들 수 있고, 트랜잭션으로 한 번에 바꿔 옛 값과 새 값이 섞이지 않습니다. 이미 있는 DB라 서비스도 늘지 않습니다.

**권한도 PostgreSQL이 겁니다.** 바깥 시스템마다 읽기 전용 계정을 주고, 정해진 뷰만 읽게 합니다. 뷰가 바깥 시스템과의 약속입니다. 읽기 API를 따로 만들 필요가 없습니다.

> **🔀 다른 길로 가는 때**
> - 골드가 PostgreSQL에 담기 어려울 만큼 커지면 → S3나 Trino.
> - 읽는 쪽이 많아지거나 믿기 어려운 상대에게 열어야 하면 → 읽기 API.

---

## 4단계 · 내보내기: 결과로 행동한다

휴면 대상에게 안내 메일을 보내고, 유예 뒤에도 쓰지 않으면 처리해야 할 때입니다. 3단계와는 서로 독립이라 필요한 쪽만 해도 됩니다.

변환은 틀리면 다시 돌리면 됩니다. **메일은 한 번 나가면 끝입니다.** 그래서 일을 둘로 나눕니다. 누구에게 보낼지는 SQL이 골라 PostgreSQL의 **대기 표**에 넣고, 실제 발송은 워커가 한 건씩 꺼내 보냅니다.

대기 표가 큐를 직접 만드는 것처럼 보이지만, 직접 만드는 건 상태 열 하나뿐입니다. 행 잠금은 `FOR UPDATE SKIP LOCKED`가, 중복 방지는 고유 제약이, 재시도와 재시작은 **Spring Batch**가 맡습니다. 상태가 복잡해지면 PGMQ, PgQ, Namastack Outbox 같은 검증된 큐 도구를 검토합니다.

유예 뒤 처리도 같은 길입니다. "안내한 지 유예 기간이 지났고 그 뒤 활동이 없는 사용자"를 SQL로 골라 같은 표에 넣으면 됩니다. 유예는 SQL 조건일 뿐이죠.

안전장치도 둡니다.

- 요청 ID를 API에 함께 보내 중복 발송을 막습니다.
- 대상 수가 기준을 넘으면 Kestra가 멈추고, 운영자가 승인해야 이어 갑니다. SQL 실수로 전원에게 메일이 나가는 걸 막기 위해서입니다.
- 보내기 직전에 대상이 여전히 조건에 맞는지 다시 봅니다.

워커는 2단계 Java 앱 안에 넣습니다. Spring Batch는 서버가 아니라 라이브러리니까요.

> **🔀 다른 길로 가는 때**
> - 도착 즉시 반응하거나 여러 곳이 같은 결과를 받아야 하면 → Kafka 같은 메시지 큐.
> - 발송이 변환과 메모리를 다투면 → 워커를 별도 앱으로.

## 데이터 플랫폼으로 확장

여기까지가 시스템의 기능입니다. 데이터 자체를 서비스로 내놓아야 할 때만 두 가지를 더합니다.

**Trino** — 플랫폼 안에서 사람이 직접 SQL로 조회해야 할 때. Trino에도 권한 기능이 있지만, 권한은 계속 저장소(S3 경로, PostgreSQL 계정)에서 줍니다. 한곳에서만 관리하기 위해서입니다.

**Iceberg** — 사용자가 S3의 표를 직접 읽거나 실버의 행을 고쳐야 할 때. 다시 쓰는 도중에 반쪽짜리 결과를 읽는 일을 막아 줍니다. 골드는 PostgreSQL 한 곳에 그대로 두고 Trino가 커넥터로 읽습니다. 두 곳에 두면 언젠가 값이 어긋나니까요.

---

## 최종 구성

결국 들어오는 컴포넌트는 이렇습니다. S3와 PostgreSQL은 처음부터 있던 것입니다.

- **Airbyte** — 1단계
- **배치 앱(DuckDB SQL)**, 운영자가 PR로 SQL을 고치게 되면 **dbt** — 2단계
- **Kestra**(권한·변경 기록이 필요하면 Airflow) — 2단계
- **Spring Batch 워커** — 4단계
- **Trino, Iceberg 카탈로그** — 확장

요구에 따라 이 중 일부만 들어올 수도 있습니다. 다 갖춘 뒤에는 **새 분석은 SQL 추가로, 새 소스는 커넥터 추가로** 받습니다. 컴포넌트가 바뀌는 건 위의 "다른 길로 가는 때"가 실제로 왔을 때뿐입니다.

## 아직 확인하지 않은 것

규칙 4에 따라, 확인 전까지 확정하지 않는 항목이 있습니다. DuckDB가 피크 한 시간을 15분 안에 처리하는지, 사내 S3의 경로 권한, Kestra 오픈소스판의 기능, DuckDB가 PostgreSQL에 바로 쓸 수 있는지, 메일 API의 중복 방지, DuckDB와 Trino가 같은 Iceberg 카탈로그를 함께 쓸 수 있는지 등입니다.

---

이 글은 샘플 시스템을 통해 비슷한 규모와 요구를 가진 시스템에 도입 방향과 단계별 대안을 제시하는 것이며, 실제 업무를 빠짐없이 분석한 것이 아니므로 위 항목의 확인 시점과 방법은 적용하는 시스템에서 정해야 합니다.
