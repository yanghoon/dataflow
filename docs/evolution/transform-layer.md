# 트랜스폼 레이어 진화 논증

형식: 사실·원칙·가정을 전제로 두고, 결론은 전제 ID로만 도출한다. 전제가 바뀌면 그 ID를 인용한 결론만 다시 검토한다.

- **F 사실**: 확인됨. 검토 대상 아님.
- **P 원칙**: 사용자 가치 판단. 바꾸려면 사용자가 결정.
- **A 가정**: 미확인. 검증 방법을 붙인다. 깨지면 의존 결론 무효.
- **V 검증**: 조사로 확인한 외부 사실. 출처를 붙인다.
- **C 결론**: `← 근거 ID`. 근거 없는 결론 금지.
- **T 전환 규칙**: `조건 → 변화 ← 근거 ID`. 조건은 관측 가능해야 한다.
- **Q 미결**: 결정 대기.

이 문서는 [transform-layer-article.md](transform-layer-article.md)의 근거 문서다. 절 순서와 단계 이름은 아티클을 따른다(1단계 수집, 2단계 변환, 3단계 분석 조회, 4단계 내보내기, 데이터 플랫폼 확장, 최종 구성). 이전 Phase 번호와의 대응은 §7 표에 있다. 대체·철회된 판단은 §15에 기록한다.

## 1. 사실

- **F1** 브론즈 메인 스토리지는 S3다. 목적은 데이터 증가 수용과 워크로드 디스크 압력 제거다.
- **F2** 수집은 push(Vector → S3)와 pull(Airbyte) 두 경로다.
- **F3** Vector 산출물은 `jsonl.gz` 파편이다. 주 4.2억 건, 피크 시간당 530만 건.
- **F4** Airbyte OSS에는 레코드 필터가 없고, S3 목적지는 파일 크기를 제어할 수 없다.
- **F5** 개발은 L3, 구성·운영·분석은 L2다. 서로 다른 사람이다.
- **F6** 현재 유즈케이스: 부서별 접근 격리 필터, 휴면 식별, 휴면 사전 안내 메일, 휴면 처리.
- **F7** 휴면은 식별 → 안내 → 유예 → 처리 순서이며 단계 사이에 시간 간격이 있다.
- **F8** 소스 원형이 다르다. Vector는 중첩 JSON 로그, Gerrit은 JSON 레코드, GHES는 CSV 파일, PG는 타입 있는 행이다.
- **F9** GHES `active_users.csv`는 Connector Builder 매니페스트(HTTP)로 수집하며, CSV를 파싱한 레코드로 내보낸다.
- **F10** 쿼터 보정: 활동 로그에서 쿼터에 영향을 주는 변화를 감지하고, 이 시스템 밖의 별도 워크로드가 그 결과를 읽어 쿼터를 직접 보정한다. ← 사용자 제공(2026-11-07)

## 2. 원칙

- **P1** 모든 데이터 경로는 Source → Tool → Logic → Sink 패턴으로 기술한다.
- **P2** 확장 방식은 패턴 요소 하나가 바뀔 때 결정한다.
- **P3** 운영(L2)은 웹 GUI로 구성·모니터링·재실행한다.
- **P4** 모던 데이터 아키텍처(메달리온, 레이크하우스)를 따른다.
- **P5** 브론즈는 원본 페이로드를 변경하지 않고 전량 보존한다. 메타데이터는 원본 옆에 추가할 수 있다.
- **P6** 기존 수단으로 요구를 충족할 수 없을 때에만 인프라를 추가한다.
- **P7** 브론즈 Sink는 사람이 읽을 수 있는 형식(JSONL, CSV)을 우선한다. Parquet·Avro는 가능하나 우선순위를 낮춘다.
- **P8** pull 수집은 단일 도구로 한다. 소스가 늘어도 도구를 늘리지 않는다. Vector push는 별도 경로다(F2).
- **P9** 중복 투자를 피한다. 각 단계에서 만드는 자원(SQL, 이미지, 실행 명령)은 최종 구성에서도 쓰이게 만든다.
- **P10** 필요가 실제로 생긴 시점에 문서화되고 검증된 도구를 도입하고, 직접 구현하지 않는다. 나중에 버릴 임시 구현도 만들지 않는다. 기술 완성도가 유지보수성과 개발 리소스를 줄인다. 필요가 없으면 도입하지 않는다(P6). ← 사용자 결정(2026-11-04)

## 3. 가정

- **A1** 메일 API는 요청 ID로 중복을 막는다. 깨지면 중복 발송을 허용한다. 검증: API 문서.
- **A2** DuckDB 컨테이너 하나(최소 2코어 4GB)가 피크 시간 윈도우(530만 건)를 15분 안에 처리한다. 필요 속도는 초당 약 5,900건이고, 공개 사례의 가장 느린 값(초당 약 4.6만 건, 사양 불명)보다 낮다. 15분은 피크 시간 기준으로 임의 지정한 상한이며, 뒤 단계(휴면 판정, 조회)가 결과를 기다릴 수 있는 한도라는 뜻이다. 조건에 따라 바뀔 수 있다(사용자 결정, 2026-11-07). scale up 상한은 4코어 8GB, scale out은 허용한다. 검증: 피크 시간 실측.
- **A3** 온프레미스 S3가 경로 단위 접근 정책을 지원한다. 검증: 스토리지 문서·테스트.
- **A4** 이벤트 구동 요구(즉시 반응, 다중 소비자)는 현재 없다.
- **A5** Airbyte CDC가 `before`·`op`를 보존한다. 검증: 실제 출력 확인. 펴서 합쳐지면 이력이 손실된다.
- **A6** 브론즈를 읽는 트랜스폼 엔진(DuckDB 등)이 여러 포맷을 읽을 수 있다.
- **A7** L2는 스킬업 후 GitOps(PR)로 Logic(SQL)을 수정한다. 그 전에는 L3가 수정한다. 검증: 스킬업 완료 시점의 L2 PR 실적.
- **A8** PG 사용자 테이블은 약 5만 건이다(예상). 검증: 실제 행 수.
- **A9** (내장 스케줄러를 고른 경우) 내장 스케줄러 화면이 날짜 인자 재실행과 실행 이력 확인을 제공한다. 검증: 작은 잡으로 시험(Q9). 깨지면 T9.
- **A10** (내장 스케줄러를 고른 경우) 서버 재기동 시 놓친 실행을 보충하거나, 보충하지 않아도 업무 영향이 없다. 검증: 재기동 시험(Q9).
- **A11** 골드 집계 표는 PG에 담을 수 있을 만큼 작다. 검증: 집계 정의 후 행 수 추정. 깨지면 골드를 Iceberg로 옮긴다(C58).
- **A12** 로그 수집기의 전송 지연은 5분 이내다. 깨지면 대기 시간을 늘리거나 운영자가 해당 시간을 다시 돌린다(C51). 검증: 수집기 설정과 관측(Q32).
- **A13** Kestra OSS가 설정 저장소, 실행 입력(표 형태 값 포함), 병렬 실행, 실행 멈춤(Pause), Airbyte 연동을 제공하고 oauth2-proxy 뒤에서 동작한다. 깨지면 실행 도구 선택(C47)을 다시 본다. 검증: 시험(Q29, Q30).

## 4. 검증된 외부 사실

- **V1** Databricks는 브론즈 적재 시 `_metadata`를 포함하고 최소 `file_path`, `file_modification_time`을 남기라고 권한다. 소스 파일 추적과 불량 데이터 재적재가 이유다. [Auto Loader best practices](https://learn.microsoft.com/azure/databricks/ingestion/cloud-object-storage/auto-loader/best-practices)
- **V2** `file_modification_time`은 적재 시각이 아니다. 적재 시각은 직접 넣는다. (일반 관행, 문서에 명시 없음)
- **V3** Airbyte S3 목적지는 `_airbyte_raw_id`, `_airbyte_extracted_at`(epoch ms), `_airbyte_meta`(sync_id 등), `_airbyte_generation_id`를 자동으로 붙인다. [S3 Migration Guide](https://docs.airbyte.com/integrations/destinations/s3-migrations), [metadata fields](https://docs.airbyte.com/understanding-airbyte/airbyte-metadata-fields)
- **V4** Airbyte "Copy raw files"는 파일을 파싱하지 않고 바이트를 그대로 S3로 복사하며 파일 메타를 함께 전달한다. 파일 기반 소스(S3, SFTP Bulk, SharePoint 등)에서만 가능하다. HTTP 소스 지원은 확인하지 못했다. 파일당 상한은 문서에 1GB와 1.5GB가 혼재한다. [Delivery methods](https://docs.airbyte.com/using-airbyte/delivery-methods)
- **V5** 브론즈 일반 관행: 원본은 변경하지 않고 계보 필드를 옆에 추가한다. 출처는 벤더 블로그이며 표준이 아니다. [Conduktor](https://www.conduktor.io/glossary/data-lake-zones-bronze-silver-gold-architecture)
- **V6** Debezium CDC 이벤트는 `before`, `after`, `op`, `source`, `ts_ms`를 가진 봉투다. 펴서 합치면 `before`와 `op`를 잃는다. 브론즈 적용은 추론이다. [Red Hat Debezium guide](https://docs.redhat.com/en/documentation/red_hat_integration/2020-q2/html/getting_started_with_debezium/viewing-change-events)
- **V7** DuckDB는 `read_ndjson`으로 읽고 `.gz`를 확장자로 자동 해제한다. `union_by_name`으로 스키마가 다른 파일을 합친다. `filename` 가상 컬럼은 v1.3.0부터다. [Loading JSON](https://duckdb.org/docs/stable/data/json/loading_json)
- **V8** Trino Hive 커넥터는 JSON SerDe를 지원한다. 압축 코덱 설정은 쓰기용이다. gzip JSONL 읽기와 `json_parse` 방식은 확인하지 못했다. [Hive connector](https://trino.io/docs/current/connector/hive)
- **V9** Dagster는 `dagster-airbyte`로 Airbyte OSS connection을 자산으로 불러와 sync를 실행한다. Airflow는 `AirbyteTriggerSyncOperator`로 connection ID의 sync를 호출하며, 재실행하면 sync가 다시 시작되어 여러 번 실행해도 결과가 같다는 보장이 없다. [Dagster & Airbyte OSS](https://docs.dagster.io/integrations/libraries/airbyte/airbyte-oss), [Airflow Airbyte operator](https://airflow.apache.org/docs/apache-airflow-providers-airbyte/stable/operators/airbyte.html)
- **V10** Dagster OSS는 계속 켜 두는 서비스로 웹서버, 데몬, 코드 로케이션이 필요하고 예제 구성에 Postgres가 있다. 기본 OSS에 사용자 인증이 없다는 설명은 제3자 템플릿 문서다. Airflow 3는 메타DB, API 서버, 스케줄러, DAG 프로세서가 필요하고 triggerer는 선택이다. [Dagster 배포](https://docs.dagster.io/deployment/overview), [Airflow 구조](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/overview.html)
- **V11** Dagster는 `dagster-dbt` + `dbt-duckdb`로 dbt 모델을 자산으로 읽는다(컴포넌트 방식은 프리뷰). Airflow의 Cosmos는 dbt 모델을 태스크로 바꾸며 dbt-duckdb가 선택 어댑터로 나열된다. Cosmos + DuckDB 공식 예제는 확인하지 못했다. [Dagster dbt](https://docs.dagster.io/integrations/dbt), [Astronomer dbt 가이드](https://www.astronomer.io/guides/airflow-dbt)
- **V12** db-scheduler-ui(Bekk)는 db-scheduler 위의 화면으로 예정·실행·실패 작업 조회와 재실행을 제공하고, 이력은 별도 로그 모듈로 켠다. Java 17, Spring Boot 3.3 이상이 필요하다. 파라미터 입력 폼과 날짜별 재실행 지원 여부는 확인하지 못했다. [db-scheduler-ui](https://gh.r-mj.com/bekk/db-scheduler-ui), [db-scheduler](https://www.github.com/kagkarlsson/db-scheduler)
- **V13** JobRunr 오픈소스는 자동 재시도(지수 백오프), 반복 작업, 내장 대시보드를 제공하고, 우선순위 큐·배치 체이닝은 Pro로 알려져 있다. 출처가 제3자 요약이라 공식 비교표 확인이 필요하다. [Quarkus Insights](https://quarkus.io/blog/quarkus-insights-264-jobrunr-failure-handling/), [JobRunr v7](https://www.jobrunr.io/en/blog/2024-04-09-jobrunr-and-jobrunr-pro-v7/)
- **V14** Trino Iceberg 커넥터의 카탈로그 유형은 hive_metastore(기본), glue, jdbc, rest, nessie다. REST 카탈로그는 뷰와 구체화 뷰를 지원하지 않는다. JDBC는 PostgreSQL 외에는 드라이버 jar가 필요하고, Iceberg 변경 시 호환성 문제가 있다는 경고가 있다. 출처는 문서 미러다. [Iceberg connector 미러](https://dell.starburst.io/443-e/connector/iceberg.html)
- **V15** DuckDB Iceberg 확장은 REST 카탈로그를 attach하면 INSERT, UPDATE, DELETE, MERGE INTO를 지원한다. 카탈로그 없이 `iceberg_scan`으로 읽은 테이블에는 쓸 수 없다. 수정·삭제는 merge-on-read(위치 삭제)이고 copy-on-write는 아직 없다. 버전별 문서가 다르다. [DuckDB Iceberg 쓰기](https://duckdb.org/docs/1.5/core_extensions/iceberg/writing_to_iceberg)
  - 재확인(2026-11-07, 2.0 문서): REST 카탈로그를 attach하면 CREATE TABLE(CTAS 포함), INSERT, UPDATE, DELETE, MERGE INTO, ALTER TABLE을 지원한다. 파티션 표의 수정·삭제도 된다. copy-on-write는 지원하지 않고 merge-on-read만 된다. 설정 문서가 있는 카탈로그는 SeaweedFS, AWS Glue, Cloudflare R2, Apache Polaris, Lakekeeper, Amazon S3 Tables, Google BigLake다. 이 중 쓰기 예시가 명시된 것은 SeaweedFS뿐이다. 정비 작업(스냅샷 만료, 파일 병합)은 문서에 없다. [Writing to Iceberg](https://duckdb.org/docs/2.0/core_extensions/iceberg/writing_to_iceberg.html), [Catalogs](https://duckdb.org/docs/2.0/core_extensions/iceberg/catalogs.html)
- **V16** Trino Iceberg 정비 명령: `OPTIMIZE`(작은 파일 병합), `expire_snapshots`, `remove_orphan_files`. 최소 보존 기본값은 7일이다. snapshot 정리를 먼저, 고아 파일 정리를 나중에 하라는 권고는 제3자 자료다. [정비 가이드](https://www.starburst.io/blog/how-table-maintenance-affects-iceberg-snapshots/), [Trino Iceberg](https://trino.io/docs/current/connector/iceberg)
- **V17** Trino OPA 플러그인은 접근 검사, 행 필터(SQL 조건), 열 마스킹을 별도 HTTP 호출로 처리한다. Trino 자체 파일 규칙의 행 필터 지원은 공식 문서로 확인하지 못했다. [Cerbos OPA 행 필터](https://www.cerbos.dev/blog/row-level-security-for-apache-trino)
- **V18** dbt-trino는 MERGE 기반 증분 모델을 만들고 Iceberg는 MERGE를 지원한다. snapshot 지원은 자료가 엇갈린다(구버전 PyPI는 미구현, Starburst 블로그는 지원). [dbt-trino PyPI](https://pypi.org/project/dbt-trino/1.2.1/), [Starburst](https://www.starburst.io/blog/lakehouse-data-pipeline-dbt-trino/etl)
- **V19** Vercel 권한 구조(참고 모델): 팀 층 역할(Owner, Member, Developer, Billing, Viewer, Contributor)과 프로젝트 층 역할(Admin, Developer, Viewer)의 두 층이다. Contributor는 명시적으로 배정된 프로젝트에만 접근한다(기본 거부). 프로젝트 역할은 Contributor에게만 유효하다. 여러 Access Group이나 직접 배정이 겹치면 가장 높은 권한이 적용된다. 프로젝트 역할과 Access Group은 Enterprise 전용이다. [Access roles](https://vercel.com/docs/rbac/access-roles), [Access groups](https://vercel.com/docs/rbac/access-groups)
- **V20** DuckDB Java 클라이언트는 JDBC 드라이버(`org.duckdb:duckdb_jdbc`)로 배포되며 `jdbc:duckdb:`로 프로세스 안에서 메모리 DB를 연다. 설정 기본값은 `memory_limit` = RAM의 80%, `threads` = CPU 코어 수다. JVM 앱 안에서 쓸 때 확장(httpfs, json) 로딩 방식은 이 문서에서 확인하지 못했다. [Java client](https://duckdb.org/docs/2.0/clients/java/overview.html), [Configuration](https://duckdb.org/docs/2.0/configuration/overview.html)
- **V21** 변환 엔진 후보 조사(2026-11-05). ① Spark: 로컬 모드로 앱 안 실행이 가능하나 gzip 파일은 쪼갤 수 없어 파일 하나를 한 작업이 읽는다(AWS 가이드). ② DataFusion: Java 바인딩 0.1.0이 2026-05 첫 출시이고, JSON 읽기 지원이 공지와 이슈에서 엇갈린다. ③ ClickHouse(clickhouse-local): 서버 없는 단일 실행 파일, `s3()` 함수로 JSONEachRow와 gzip을 읽는다는 설명은 제3자 자료다. Java 내장 방식은 확인하지 못했다. ④ Polars: Python·Rust 전용, S3 gzip NDJSON 직접 읽기는 확인하지 못했다. [AWS Glue Spark 튜닝](https://docs.aws.eu/prescriptive-guidance/latest/tuning-aws-glue-for-apache-spark/reduce-data-scan.html), [DataFusion Java 0.1.0](https://datafusion.apache.org/blog/2026/05/26/datafusion-java-0.1.0), [datafusion-java #35](https://github.com/apache/datafusion-java/issues/35), [ClickHouse s3()(제3자)](https://oneuptime.com/blog/post/2026-03-31-clickhouse-s3-table-function/markdown), [Polars cloud storage](https://docs.pola.rs/user-guide/io/cloud-storage)

PyPI의 pgqueue는 PgQ의 Python 경량 구현이며, Java용 "pgqueue" 라이브러리는 찾지 못했다. ③ Namastack Outbox: Spring Boot용 transactional outbox 라이브러리(JDBC, JPA, MongoDB, Apache 2.0). 업무 데이터와 outbox 기록을 같은 트랜잭션에 커밋하고, 키별 순서, 인스턴스 간 분할, 재시도를 제공한다. 관리자 답변에 따르면 1.0.0 이후는 Spring Boot 4만 지원한다. 엄격한 SemVer는 보장하지 않는다고 밝힌다. SQL로 직접 넣을 수 있는지는 확인하지 못했다. [PGMQ](https://github.com/pgmq/pgmq), [PGXN pgmq](https://pgxn.org/dist/pgmq/README.html), [SkyTools 미러](https://github.com/jbaanus/skytools-legacy), [pgqueue PyPI](https://pypi.org/project/pgqueue), [Namastack Outbox](https://github.com/namastack/namastack-outbox), [Boot 버전 답변](https://github.com/orgs/namastack/discussions/110)

## 8. 1단계: 수집

**받을 요구:** R5 데이터 증가 수용, R10 PG 수집, R9 이력 쌓기 시작, R6 L2 운영(Airbyte 화면).

**구성**
- **C20** 1단계 구성: S3 저장소와 Airbyte(자체 스케줄 + GUI) 하나다. Airbyte가 PG, Gerrit(CDK), GHES(Builder)를 S3 브론즈로 수집한다. 로그는 기존 Vector가 보낼 곳만 S3로 바꾼다(F2). 변환·발송은 없다. 사용자 테이블은 full 적재를 누적해 이력 쌓기를 이 단계부터 시작한다(C26). 시작 전 과거는 복구할 수 없기 때문이다. L2는 Airbyte 화면으로 운영한다(R6). 새로 켜 두는 구성 요소는 Airbyte 1개다. ← F2, F5, P3, P8, C7, C26, R6, R9

**결론: 수집 Sink와 포맷**
- **C7** 모든 소스의 브론즈 Sink는 S3다. PG를 브론즈 Sink로 쓰지 않는다. UPDATE가 가능해 P5를 위반하고, F1의 디스크 압력 문제가 재발한다. ← F1, P5
- **C60** 브론즈 원본 보존은 권한 규칙으로 지킨다. 브론즈 경로에는 수집 도구만 쓰고, 쓸 때는 항상 새 파일로 쓴다. S3도 덮어쓰기와 삭제가 가능하므로 저장소에 넣는 것만으로 원본이 지켜지지 않는다. 사내 S3가 버전 관리나 삭제 잠금을 지원하면 더한다(Q33). ← P5, C7
- **C8** 브론즈 포맷은 하나로 통일하지 않는다. 타입 손실(JSONL)과 크기 비효율을 피하고, 읽는 쪽 비용은 작다. 일관성은 포맷이 아니라 패턴(Sink = S3)과 경로·메타 계약에서 지킨다. ← F8, A6, P1
- **C9** "원본"은 소스 유형별로 정의한다. ← F8, P5, V4, V5, V6

| 소스 유형 | 원본 | 메타 위치 |
|---|---|---|
| 로그(Vector) | `jsonl.gz` 바이트 그대로 | 경로, 객체 메타데이터 |
| 파일(GHES CSV) | CSV 바이트가 이상적 | 경로, 사이드카 |
| CDC | 이벤트 전체(`before`, `after`, `op`, `source`) | 이벤트 내부 |
| 레코드 API(Gerrit) | 레코드 | 도구가 붙인 `_airbyte_*` |

- **C10** GHES CSV는 Airbyte 기능 제한으로 레코드(JSONL)로 받고 `_airbyte_*` 메타를 붙인다. 파싱 결과가 원본과 완전히 같지 않으므로 모든 컬럼을 string으로 받는다. 이는 원칙(C9)의 예외이며 수용된 한계다. ← F9, V4, 사용자 결정
- **C11** CDC는 펴지 않고 이벤트 전체를 저장한다. ← V6, A5
- **C12** 레코드 단위 메타는 도구 제공 필드를 쓰고, 도구가 못 넣는 경우만 직접 추가한다. 공통 계약 후보: 소스ID, 적재시각, 실행ID. ← V1, V2, V3
- **C13** Parquet·Avro는 실버 이후로 미룬다. ← P7

**결론: 수집 도구와 이력**
- **C25** Airbyte는 pull 수집의 단일 도구다. 운영자가 코드 없이 연결 정보, 실행 일정, 받을 표를 화면에서 바꾸는 요구(R6)를 수집 경로에서 받는 것은 Airbyte뿐이다. 스케줄러 화면은 설정을 바꾸지 못하고(C53), 2단계의 Kestra도 Airbyte의 연결 설정 화면을 대신하지 못한다(C54). 소스가 늘어도 바꿀 필요가 없어 최종 구성의 도구이기도 하다(K2). 운영 부담은 수용한다. PG 소스의 full·CDC 지원은 미검증(Q14). 대안은 T8. ← P8, P3, F5, R6, C53, C54, K2
- **C26** 사용자 테이블은 full 적재를 누적해 일·시간 스냅샷으로 쓴다. 5만 건이면 full 비용이 작고 삭제는 다음 스냅샷의 부재로 드러난다. `snapshot_date`는 `_airbyte_extracted_at`(V3)에서 얻을 수 있다. 적재 시작 전 과거는 복구할 수 없다. 휴면 판정에는 사용자 테이블 외에 활동 정보(로그)가 필요하다. CDC 전환은 T5. ← R9, R10, A8, V3, T5

**다음으로 가는 조건**
- **T5** 주기 사이의 변경이나 삭제 시점까지 알아야 하면 → Airbyte CDC로 S3에 변경 이벤트를 적재한다. Sink는 S3다. ← C7, A5, Q12
- **T8** 다음 셋이 모두 맞으면 → pull 수집을 Kestra 수집 작업 또는 dlt로 옮긴다. ① 소스가 PG, Gerrit, GHES 외로 늘지 않는다 ② 운영자가 연결 설정을 화면에서 바꿀 필요가 없어진다 ③ Airbyte 월 운영 작업이 Q13의 한도를 넘는다. 직접 구현하지 않는다(K3). 두 대안은 Airbyte와 같은 수준이 아니며 커넥터 폭, 연결 설정 화면, 추적 메타 자동 부착을 잃는다(C54). dlt의 커넥터 수와 화면 기능은 미확인. ← P8, C25, C54, Q13, K3, 사용자 결정(2026-11-07)

**미결**
- **Q4** 공통 메타 계약(소스ID, 적재시각, 실행ID)을 Vector 경로에서 어떻게 붙일지. 원본 바이트 보존(C9)과 충돌하므로 경로·객체 메타로 갈지 결정.
- **Q5** HTTP 소스에서 raw 파일 복사가 가능한지(V4 미확인). 가능하면 C10 예외 해소.
- **Q11** Airbyte S3 목적지가 full 동기화를 덮어쓰지 않고 누적하는지, 시간별 스냅샷 경로 설계. 실제 설정으로 확인한다.
- **Q12** PG 사용자 데이터의 삭제·중간 변경 이력이 필요한가. 필요하면 CDC(T5, A5).
- **Q13** Airbyte 존치 지표: 월별 운영 작업 기록(업그레이드, 장애, 설정 변경)을 지표로 정하고 T8의 한도를 정한다.
- **Q14** Airbyte PG 소스의 full·CDC 지원 확인. S3 접근키처럼 Airbyte와 변환 양쪽에 필요한 시크릿의 중복 관리 방식.
- **Q33** 사내 S3의 버전 관리와 삭제 잠금 지원 여부(C60).

## 9. 2단계: 변환

**받을 요구:** R1 부서별 접근 격리, R2 휴면 식별, R9 이력 분석, R7 유지보수·진화, R6 L2 운영(실행 도구 화면).

**구성**
- **C21** 2단계 구성: 1단계에 배치 앱 1개(단일 인스턴스, DuckDB를 JDBC로 내장)와 실행 도구를 더한다. 실행 도구는 요구에 따라 셋 중 하나다. ① 내장 스케줄러(db-scheduler-ui 또는 JobRunr, 배치 앱 안): 실행을 보고 다시 돌리기만 하면 될 때 ② Kestra OSS + oauth2-proxy: 작업 순서 의존, 시간 구간 재실행, 놓친 실행 채우기, 화면에서 설정 바꾸기 중 하나라도 필요할 때 ③ Airflow: 위에 더해 운영자별 권한이나 설정 변경 기록이 필요할 때. 샘플 시스템은 운영자가 화면에서 설정을 바꿔야 하므로(R6) Kestra를 고른다(C47). 새로 켜 두는 것은 배치 앱, Kestra(PG 사용), oauth2-proxy다. 수집 일정은 Airbyte가 유지한다. ← C2, C16, C47, C48, C49, C53, R6, V12, V13, A13, 부록 D
- **C22** 로직은 SQL 파일로 두고 실행 도구와 분리한다. 날짜·기준일은 인자, 상태는 PG, 일정 정의는 로직 밖이다. 실행 도구를 바꿔도 로직은 그대로다. ← P9, C15

**결론: 로직과 엔진**
- **C1** 병합·필터는 Airbyte가 아닌 트랜스폼 레이어의 Logic이다. ← F4, P4
- **C4** 휴면 단계는 잡 경계를 넘는 의존이지만 PG 상태 컬럼으로도 풀 수 있다. 실행 도구가 필요한 근거는 C2(L2 GUI)다. Airbyte 일정 기능은 sync 전용이고 Vector 경로는 Airbyte 밖이다(F2). ← F7, C2, C3 (철회: 최초 "오케스트레이터 필수" 판단, §15)
- **C14** Logic은 SQL 파일로 Git에 두고 L3가 고친다. dbt 이관은 T7이며 판단 근거는 C57이다. 엔진 교체 시 변환 SQL은 재사용한다. 브론즈를 읽는 문법은 엔진마다 바뀔 수 있다(C33, 확인 전). ← C1, A6, A7, T3, T7, C57
- **C16** SQL 실행은 SQL 파일과 DuckDB로 충분하다. DuckDB는 배치 앱 안에 JDBC 라이브러리로 넣어 실행한다(V20). 로직은 SQL 파일에 있으므로 실행 방식이 바뀌어도 SQL은 그대로다. 기본값(RAM 80%, 코어 수)으로 두면 JVM과 메모리를 다투므로 `memory_limit`과 `threads`를 반드시 정한다. 코드는 R3·R4(HTTP 호출, 상태 갱신)부터 필요하다. 언어는 C23. S3 접근 조합은 미검증(Q8). ← R1, R2, R3, R4, A6, V20, 사용자 결정(2026-11-05)
- **C24** 변환 단계(SQL 실행)에는 Spring Batch가 필요 없다. 앱 안의 DuckDB와 SQL 파일로 충분하다(C16). 4단계 워커는 C36에서 Spring Batch를 쓴다. ← A8, C16, C17, P6
- **C39** 변환 엔진은 DuckDB다. 조건은 넷이다: ① 켜 둘 서버 없음(P6) ② Java 배치 앱에 내장 가능(C21) ③ S3의 gzip JSONL 직접 읽기(F3) ④ 최종 구성 연결(dbt, Iceberg, K2). DuckDB는 넷을 모두 만족한다(V7, V11, V15, V20). Iceberg 쓰기는 REST 카탈로그를 붙이면 가능하며, 수정·삭제는 merge-on-read만 지원한다(V15 재확인). Spark는 조건을 만족하나 이 규모에 의존성이 과하다(P6). DataFusion은 Java 바인딩이 미성숙하고, ClickHouse는 Java 내장과 Iceberg 쓰기가 미확인이며, Polars는 Java에서 쓸 수 없고, Trino는 클러스터가 필요하며, PostgreSQL은 로그를 DB로 옮겨야 한다(C7, V21). gzip 파일은 어느 엔진에서도 쪼개 읽을 수 없으므로 병렬성은 파일 수에서 나온다. DuckDB의 여러 파일 동시 읽기와 처리 속도는 미검증이다(A2). ← P6, C7, F3, K2, V7, V11, V15, V20, V21, A2
- **C57** dbt는 SQL 관리의 적합한 다음 도구다. 도입 이유: 모델 의존에 따른 실행 순서, 결과 시험(합치기 전 PR 검증)으로 L2가 SQL을 고칠 때(A7)의 안전장치가 된다. 연동: dbt-duckdb(DuckDB 조직, Apache 2.0)는 S3(httpfs)와 PG attach를 지원하고, 확장 때는 dbt-trino(V18)로 이어진다. Kestra는 DbtCLI 작업으로 컨테이너에서 dbt를 돌리고 run_results를 읽어 모델별 시험 결과를 보여 준다. Airflow는 Cosmos(Apache 2.0)가 모델을 작업·작업 그룹으로 펼친다. 실행 도구를 바꿔도 dbt 프로젝트는 남는다(C22). 영향: dbt는 Python이라 변환이 Java 배치 앱(C21, C39 ②)을 떠나 실행 도구가 부르는 dbt 컨테이너로 옮긴다. 배치 앱에는 4단계 워커만 남는다. 내장 스케줄러로는 부르기 어려우므로 Kestra 또는 Airflow가 전제다. dbt Core에는 실행 기록 화면이 없고(dbt docs는 문서·열 계보), 현황은 실행 도구 화면에서 본다. 미확인: Kestra OSS의 dbt 플러그인 포함 여부, external 모델의 증분 미지원 영향, dbt-duckdb의 PG 쓰기 동작, Iceberg는 플러그인 수준(로드맵). ← A7, C14, C21, C22, C39, V18, 사용자 결정(2026-11-07). [dbt-duckdb](https://github.com/duckdb/dbt-duckdb), [Kestra dbt](https://kestra.io/plugins/plugin-dbt), [Cosmos](https://github.com/astronomer/astronomer-cosmos), [dbt docs](https://docs.getdbt.com/reference/commands/cmd-docs)
- **C18** dbt는 일정 기능이 없는 CLI다. dbt로 옮기면 실행 도구가 dbt 컨테이너를 실행하고, dbt는 어댑터로 엔진에 SQL을 보낸다. 이미지는 dbt·DuckDB·모델을 담아 Git 태그로 버전 관리한다. 실행 이력·재시도·재실행은 실행 도구 화면, 모델·시험 결과는 `run_results.json`이 제공한다. ← C57, R6

**결론: 변환이 하는 일**
- **C61** 부서별 격리(R1): 부서별 리소스 목록(PG 표, C27)으로 로그를 걸러 부서 경로에 복사본을 쓰고 S3 경로 권한으로 나눈다. 이 단계에는 행 단위 권한을 걸 엔진이 없고 S3 권한은 경로 단위뿐이기 때문이다. 조회 기능은 제공하지 않는다(R1). 경로 권한 지원은 미확인(A3). 전환은 T2. ← R1, A3, C27
- **C62** 3단계 입력: 바깥 시스템이 읽을 집계(예: F10의 쿼터 변화)를 골드로 만든다. 휴면 대상 목록은 4단계의 입력이다. ← R11a, R2, F10

**결론: 실행과 설정**
- **C27** 실행 값과 설정: 기준값(휴면 기준일, 유예 기간, 승인 기준)은 Kestra 설정 저장소에 두고 SQL 인자로 넘긴다. 표 형태 설정(부서 리소스 목록, 정규식)은 PG 표에 두고, 운영자는 Kestra 실행 입력으로 작업을 돌려 표를 고친다. Kestra로 설정을 바꿀 수 있으므로 별도 설정 관리 GUI(NocoDB 등)는 표 전체 편집 화면이 꼭 필요할 때만 대안이다. 기준일을 바꿔 보는 분석은 실버를 SQL로 직접 조회한다. 발송은 조건을 바꿔도 건수 기준 승인(C17)을 거친다. 실행 입력의 표 형태 값 지원은 미확인(A13). ← R6, R9, C17, C47, C55, A7, A13, 사용자 결정(2026-11-07)
- **C28** 수집→변환 순서: pull 경로는 Kestra가 Airbyte sync 완료 뒤 변환을 시작한다. 내장 스케줄러를 고르면 순서 보장이 없으므로 시각 간격을 두고, 입력(당일 스냅샷)이 없으면 실패한다(fail-closed). push(로그) 경로는 C51. ← C21, C25, C26, C47, C51
- **C51** 로그(push) 경로는 수집 완료 신호가 없으므로 변환을 30분마다 돌린다. 정각+5분 실행은 지난 한 시간을 처음부터 다시 계산한 최종 결과로, 30분+5분 실행은 그 시간 앞 30분의 임시 결과로 쓴다. 최종이 임시를 덮어쓰므로 임시 뒤에 늦게 온 파일도 반영된다(재실행 시 같은 결과). 5분 대기는 임의 값이고(A12), 그보다 늦은 파일은 운영자가 해당 시간을 다시 돌린다. 휴면 판정(R2)은 최종 결과만 읽는다. 임시 결과로 판정하면 기록이 빠진 사용자를 휴면으로 잡아 4단계의 되돌릴 수 없는 행동으로 이어질 수 있기 때문이다(C59). 처리 기준(A2)은 그대로다. 결과를 15분 안팎으로 봐야 하는 요구가 생기면 새로 들어온 파일만 처리해 이어 붙이는 방식으로 바꾼다(Q32). ← A2, A12, R2, C47, C59, 사용자 결정(2026-11-07)

**다음으로 가는 조건**
- **T2** 부서가 파일 대신 조회로 받기를 원하거나, 복사 격리 비용이 정책 격리 비용보다 커지면 → 부서별 복사를 폐기하고 조회 시점 권한으로 전환한다. 권한은 저장소 권한으로 준다(C52). 숫자 기준(N, M)은 미정. ← A3, C61, C52, R1
- **T3** 1시간 윈도우 처리가 15분을 넘으면 → 먼저 4코어 8GB로 scale up, 그래도 넘으면 scale out한다. scale out은 같은 SQL을 입력 범위(시간대, 부서)만 바꿔 별도 컨테이너에서 동시에 실행하는 것이다. 실행끼리 데이터를 주고받지 않으므로 범위를 넘는 집계(예: 전 기간 사용자별 마지막 활동)는 부분 결과를 합쳐야 한다. 동시 실행은 실행 도구(Kestra 병렬 실행)가 맡고, 합치기는 SQL 한 단계로 한다. 분할·병합 코드를 직접 짜지 않는다(K3). 내장 스케줄러를 쓰는 중이면 이때 Kestra로 옮긴다(T9). 이것으로도 풀리지 않을 때만 분산 엔진으로 교체한다. Logic은 유지한다. scale out 대수 상한은 미정. Kestra 병렬 실행의 적합성은 미확인(A13). ← A2, C16, C39, C47, K3, 사용자 결정(2026-11-07)
- **T7** 모델이 늘거나 L2가 PR로 SQL을 수정하기 시작하면(A7) → dbt로 옮긴다(C57). SQL 파일은 모델로 이관한다. 실행 도구가 Kestra 또는 Airflow여야 한다. ← C14, C57, A7
- **T9** 실행 도구 전환. ① 내장 스케줄러 → Kestra: 작업 순서 의존, 시간 구간 재실행, 놓친 실행 보충이 업무에 영향, 화면에서 설정 바꾸기, scale out(T3), dbt 이관(T7) 중 하나가 필요해지거나 내장 화면이 A9를 충족하지 못할 때. ② Kestra → Airflow: 운영자별 권한이나 설정 변경 기록이 필요할 때(C48, C49). 로직(SQL)은 유지한다(C22). Dagster는 후보에서 뺐다(C50). ← C21, C22, C47, C48, C49, C50, A9, T3, T7, V9, V10
- **T6** 휴면 안내·처리(R3, R4)를 시작하면 → 4단계로 간다. ← C38

**미결**
- **Q2** L2가 고칠 수 있는 범위: SQL 전체인지, 값(부서 목록, 정규식)만인지. dbt 이관은 T7.
- **Q6** (내장 스케줄러를 고를 때) 조직에 GUI(이력·재실행)를 가진 자바 스케줄러가 이미 있는가. Quartz는 GUI가 없고, 이력·로그·재시도를 직접 만들면 유지보수가 커진다(K3).
- **Q8** 앱 안 DuckDB JDBC의 온프레미스 S3 접근(`url_style=path`)과 gz JSONL 읽기, dbt-duckdb의 S3 JSONL 읽기·쓰기 검증.
- **Q9** (내장 스케줄러를 고른 경우) JobRunr, db-scheduler-ui의 날짜 인자 재실행과 이력 화면(A9), 재기동 시 놓친 실행 보충(A10), JobRunr 오픈소스 기능 범위(V13은 제3자 요약). Spring Batch의 같은 파라미터 재실행(C36)은 실행 도구와 무관하게 확인한다.
- **Q32** 로그 수집기의 최대 전송 지연(A12). 파일 기준 증분 처리로 바꿀 때 처리한 파일을 기록하는 방법(Kestra·DuckDB 기능인지, 직접 구현인지).

## 10. 3단계: 분석 조회 (바깥 시스템이 골드를 읽는다)

**받을 요구:** R11a 바깥 시스템의 골드 읽기.

**구성**
- **C43** 3단계 구성: 골드(집계 표)를 PG에 쓰고, 바깥 시스템에 읽기 통로(C52)를 연다. 2단계의 DuckDB가 postgres 확장으로 골드를 PG에 바로 쓴다. 집계 SQL이 결과를 바로 넣으므로 로직이 SQL에 남는다(C22). 확장이 안 되면 앱이 DuckDB 결과를 JDBC로 읽어 넣는다(Q24). 새로 켜 두는 서비스는 없다. 골드를 PG에 두는 이유: ① 골드는 작아 S3를 고른 이유(데이터양, F1)가 맞지 않는다(A11) ② 실버에서 언제든 다시 만들 수 있어 원본 보존 대상이 아니다(P5는 브론즈) ③ 표 재생성을 트랜잭션으로 한 번에 바꿔, 읽는 중에 옛 값과 새 값이 섞이지 않는다 ④ 앱이 DB를 읽는 일반적인 방식이고, 바깥 시스템에 S3 접근 키가 필요 없다 ⑤ PG가 이미 있어 서비스가 늘지 않는다(K1). 2단계만 전제하며 4단계와 무관하다(C59). ← R11a, F1, P5, C3, C22, C52, C59, K1, A11, Q24, 사용자 결정(2026-11-05, 2026-11-07)

**결론**
- **C52** 바깥 시스템의 골드 읽기 통로는 PG 읽기 전용 계정(바깥 시스템마다 하나)과 뷰다. 뷰가 바깥 시스템과의 계약이며, 안쪽 표가 바뀌어도 뷰를 유지한다. 사용자별 분할은 바깥 시스템이 맡는다(R11a). Trino가 사용자별 저장소 자격 증명으로 읽는 방법은 미확인(Q34). ← R11, C43, K1, K3, 사용자 결정(2026-11-07)
- **C45** 바깥 시스템에 필요한 집계는 L3가 변환 SQL(dbt 이관 뒤에는 모델)에 더하고 뷰를 연다. 플랫폼 안에서 사용자가 SQL을 직접 써야 하면 T1a다. ← R11, T1a, C14, C52

**미결**
- **Q24** 앱 안 DuckDB의 postgres 확장으로 골드 집계 표 적재와 4단계 대기 표의 충돌 무시 적재(요청 ID 기준)가 되는지. 작은 표로 시험한다. 실패하면 JDBC 복사(C35, C43).

## 11. 4단계: 내보내기

**받을 요구:** R3 휴면 안내 메일, R4 휴면 처리, R6 L2 운영(2단계 실행 도구 화면).

**구성**
- **C38** 4단계 구성: 2단계에 워커(Spring Batch, C36)와 PG 대기 표(outbox)를 더해 휴면 안내 메일과 휴면 처리(R3, R4)를 한다. 대상 선정은 2단계의 SQL이 대기 표에 적재하고(C35, 3단계의 골드 적재와 같은 방법), 2단계 실행 도구가 발송 작업을 시작한다. 워커는 2단계의 배치 앱 안에 넣는다(C40). 휴면 처리도 같은 대기 표와 워커로 한다(C41). L2는 2단계 실행 도구 화면으로 운영한다(C42). 새로 켜 두는 구성 요소는 없다. 2단계만 전제하며 3단계와 무관하다(C59). 막고 있는 미검증: 메일·처리 API의 중복 방지·호출 한도(A1, Q10), 같은 파라미터 재실행(Q9), 대기 표 적재 방법(Q24). 확인되기 전에는 확정하지 않는다(K4). ← C35, C36, C17, C40, C41, C42, C59, T6, A1, Q9, Q10, Q24, K4

**결론**
- **C5** 부작용(메일, 처리)은 상태를 기록하고 최소 한 번 실행한다. ← A1, C3
- **C17** 발송 패턴: ① 기준일 고정 SQL로 후보를 PG에 적재, 이미 발송·활동 재개·제외 목록은 조인으로 제외 ② 건수가 기준 건수를 넘으면 중단하고 승인 ③ 발송 직전 재검증 ④ `pending → sending` 먼저 잡기(`FOR UPDATE SKIP LOCKED`) ⑤ 요청 ID = (사용자, 요청 종류, 회차) ⑥ 결과를 `sent`/`failed`로 기록, 실패분만 재시도. A1이 깨지면 중복 발송을 허용한다. ← A1, C3, C5, R3, R4
- **C23** 변환과 발송은 분리한다. 후보 선정은 SQL(변환), 발송·상태 기록·재시도는 코드(소비 쪽)이고 경계는 PG 표다. 발송 코드는 하나로 둔다. 배치 앱과 같은 Java의 Spring Batch로 한다(C36, C40). 서비스와 언어가 늘지 않기 때문이다. 경계가 PG 표이므로 발송 코드는 언어와 무관하게 바꿀 수 있다. 필요하면(예: 목적지 SDK가 다른 언어만 지원) L3가 별도 언어를 대안으로 고를 수 있고, 이때 워커는 별도 앱이 된다(T12). ← C17, C5, C36, C40, F5, 부록 B, 사용자 결정(2026-11-05)
- **C35** 메일 알림(R3, R4)은 별도 CRM·메일 플랫폼을 만들지 않고 내보내기(리버스 ETL) 레이어로 처리한다. 패턴(P1)은 Source = 실버·골드, Tool = 워커, Logic = 후보 선정 SQL, Sink = 외부 REST API다. 후보는 SQL이 PG 대기 표에 적재하고, 워커가 행 단위로 먼저 잡아 호출한다. 대기 표(변경 가능한 진행 상태)는 모든 단계에서 PG에 둔다. S3와 Iceberg는 행 잠금이 없어 같은 행을 둘이 잡는 일을 막지 못한다(Iceberg는 미확인). 발송 결과 이력은 S3에 추가만 한다(P5). 발송 기록은 분석·확인에 쓰고 고칠 일이 없기 때문이다. 목적지가 메일 알림 하나이므로 목적지 어댑터 추상화는 두 번째 목적지가 생길 때로 미룬다. 후보 적재는 DuckDB postgres 확장으로 선정 SQL이 대기 표에 직접 쓴다. 선정과 적재가 SQL 하나에 있어 로직이 SQL에 남는다(C22). 요청 ID가 이미 있으면 넣지 않으므로(충돌 무시) 선정 SQL을 다시 돌려도 중복 행이 생기지 않는다. 확장은 미검증이다(Q24). 실패하면 배치 앱이 DuckDB 결과를 JDBC로 읽어 PG에 넣는다. ← R3, R4, C3, C5, C17, C22, P1, P5, P6, P9, V15, Q24, 사용자 결정(2026-11-04, 2026-11-05)
- **C56** 대기 표의 직접 구현 범위는 상태 열과 상태를 바꾸는 SQL뿐이다. 잠금과 건너뛰기는 PG `FOR UPDATE SKIP LOCKED`, 중복 방지는 고유 제약, 재시도·재시작은 Spring Batch가 맡는다(K3). 상태가 늘거나 지연 실행·우선순위가 필요해지면 큐 도구(PGMQ, PgQ, Namastack Outbox)를 검토한다. 후보와 단점은 V22. ← C35, C36, V22, K3, 사용자 결정(2026-11-07)
- **C36** 워커는 Spring Batch로 구현한다. 부분 재시도, 건너뛰기, 실패 지점부터 재시작은 검증된 도구가 제공하므로 직접 만들지 않는다(K3). L3의 Spring Batch 경험 부족은 학습 비용이며 직접 구현의 근거가 아니다. 구성: reader = 대기 표의 `pending` 행, processor/writer = 외부 호출과 `sent`/`failed` 상태 갱신. 행 단위 상태와 요청 ID 중복 방지는 대기 표가 맡는다(Spring Batch는 외부 호출 후 저장 전 사망 시의 중복 발송을 막지 않는다). 재처리는 작업 재실행(`failed`/`pending`만 처리), `sending`에 멈춘 행 복구, 같은 기준일 재산출 시 요청 ID 충돌 무시, 발송 직전 재검증 실패 시 `cancelled`다. 재시도·속도 제한 부품은 Spring Batch 설정과 Resilience4j 등(사내 사용 가능 여부 미확인). 실행 도구는 트리거일 뿐 논리 재시도를 맡지 않는다. 같은 실행 파라미터의 재실행 가능 여부는 Q9에서 시험한다(미검증). 이전 결정(일반 Spring Boot)은 철회한다. ← C35, C17, F5, K3, 사용자 결정(2026-11-04)
- **C40** 워커는 2단계의 배치 앱 안에 넣는다. Spring Batch는 계속 켜 두는 서버가 아닌 라이브러리이고 배치 앱은 이미 Java다(C21). 실행 도구가 발송 작업을 시작하고, Spring Batch 메타 표는 PG에 둔다. 신규 서비스가 늘지 않는다(K1). dbt로 옮긴 뒤(T7)에는 배치 앱에 워커만 남는다(C57). 분리 조건은 T12. ← C21, C36, C57, P6, K1, 사용자 결정(2026-11-05)
- **C41** 휴면 처리(R4)는 안내 메일과 같은 대기 표와 워커로 한다. 처리도 외부에 남는 부작용이기 때문이다(C5). 선정 SQL이 "안내 `sent` 시각 + 유예 기간 < 기준일이고 그 뒤 활동 없음"을 골라 요청 종류 = 처리로 적재한다. 유예는 SQL 조건이므로 대기 전용 부품이 필요 없다. 처리 API의 중복 방지 지원은 미확인이다(A1과 같은 방식으로 확인). ← R4, F7, C5, C17, C35, 사용자 결정(2026-11-05)
- **C42** 4단계의 L2 운영(R6)은 2단계 실행 도구 화면을 쓴다. 작업 단위로 성공·실패를 보고 다시 돌리며, 다시 돌리면 `failed`/`pending`만 처리한다(C36). 대상 수가 기준을 넘으면 작업이 멈추고, L2가 대상을 확인한 뒤 승인하면 이어 간다. Kestra는 실행 멈춤(Pause)으로 하고(A13), 내장 스케줄러는 승인 인자를 넣어 다시 돌리는 방식이다(Q9, V12 미확인). 사용자 한 명씩 다루는 화면은 요구가 생길 때 더한다(K1). ← R6, C17, C27, C36, C47, A13, V12, Q9, 사용자 결정(2026-11-05)

**다음으로 가는 조건**
- **T12** 발송 작업이 변환과 메모리를 다투거나(DuckDB `memory_limit` 조정으로 풀리지 않음), 발송과 변환의 배포 주기가 달라지거나, 발송 코드를 다른 언어로 바꾸면(C23) → 워커를 별도 앱으로 분리한다. 대기 표와 선정 SQL은 그대로다. ← C16, C23, C40

**미결**
- **Q10** 메일 API의 호출 한도와 1회 발송 건수 제한. A1(중복 방지)과 함께 API 문서로 확인한다.

## 12. 데이터 플랫폼 확장 (Trino, Iceberg)

**받을 요구:** R11b 플랫폼 안 직접 조회. 3·4단계까지는 시스템의 기능이고, 데이터 자체를 서비스로 내놓는 요구가 생길 때 확장한다. Trino와 Iceberg는 각자의 요구가 생길 때만, 순서 없이 들인다(C19).

**다음으로 가는 조건**
- **T1a** 플랫폼이 조회 기능을 제공해 사용자가 직접 SQL로 조회해야 하면(R11b: 여러 사용자 동시 사용, 쿼리·표 공유 중 하나 이상) → Trino를 도입한다. 권한은 저장소 권한으로 준다(C52). 신뢰하는 L2의 개인 도구(DuckDB + DBeaver 등) 직접 조회는 해당하지 않는다. ← C37, C52, R11
- **T1b** S3의 표를 직접 읽는 쪽(Trino)이 생겨 표를 다시 쓰는 중에 읽힐 수 있거나, 실버의 행 단위 수정·삭제, dbt 증분 MERGE가 필요해지면 → 실버를 Iceberg로 전환한다. 일반 파일 표를 다시 쓰는 도중에 읽으면 옛 파일과 새 파일이 섞인 결과를 읽을 수 있고, Iceberg는 커밋 시점에 한 번에 바뀌어 이를 막는다. 골드는 PG에 둔다(C58). Iceberg 없이 T1a를 먼저 도입할 수 있다. ← P4, P6, P10, C37, C58, V15, V18

**결론**
- **C37** Trino 도입(서버형 SQL 서비스, T1a)과 Iceberg 도입(표 형식, T1b)은 별개 결정이다. 그 전의 개인 도구 분석은 DuckDB + DBeaver 등으로 하며 S3 접근 키가 필요하므로 신뢰하는 L2에 한정한다. 레이크하우스가 최종 방향이다(P4, 사용자 확인 2026-11-04). 실버에 동시 쓰기는 없다. 3단계의 바깥 시스템은 PG를 읽으므로 Iceberg 도입 조건에 해당하지 않는다(C43). 그 전은 일반 파일이다(P10, P6). Hive 메타스토어는 별도 서비스가 필요하고 JDBC 카탈로그는 PG를 쓸 수 있다(V14). 카탈로그 선택과 DuckDB·Trino 호환, Trino의 gzip JSONL 읽기는 미검증이다(Q15, Q16, C31). ← T1a, T1b, P4, P6, P10, C43, V8, V14, V15, V18
- **C58** Iceberg 도입(T1b) 뒤에도 골드는 PG 한 곳에 둔다. Trino는 PostgreSQL 커넥터로 골드를 읽고, Iceberg는 실버에만 쓴다. 두 곳 적재는 쓰기 두 번과 한쪽 실패 시 값 불일치(Trino 조회와 바깥 시스템 조회가 다름)를 낳는다. 한 곳이면 권한도 PG 계정 권한 하나다(C52). 골드가 PG에 담기 어려울 만큼 커지면(A11 붕괴) 그때 골드를 Iceberg로 옮긴다. 미확인: Trino PG 커넥터의 읽기 성능, 사용자별 PG 계정 권한으로의 연결(Q34). ← C43, C52, A11, 사용자 결정(2026-11-07)
- **C31** 엔진과 카탈로그 제약이 꼬리를 문다. DuckDB가 Iceberg에 쓰려면 REST 카탈로그가 필요하고(V15), Trino의 REST 카탈로그는 뷰를 지원하지 않으며(V14), JDBC 카탈로그는 PG로 가능하나 DuckDB 호환은 미확인이다. 둘 다 REST 카탈로그를 지원한다는 것은 문서로 확인했고, 같은 카탈로그를 함께 쓰는 조합은 시험하지 않았다. Trino가 브론즈 `jsonl.gz`를 읽는 경로(Hive 커넥터)도 미확인이라(V8) 확장 뒤에도 DuckDB(브론즈 파싱) + Trino(조회) 두 엔진이 공존할 수 있다. ← V8, V14, V15, Q15, Q16
- **C32** Iceberg 테이블은 정비 잡이 필요하다: `OPTIMIZE`(작은 파일 병합), `expire_snapshots`, `remove_orphan_files`. snapshot 정리를 먼저 하고 고아 파일 정리를 나중에 한다. 보존 기간 기본값은 7일이다. 이 잡은 2단계 실행 도구가 실행한다. DuckDB 문서에는 정비 작업이 없으므로 Trino로 한다(V15 재확인, V16). ← V15, V16, C21
- **C33** C14·C15의 "SQL은 다음 단계에서 재사용"은 읽기 구문(DuckDB `read_ndjson`, `filename`)과 함수 방언에서 깨질 수 있다. 변환 로직의 SQL은 재사용하되 브론즈를 읽는 구문은 엔진별로 바뀐다고 보고 범위를 Q19로 확인한다. 미검증. ← C14, C15, V7, V8

**미결**
- **Q15** Trino가 브론즈 `jsonl.gz`를 메타스토어 없이 읽을 수 있는지(Hive 커넥터 JSON SerDe, V8). 불가하면 브론즈→실버는 DuckDB가 맡는다(C31).
- **Q16** 카탈로그 선택(REST, JDBC on PG, hive_metastore): DuckDB·Trino 양쪽 호환, 뷰 필요 여부, 추가로 켜 두는 서비스 여부.
- **Q18** Iceberg 정비 잡의 주기와 보존 기간. 스냅샷 이력 분석 요구(R9)와 충돌하는지.
- **Q19** SQL 방언 차이로 재사용이 깨지는 범위(C33). 읽기 구문, JSON 함수, 날짜 함수.

## 13. 최종 구성

- **C29** 오픈소스 중심의 최종 구성은 아래 컴포넌트다. 요구가 생길 때마다 더하며, 어떤 요구가 생기느냐에 따라 일부만 들어올 수 있다(K5). S3와 PG는 처음부터 있다. 3단계의 읽기 통로는 PG 기능이라 컴포넌트가 늘지 않고, 골드를 읽는 앱은 바깥 시스템에 있다. 권한은 확장 뒤에도 저장소 권한으로 주므로 정책 서버를 두지 않는다(C52). ← C20, C21, C38, C43, C47, C52, C57, C58, T1a, T1b, K5

| 컴포넌트 | 들이게 하는 요구 | 들어오는 때 |
|---|---|---|
| Airbyte | 흩어진 시스템의 데이터를 한곳으로 가져온다(R10) | 1단계 |
| 배치 앱(DuckDB SQL), L2가 PR로 SQL을 고치게 되면 dbt | 업무 규칙으로 실버와 골드를 만든다(R1, R2, R9, R11a) | 2단계(dbt 이관 뒤 변환은 dbt 컨테이너, 배치 앱에는 워커만, T7) |
| 실행 도구(Kestra + oauth2-proxy, 권한·변경 기록이 필요하면 Airflow) | 작업 순서, 시간 구간 재실행, 화면 설정 변경(R6) | 2단계(요구가 없으면 배치 앱 안 내장 스케줄러, T9) |
| 워커(Spring Batch, 배치 앱 안) | 메일 발송과 휴면 처리(R3, R4) | 4단계 |
| Trino | 플랫폼 안 직접 SQL 조회(R11b) | 확장(T1a) |
| Iceberg 카탈로그 | S3 표의 직접 읽기, 행 수정·삭제 | 확장(T1b) |

- **C30** 샘플 시스템의 요구 아홉(§5 대응 표)은 1~4단계에서 받는다. 예외는 GHES CSV를 원본 대신 레코드로 보관하는 것(C10)이다. 받아들인 빈칸은 로그 경로 설정에 운영자 화면이 없는 것(C55)이다. 최종 구성에서는 새 분석을 SQL로, 새 소스를 Airbyte 커넥터로 받고, 컴포넌트는 T의 조건이 생길 때만 바뀐다(K5). 범위 밖 후보는 즉시 반응(T4, T11), BI 대시보드(§14), 분산 엔진(T3의 마지막)이다. ← K5, C10, C29, C55, T3, T4, T11

## 15. 의사결정 코멘트

아래 "2026-11-06 이전 기록"은 당시 판단의 기록이다. Phase 번호는 §7 표로 읽는다.

**2026-11-07 아티클 정합 재정리**

- **단계 재구성**: 이전 Phase 3(메일)과 Phase 4(조회 앱, 오케스트레이터, Iceberg, Trino)를 아티클 기준으로 나눴다. 조회는 3단계, 내보내기는 4단계이고 둘은 서로 독립이다. 구분 기준은 "바깥에 되돌릴 수 없는 영향을 남기는가"다(C59). Trino와 Iceberg는 데이터 플랫폼 확장으로, 오케스트레이터는 2단계의 실행 도구 선택지로 옮겼다(C21, C29). "최소 구성", "끝 구성"은 쓰지 않고 "최종 구성"으로 통일했다(K5).
- **조회 앱 철회**: 이 시스템이 최종 사용자용 조회 앱을 만든다는 판단(C34, C44, Q23, Q25)을 철회했다. 골드를 읽는 앱은 바깥 시스템에 있고, 이 시스템은 PG 읽기 전용 계정과 뷰만 연다(C52). 사용자별 분할은 바깥 시스템이 맡으므로 소속 정보 읽기(Q25)도 필요 없다. "사용자가 직접 본다"는 R11a(바깥 읽기)와 R11b(플랫폼 안 직접 조회)로 나눴다.
- **행 필터·정책 서버 철회**: Trino 행 필터와 OPA(Q17의 행 필터 부분, V17)는 쓰지 않는다. 권한은 확장 뒤에도 저장소 권한으로 준다(C52). V17은 외부 사실로 남긴다. Q17의 "부서 격리를 복사본으로 할지 정책으로 할지"는 T2로 옮겼다.
- **골드 두 곳 적재 철회**: C43의 "Iceberg 도입 뒤 골드 원본을 S3 Iceberg로 옮기고 PG는 사본"을 철회했다. 골드는 PG 한 곳이고 Trino는 PostgreSQL 커넥터로 읽는다(C58).
- **오케스트레이터 후보 정리**: Dagster는 OSS에 권한이 없고 Kestra보다 무거워 뺐다(C50). 기본은 Kestra OSS + oauth2-proxy(C47), 사람별 권한이 필요하면 Airflow(C49)다. 설정 관리 GUI(NocoDB 등)는 Kestra로 설정을 바꿀 수 있어 대안으로만 둔다(C27).
- **Airbyte 대안 정정**: T8의 "스케줄러 안의 코드로 흡수"는 직접 구현이라 K3와 충돌했다. 대안을 Kestra 수집 작업 또는 dlt로 바꾸고, 세 조건이 모두 맞을 때만 고르게 했다(T8).
- **dbt 위치 정정**: C14의 "Logic은 dbt 모델로 둔다"는 T7(도입 시점)과 앞뒤가 맞지 않았다. 지금은 SQL 파일이고 dbt는 T7 조건에서 옮기는 다음 도구다(C14, C57). dbt로 옮기면 변환 실행 위치가 바뀐다는 영향을 함께 적었다.
- **부서 격리의 제공 형태**: 부서는 자체 도구로 S3 파일을 읽는다. 이 시스템은 조회 기능을 제공하지 않는다(R1, C61).
- **로그 변환 주기**: 로그 경로는 수집 완료 신호가 없어 30분 주기와 최종 결과 덮어쓰기로 늦게 온 파일을 처리한다(C51).
- **대기 표 직접 구현 범위**: 상태 열과 SQL뿐이며 나머지는 PG와 Spring Batch 기능이다(C56). 큐 도구 후보는 V22.
- **문서의 한계**: 이 문서와 아티클은 샘플 시스템을 통한 방향 제시이며, 미확인 항목의 확인 시점과 방법은 적용 시스템이 정한다(Q22).

**2026-11-06 이전 기록**

- **S3 선택**: 데이터 증가를 수용하고 워크로드 디스크 압력을 제거하기 위함(F1). PG는 갱신이 가능해 불변 보존(P5)과 맞지 않는다(C7).
- **CSV 통일 기각**: 로그는 중첩 JSON이라 CSV로 변환하면 손실이 생기고 원본이 아니게 된다(C8).
- **JSONL 통일 철회**: 처음에는 JSONL 통일을 권했으나, 표 형태 소스에서 타입 손실과 크기 비효율이 있고 통일의 이점(읽는 쪽 단순화)이 작아 철회했다(C8).
- **봉투 패턴**: 레코드 소스는 도구가 만든 봉투(`_airbyte_*`, Debezium 이벤트)가 곧 원본이다. 파일 소스는 바이트를 보존하고 메타를 옆에 둔다(C9).
- **GHES 예외**: 처음에 "API 응답이라 레코드가 원본"이라 구분했으나 근거가 없어 철회했다. 파일이므로 바이트 보존이 원칙이지만, Airbyte 기능 제한으로 레코드 + 메타로 근사한다(C10).
- **포맷 우선순위**: 사람이 읽을 수 있는 JSONL, CSV를 우선하고 Parquet, Avro는 가능하되 후순위다(P7, C13).
- **오케스트레이터 필수 판단 철회**: 처음에 "휴면 단계가 잡 경계를 넘으므로 오케스트레이터 필수"라 했으나, 단계는 PG 상태로 풀 수 있어 근거가 약했다. 필수 근거는 L2의 GUI 요구(C2)다(C4).
- **dbt 채택 이유와 한계**: 선택 이유는 SQL 재사용(엔진 교체), PR 리뷰의 안전망(테스트·리니지)이다(C14). 4개 유즈케이스만 보면 과한 면이 있어 도입은 T7 시점으로 미룬다. 대안은 SQL 파일 + 러너(가장 단순, 테스트·리니지 직접 구현)와 SQLMesh(세부 미검증)다. 빠지는 기능은 `ref()` 의존 해석, 적재 방식 템플릿, 테스트, 리니지·문서, 어댑터 교체다.
- **Python 필수 아님**: SQL 실행은 DuckDB로 충분하다(C16). 최초 제안의 "Python + DuckDB"는 R3·R4 이전에는 과했다.
- **DuckDB 실행 방식 변경 (CLI → 앱 내장)**: 처음에는 `duckdb -f` CLI로 실행한다고 했다. 사용자가 "스케줄러가 Java 앱이면 DuckDB 라이브러리를 앱에 넣으면 되고, 로직은 SQL에 있다"고 지적해 앱 내장으로 바꿨다. 대가는 메모리 공유이며 한도 설정으로 막는다. 나눠 돌려야 하면 실행을 별도 컨테이너로 뗀다(T3, C16).
- **환경**: 온프레미스, VM 또는 k8s, k8s 필수 아님, 운영 컴포넌트 최소화, 개발·커스터마이징 자원은 최종까지 재사용이 설계 조건이다. 단계 0의 신규 계속 켜 두는 구성 요소는 스케줄러 1개다. dbt와 DuckDB는 실행 후 종료된다.
- **Phase 구분과 제로 베이스 점검**: Phase 2를 Phase 1 위에 쌓지 않고 처음부터 설계해도 Airbyte가 남는지 점검했다. 스케줄러가 있으면 Airbyte의 스케줄 기능은 겹치고, 남는 가치는 오픈소스 커넥터와 소스 설정 GUI다. 소스가 Gerrit(직접 만든 CDK), GHES(Builder), PG뿐이면 이 가치는 작고 Airbyte 운영은 가장 무겁다. 그래도 "수집 단일 도구"(P8)와 PG CDC 가능성 때문에 유지하고, 재검토 조건을 T8로 남겼다(C25).
- **스케줄러 범위 축소**: 처음에는 스케줄러가 Airbyte sync까지 호출하는 통합 GUI를 제안했다(V9로 가능함을 확인). 사용자가 스케줄러를 변환·발송 전용으로 좁혔고, 대가로 수집→변환 순서 보장이 없어졌다. 시각 간격과 입력 없음 실패로 대신한다(C28).
- **직접 SPA 기각**: 이력, 재실행, 입력 폼, 로그인을 모두 만들고 유지해야 한다(P6). 내장 화면(V12, V13)이나 오픈소스 스케줄러를 쓴다.
- **입력 폼 중요도 판단 철회**: 처음에 "낮음"이라 했으나 휴면 기준일을 바꿔 보는 분석 용도를 놓친 판단이었다. 운영 재실행(인자)과 분석 탐색(실버 직접 SQL 조회)으로 나누어 해결한다(C27).
- **워커 위치와 휴면 처리 (미정 → 최소 구성)**: 워커를 배치 앱에 넣을지, 휴면 처리를 누가 시작할지, outbox에 어떻게 넣을지가 미정이었다. 사용자가 최소 구성으로 정하라고 해서, 워커는 배치 앱 안(C40), 처리는 같은 outbox의 다른 안내종류(C41), 적재는 DuckDB postgres 확장(C35), 운영은 기존 스케줄러 화면(C42)으로 정했다. Phase 3에서 새 서비스는 늘지 않는다.
- **Phase 4 최소 구성**: Phase 4가 조회 앱, Trino, Iceberg, 오케스트레이터를 한꺼번에 더하는 것처럼 읽혔다. 사용자가 최소 구성으로 정하라고 해서, 최소는 조회 앱 하나(C29)로 두고 나머지는 조건 순서로 들어오는 끝 구성으로 나눴다. 골드는 데이터양 기준의 예외로 PG에만 적재하고(C43, 실버까지는 S3), 권한은 앱(C44), 지표는 L3의 SQL(C45)로 정했다. 그 결과 Iceberg 도입 시점이 "R11 서빙 시작"에서 "S3 표를 직접 읽는 쪽이 생길 때"로 늦어졌다(C37, T1b).
- **Spring Batch 필수 아님 (철회)**: 처음에는 발송 대상 상한이 5만 건이고 재시작·중복 방지는 PG 상태로 해결된다고 보았다(C24). 이후 기준을 "필요한 시점에 검증된 도구를 쓰고 직접 만들지 않는다"(P10)로 고정하면서 활성화 워커에는 Spring Batch를 채택했다(C36). 변환 단계(SQL 실행)에는 여전히 쓰지 않는다(C24).
- **Spring Batch가 필요 없는 목적지 사례(향후 두 번째 목적지 검토용, 가정 예시)**: 필요 여부는 "수천 건 이상을 건마다 외부로 호출하고, 중간에 실패한 건만 다시 보내야 하는가"로 판단한다(C36). 아래는 이 기준에 해당하지 않아 필요 없다고 본 사례다. ① 하루 한 번 요약 알림: 휴면 대상 인원을 슬랙에 한 건만 보낸다. 실패하면 다시 호출하면 되므로 행 단위 재시도와 재시작이 없다. ② 파일로 내보내기: 휴면 후보 목록을 CSV로 만들어 다른 팀이 가져가도록 S3에 쓴다. 외부 호출이 아니고, 실패하면 통째로 다시 쓴다. ③ 소수 건 호출: 하루 몇 건만 외부 시스템에 등록한다. 한 건이 실패하면 사람이 확인하고 다시 실행한다. 사례는 모두 미검증 가정이며, 두 번째 목적지가 실제로 생기면 건수와 실패 처리 요구를 확인한 뒤 다시 판단한다(C35).
- **스케줄러 후보 비교 결과**: Dagster·Airflow는 연동이 풍부하나 계속 켜 두는 서비스가 3~4개와 DB다(V10). db-scheduler-ui·JobRunr는 서비스가 늘지 않으나 Airbyte·dbt 연동, 날짜별 재실행, 잡 체이닝은 직접 만들거나 유료다(V12, V13). 그래서 최소 구성은 내장 화면, 확장 구성은 Dagster 또는 Airflow로 둔다(C21, T9). Argo Workflows는 쿠버네티스에서만 돌아가 VM에서 쓸 수 없으므로 제외했다.
- **설정 이원화**: S3 접근키는 Airbyte 목적지와 변환 양쪽에 필요하다. 소스 접속정보(PAT, Gerrit 계정)는 Airbyte에만 둔다(Q14).
- **Phase 4 정의와 평가 기준**: 최종 구성을 "더 이상의 인프라 추가 없이 적재·분석 요구를 모두 수용하는가"로 평가했다. 오케스트레이터, Iceberg, Trino를 더한 구성이 이를 충족하므로 Phase 4로 부른다(C29, C30). 처음에는 "인프라 2개"로 보았으나 Iceberg는 저장 형식이고, 실제로 늘어나는 것은 Trino, 카탈로그, (정책 서버), 오케스트레이터다. 세 가지는 조건 순서대로 들어오므로 Phase를 더 늘리지 않고 전환 규칙으로 순서를 정한다. 이벤트 트리거와 BI는 엑스트라 후보이며 현재 범위 밖이다.
- **Phase 4 검토 사항(재검토 후보)**: C14·C15의 "SQL 전 단계 재사용" 가정이 읽기 구문에서 깨질 수 있다(C33). 엔진 2개가 공존할 수 있어 "엔진 교체 시 어댑터만"이라는 단순한 그림이 성립하지 않을 수 있다(C31). C14·C15에는 "읽기 문법은 예외일 수 있음(확인 전)"을 이미 표시했다. Q15~Q21로 확인한 뒤 확정 문구로 바꾼다.

## 부록 A. 작업 규칙 (논리와 무관한 사용자 지정)

**답변 분량**
- 짧은 답은 300자, 중간 답은 500자, 긴 답은 800자 이내로 한다.

**답변 형식**
- 명제 중심으로 쓰고 불필요한 서술어를 쓰지 않는다. 사실, 가정, 결론을 섞지 않는다.
- 한 번에 쏟아내지 않는다. 새 개념이나 용어는 천천히 풀어서 설명한다.
- 질문은 한 번에 하나만 하고, 답을 기다리는 질문은 마지막에 둔다.
- 길고 방대해지면 논점이 흐려지므로 범위를 좁혀서 설명한다.

**검토 방식**
- 의견은 객관적으로 검토해서 낸다. 맞춰 주기 위해 동의하지 않는다.
- 협업 방식이나 모던 데이터 아키텍처 기준에서 비효율이 있으면 근거를 들어 수정을 요청해도 된다.
- 조사가 필요한 주장은 출처를 붙여 검증한다. 검증하지 못한 부분은 미검증으로 표시한다.
- 틀린 판단은 변명 없이 철회하고 이유를 기록한다.
- **ADR 검토 기준**: 최종 구성을 위한 최적의 기술을 선정하고, 오버엔지니어링이 되지 않도록 각 페이즈에 맞는 적절한 최소 구성 기술을 도입하여, 플랫폼의 확장에 맞춰 최종 구성을 단계별로 완성한다. (P6, P9, P10과 같은 방향)
  - **검토 대상**: 최종 구성을 위한 포석, 즉 각 페이즈의 선택이 최종 구성으로 이어지는지(재사용되는지, 버려지는지).
  - **검토 목적**: 포석을 엄밀하게 검증해 ADR로 남긴다. 근거(V)가 없거나 미검증인 포석은 ADR로 확정하지 않고 검증 과제(Q)로 둔다.

**검토 절차**
- 논점마다 같은 순서로 진행한다: 전제(사실·원칙·가정) 제시 → 조사로 검증 → 결론(근거 ID 명시) → 미결·위험 → 확인 질문 1개.
- 사용자가 지적하면 즉시 재검토하고, 문서에는 철회한 판단과 이유를 코멘트로 남긴다.
- 영역별 정리 요청(예: 수집 영역)에는 소스 · 도구 · 원본 · 메타 표, 원칙, 예외, 미결, 영역 밖 경계 순으로 답한다.

**문서 양식**
- 문서는 `docs/evolution/`에 두고 공통(§사실 · 원칙 · 가정 · 검증된 외부 사실 · 요구사항 · 검토 기준과 평가 축 · 공통 결론) → 1~4단계와 데이터 플랫폼 확장(단계마다 받을 요구 · 구성 · 결론 · 다음으로 가는 조건 · 미결) → 최종 구성 → 엑스트라 → 의사결정 코멘트 순서를 유지한다. 단계 이름과 순서는 아티클(`transform-layer-article.md`)을 따른다.
- 결론은 `← 근거 ID`를 반드시 붙인다. 근거 없는 결론은 쓰지 않는다.
- 외부 사실(V)은 출처 링크를 붙이고, 미검증 부분은 문장 안에 명시한다.
- 사용자 지정 규칙과 배경은 부록에 두고, 논증 본문과 섞지 않는다.
- 새 결정이나 규칙이 확정되면 해당 섹션과 부록을 즉시 갱신한다. 커밋은 요청이 있을 때만 한다.

**답변 양식**
- 첫 줄에 결론을 쓴다. 문단마다 `→`로 시작하고 핵심어를 굵게 쓴다.
- 비교는 표로, 근거는 ID(F, P, A, V, C, T, Q)로 인용한다.
- 마지막은 답을 기다리는 질문 하나로 끝낸다. 질문이 없으면 이어서 다룰 항목을 쓴다.

**용어**
- 요구사항 중 전환을 일으키는 핵심 조건을 "선택압"이라 부른다. 선택압은 측정할 수 있는 조건이어야 한다.
- 이 문서의 목적은 요구가 생길 때 레이어를 더하고, 선택압에 따라 최종 구성으로 진화하는 논리 전개와 변곡점을 확립하는 것이다.
- 단계는 아티클을 따른다: 1단계 수집, 2단계 변환, 3단계 분석 조회, 4단계 내보내기, 데이터 플랫폼 확장, 최종 구성(C29). 이전 "Phase 1~4"와의 대응은 §7 표에 있다. "최종 구성"은 컴포넌트의 종류와 연결을 뜻한다(K5).

## 부록 B. 운영 배경 (사용자 제공 정보)

- 파이프라인 개발은 L3(개발팀), 구성·운영·분석은 L2가 담당한다. 서로 다른 사람이다.
- 현재 파이프라인은 모던 데이터 아키텍처 중심으로 구성하고, 유지보수와 진화가 유연해야 한다.
- 모든 수집 경로는 소스, 도구, 로직, 싱크의 일반 패턴으로 처리한다.
- 패턴 요소가 바뀔 때 확장 방식을 정한다. 예: Airbyte로 PG 소스를 추가할 때 Sink를 S3로 할지 PG로 할지.
- 초기 논점은 dbt 같은 트랜스폼 레이어를 패턴으로 수용하는 방법이다. 포함할 판단 항목: S3 → S3 / PG / Iceberg 중 무엇인지, 언제 하는지, 개발이 하는지 운영이 하는지, 관리 범위, 최종 아키텍처에서 쓸 수 있는지, 운영 부담, 쓸 수 없다면 투입 한도와 전환 시점.
- 휴면 식별과 처리는 이미 있는 유즈케이스다. 사전 안내 메일이 필요하며, 메일 API는 요청 ID 기반 중복 방지를 지원할 것으로 예상한다. 지원하지 않으면 중복 발송을 허용한다.
- 향후 유즈케이스 후보: 일별 사용자 수 집계, 저장소별 스토리지 사용량, 이벤트 트리거 기반 분석.
- 독립 변환은 잡을 추가하는 것으로 수용한다. 모든 변환이 서로 의존하는 것은 아니다.
- PG 사용자 테이블 적재가 필요하다. 예상 규모는 약 5만 건이고 full·CDC는 미정이었다.
- 실버에 `snapshot_date`를 붙여 일·시간 단위 이력을 남기고, 사용자 추이와 휴면 기준일 다중 비교에 쓰려 한다.
- 앞으로 모든 pull 수집은 단일 도구로 하고 싶다.
- 스케줄러는 변환(transform)과 소비(uses) 대상으로만 쓰고, 상시 실행 단일 인스턴스를 선호한다.
- 아키텍처 평가 기준은 유지보수성, 개발 리소스·속도다. 리소스를 중복 투자하지 않고 최종 구성으로 최소 투입하는 것을 원한다(세 번째 기준은 이렇게 해석했다).
- Java도 Python과 동등하게 관리해야 한다. Airbyte CDK 커넥터는 Python으로 만들었다.
- 최종 구성은 더 이상의 인프라 추가 없이 데이터 적재와 분석 요구사항을 모두 수용하는지로 평가한다. 최소 구성에서 어떤 컴포넌트를 언제 바꾸는지가 평가 대상이다.

## 부록 C. 수집·스케줄러 도구의 운영자 GUI 비교 (2026-11-06 조사)

운영자(L2)가 코드 없이 화면에서 할 수 있는 일을 비교한다. R6(L2가 웹 GUI로 구성·모니터링·재실행)과 Phase 1 도구 선택(Airbyte 유지)의 근거다. 표의 "언급 없음"은 아래 출처 문서에서 확인하지 못했다는 뜻이다. 기능이 없다는 뜻은 아니다.

**결론**
- **C53** 스케줄러 화면(db-scheduler-ui, JobRunr)은 실행 확인과 재실행에 그치고, 연결 정보·일정·대상 같은 설정은 바꾸지 못한다. 운영자가 설정을 화면에서 바꾸는 요구(R6, "구성")는 수집 경로에서 Airbyte만 받는다. ← R6, F5, 이 부록 표
- **C54** 따라서 Phase 1의 Airbyte는 운영 부담에도 불구하고 유지한다. 앞서 "운영자 화면은 Phase 2 스케줄러로 대신할 수 있어 Airbyte는 현재 규모에 과하다"고 본 판단은 스케줄러 화면이 설정 변경을 하지 못한다는 점을 빠뜨린 비교였으므로 철회한다. ← C53, 부록 B("모든 pull 수집은 단일 도구")
  2단계의 Kestra(부록 D)도 Airbyte의 연결 설정 화면을 대신하지 못한다. Kestra 화면은 YAML 수정과 실행 입력이라 운영자 양식 화면이 아니다. 대안(Kestra 수집 작업, dlt)과 고르는 조건은 T8이다. dlt는 Python 라이브러리로 즉시 쓸 수 있는 커넥터가 적고 새 소스는 대개 코드로 붙이며, 연결 설정 화면이 없다(미확인). 추적 메타데이터도 직접 챙겨야 한다. ← 사용자 결정(2026-11-07)
- **C55** Airbyte 화면은 pull 경로에만 쓰인다. 변환 설정(휴면 기준일, 유예 기간, 승인 기준, 부서 리소스 목록)은 2단계 실행 도구(Kestra) 화면에서 바꾼다(C27). 로그 경로(수집기의 S3 전송 설정)는 운영자 화면 없이 개발자가 서버 배포 설정으로 바꾼다. 거의 바뀌지 않으므로 받아들인 빈칸으로 둔다(C30). ← C53, C27, C47, 사용자 결정(2026-11-07)

**미결**
- **Q27** Airbyte self-managed(Core)에서 위 연결 설정이 모두 제공되는지. 출처 문서의 등급 표시에 Core가 있으나 등급별 차이는 문서에 설명이 없다.
- **Q28** Airbyte 화면의 수동 실행(Sync now)과 실패 sync 재시도 동작.

## 부록 D. 오케스트레이터 오픈소스판의 인증·권한 비교 (2026-11-07 조사)

R6(운영자가 화면에서 설정·재실행)과 C55(변환 설정과 로그 경로의 화면)을 받을 오케스트레이터를 오픈소스판 기준으로 비교한다. "미확인"은 출처 문서에서 확인하지 못한 항목이다.

| 항목 | Kestra OSS | Dagster OSS | Airflow OSS |
|---|---|---|---|
| 켜 두는 것 | 단일 프로세스 + PostgreSQL | 웹서버, 데몬, 코드 로케이션 + PostgreSQL(V10) | API 서버, 스케줄러, DAG 프로세서(triggerer 선택) + 메타DB(V10) |
| 로그인 | Basic Auth 계정 하나(`kestra.server.basic-auth`) | 내장 없음(미확인) | 인증 관리자. 기본 Simple은 개발·시험용 |
| 역할별 권한 | 없음. RBAC는 Enterprise | 없음. Dagster+ 전용(미확인) | Simple은 고정 역할 넷(viewer, user, op, admin). 운영용 FAB·Keycloak 인증 관리자(미확인) |
| 감사 기록 | 없음. Enterprise | 없음(미확인) | Audit Log(미확인) |
| 인증 확장 지점 | 문서에 없음. 플러그인은 작업·트리거용 | 문서에 없음 | `BaseAuthManager` 상속으로 직접 구현 가능 |
| 작업 플러그인 언어 | Java(Gradle) | Python | Python |
| 화면에서 설정·실행 값 | KV 저장소, 실행 입력(판별 제공 여부 미확인) | Launchpad 실행 설정 | Variables, Connections, Params 폼 |

**결론**
- **C47** 오케스트레이터가 필요하면 기본 후보는 Kestra OSS다. 켜 두는 것이 가장 적고, 플러그인이 Java라 배치 앱과 기술이 같다. 인증은 앞단에 oauth2-proxy를 두어 사내 SSO로 로그인만 통제한다. ← 이 부록 표, 부록 B(Java·Python 동등 관리)
- **C48** C47의 한계: oauth2-proxy는 "들어올 수 있는가"만 정한다. 들어온 사람은 모두 Kestra의 같은 계정으로 동작하므로 사람별 권한과 변경 기록이 없다. ← 이 부록 표
- **C49** 운영자별 권한이나 설정 변경 기록이 요구되면 개별 대안으로 Airflow OSS를 쓴다. 오픈소스판 중 역할별 권한과 인증 확장 지점을 가진 것은 Airflow뿐이다. 대가는 켜 두는 서비스가 늘고 흐름 정의가 Python이라는 점이다. ← 이 부록 표, V10
- **C50** Dagster OSS는 Kestra보다 무겁고 오픈소스판에 권한이 없어 이 유즈케이스에서는 두 후보보다 이점이 적다. 후보에서 뺀다. ← 이 부록 표

**미결**
- **Q29** Kestra OSS 앞단 oauth2-proxy 구성: Basic Auth를 끌 수 있는지, 프록시 뒤에서 API·웹훅 경로(`open-urls`)를 어떻게 열지.
- **Q30** Kestra OSS의 KV 저장소와 실행 입력 폼 제공 여부, Airbyte·DuckDB 플러그인의 동작.
- **Q31** Airflow 운영용 인증 관리자(FAB, Keycloak)의 역할 구성과 Audit Log 범위.
