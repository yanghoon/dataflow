# 워크로드를 한 칸씩 더해 데이터 분석 서브시스템을 완성하기

> 이 글은 읽기용이다. 판단 근거와 검증 기록은 [transform-layer.md](transform-layer.md)에 있다.

## 이 글이 다루는 것

서비스를 운영하다 보면 데이터로 답해야 하는 질문이 생긴다. 사용자는 얼마나 늘고 있는가. 오래 쓰지 않은 계정은 누구이고, 언제 정리해야 하는가. 각 부서는 자기 데이터만 보고 있는가. 이런 질문에 답하고, 그 답으로 계정 정리나 접근 제한 같은 정책을 실행하려면 데이터 분석이 필요하다. 특별한 시스템만의 이야기가 아니다. 사용자가 있는 시스템이라면 대부분 겪는다.

그런데 필요한 기술과 범위는 시스템마다 다르다. 데이터가 적고 개발자가 직접 운영하는 시스템은 DB에 쿼리 하나를 날리는 것으로 충분하다. 데이터가 서버 디스크를 압박할 만큼 늘고, 개발하는 사람과 운영하는 사람이 나뉘면 이야기가 달라진다. 별도 저장소, 수집 도구, 실행 일정을 관리할 스케줄러, 운영자가 쓸 화면이 필요해진다. 처음부터 큰 구성을 들이면 쓰지 않는 서비스를 운영하느라 비용이 든다. 반대로 지금 편한 도구로 시작했다가 나중에 버리면 같은 일을 두 번 한다.

이 글은 하나의 샘플 시스템을 예로 들어, 시스템이 커지는 단계마다 어떤 도구와 구성이 필요한지 알아본다. 단계마다 왜 그 기술을 골랐는지, 어떤 상황이 오면 다른 기술로 바꾸는지를 함께 적는다. 상황이 다르면 답도 다르므로, 대안은 그 대안이 맞는 상황과 함께 읽어야 의미가 있다. 마지막 단계의 구성은 워크로드나 서비스를 더 늘리지 않고 대부분의 분석 요구를 받는다.

자기 시스템에 적용하려면 아래 표에서 지금 어느 단계에 있는지 먼저 찾고, 그 단계의 갈림길 표에 적힌 조건을 자기 상황과 비교하면 된다.

| 단계 | 이 단계가 필요해지는 때 | 더하는 것 |
|---|---|---|
| 1. 모으기 | 데이터가 여러 곳에 흩어져 있고, 서버 디스크로 감당하기 어려울 만큼 늘어날 때 | S3 저장소, Airbyte 수집 도구 |
| 2. 가공하기 | 모은 데이터에 부서별 필터나 휴면 판정 같은 업무 규칙을 적용해야 할 때 | DuckDB 변환, 스케줄러가 든 배치 앱 |
| 3. 내보내기 | 분석 결과로 메일 발송 같은 바깥 행동을 해야 할 때 | 대기 표, Spring Batch 워커 |
| 4. 보여 주기 | 운영자 외에 최종 사용자가 직접 결과를 봐야 할 때 | 조회 앱, Trino, Iceberg, 오케스트레이터 |

## 기본 개념: 메달리온 구조

이 글은 모던 데이터 아키텍처의 흔한 방식인 **메달리온 구조**를 따른다. 데이터를 세 층으로 나눠 쌓는 방식이다.

- **브론즈:** 소스에서 받은 원본을 그대로 둔다. 고치지 않는다. 나중에 가공 규칙이 틀린 것을 알았을 때 원본에서 다시 만들 수 있어야 하기 때문이다.
- **실버:** 브론즈를 합치고 거르고 정리한 데이터다. 업무 규칙은 여기서 적용한다.
- **골드:** 실버를 집계해 바로 보여 줄 수 있게 만든 데이터다.

층을 나누면 각 층의 책임이 분명해진다. 수집 도구는 브론즈까지만 책임지고, 업무 규칙은 실버 이후에서만 다룬다.

## 샘플 시스템

샘플 시스템은 개발 조직이 쓰는 플랫폼이다. 데이터는 서버 디스크로 감당하기 어려울 만큼 많고, 개발하는 사람과 운영하는 사람이 나뉘어 있다. 앞에서 말한 "이야기가 달라지는" 규모다. 선택의 이유를 구체적으로 따지기 위해 숫자까지 정해 둔다.

**데이터 소스는 네 가지다.**

- **로그:** 로그 수집기가 서버 로그를 압축 파일로 계속 보낸다. 주 4.2억 건, 가장 많은 시간에는 시간당 530만 건이다.
- **코드 리뷰 시스템:** API로 레코드를 준다.
- **코드 호스팅 서버:** 사용자 목록을 CSV 파일로 준다.
- **사용자 DB:** PostgreSQL에 있는 사용자 테이블이다. 약 5만 건으로 예상한다.

**사람은 둘로 나뉜다.** 개발자가 파이프라인을 만들고, 운영자가 구성과 운영과 분석을 맡는다. 운영자는 코드를 쓰지 않으므로 웹 화면에서 설정을 바꾸고, 실행 상태를 보고, 실패한 작업을 다시 돌릴 수 있어야 한다.

**요구는 여섯 가지다.**

| 요구 | 왜 필요한가 |
|---|---|
| 흩어진 데이터를 한곳에 모은다 | 모든 분석의 출발점이다. 데이터는 계속 늘어난다 |
| 부서별로 데이터 접근을 나눈다 | 부서는 자기 리소스의 데이터만 봐야 한다 |
| 오래 쓰지 않은 사용자를 찾아 안내하고 처리한다 | 이미 하고 있는 업무다. 찾기, 안내, 유예, 처리 순서로 진행한다 |
| 운영자가 웹 화면으로 운영한다 | 운영자와 개발자가 다른 사람이다 |
| 시간별 사용자 이력으로 추이를 본다 | 기준일을 바꿔 가며 비교하고 예측해야 한다 |
| 최종 사용자에게 분석 결과를 보여 준다 | 사용자가 자기 권한 범위의 지표를 직접 봐야 한다 |

## 선택 규칙

모든 단계에서 같은 규칙으로 고른다.

1. **필요가 생겼을 때만 더한다.** 미리 만든 서비스는 쓰이기 전까지 비용만 든다.
2. **검증된 도구가 있으면 직접 만들지 않는다.** 직접 만든 것은 만든 사람이 계속 고쳐야 한다.
3. **지금 고른 것은 끝 구성에서도 쓰여야 한다.** 버릴 임시 구현은 만들지 않는다.
4. **확인하지 못한 것은 확정하지 않는다.** 확인 전까지는 "미확인"으로 표시하고 시험할 항목으로 남긴다.

## 1단계: 데이터를 모은다

### 언제 필요한가

데이터가 여러 곳에 흩어져 있고, 서버 디스크로 감당하기 어려울 만큼 늘어날 때다. 분석을 하려면 먼저 데이터를 한곳에 모아야 한다. 샘플 시스템의 로그는 이미 많고 계속 늘어난다. 지금처럼 각 서버의 디스크에 쌓으면 디스크가 차서 서비스가 멈출 위험이 커진다.

### 저장소: S3

모든 원본은 **S3**(파일을 객체 단위로 저장하는 저장소, 사내에서는 S3 호환 스토리지)에 쌓는다. 이유는 네 가지다.

- **늘어나는 데이터를 감당한다.** 용량을 미리 정하지 않고 필요한 만큼 늘릴 수 있다. 서버 디스크 압박에서 벗어난다.
- **비용이 낮다.** 같은 양을 DB에 넣는 것보다 저렴하다.
- **넣는 방식 두 가지를 모두 받는다.** 로그 수집기처럼 데이터를 직접 밀어 넣는 방식(push)은 파일을 S3에 쓰기만 하면 된다. 다른 소스에서 데이터를 가져오는 방식(pull)도 수집 도구가 S3에 쓰면 된다. 들어오는 길이 달라도 도착지는 하나다.
- **원본을 고치지 않는다.** S3에는 파일을 새로 쓰기만 한다. PostgreSQL 같은 DB는 행을 고칠 수 있어서, 원본을 그대로 두어야 하는 브론즈와 맞지 않는다.

### 수집 도구: Airbyte

로그 외의 세 소스는 **Airbyte**로 가져온다. Airbyte는 소스에서 데이터를 읽어 목적지에 쓰는 오픈소스 수집 도구다. 고른 이유는 세 가지다.

- **커넥터가 이미 많다.** 커넥터는 특정 소스를 읽는 부품이다. PostgreSQL처럼 흔한 소스는 오픈소스 커넥터를 그대로 쓴다. 없는 소스는 두 방법으로 만든다. 단순한 HTTP API는 화면에서 설정만으로 만드는 Connector Builder를 쓰고, 복잡한 소스는 Python 개발 도구(CDK)로 만든다.
- **운영자 화면이 있다.** 소스 추가, 일정 설정, 실행 이력 확인, 재실행을 웹 화면에서 한다. 운영자가 코드를 몰라도 된다.
- **추적 정보를 자동으로 붙인다.** 레코드마다 고유 ID, 가져온 시각, 실행 ID를 붙인다. 데이터가 이상할 때 어느 실행에서 왔는지 따라갈 수 있다.

가져오는 도구는 Airbyte 하나로 둔다. 소스가 늘 때마다 도구를 늘리면 운영할 것이 같이 늘기 때문이다.

### 파일 형식은 소스마다 다르게 둔다

소스의 원래 모양이 서로 다르다. 로그는 겹겹이 들어간 JSON이고, 사용자 목록은 CSV이고, DB 행은 타입이 있다. 하나의 형식으로 맞추면 로그를 CSV로 바꿀 때처럼 정보가 사라진다. 그래서 형식은 소스마다 그대로 두고, 대신 "모두 S3에 둔다"와 "경로와 추적 정보 규칙을 지킨다"로 일관성을 맞춘다. 사람이 바로 열어 볼 수 있는 JSONL(한 줄에 JSON 하나)과 CSV를 우선한다. 분석용으로 압축한 형식(Parquet 등)은 실버 이후에 쓴다.

### 이력은 지금부터 쌓는다

사용자 테이블은 매번 전체를 가져와 날짜별로 쌓는다. 5만 건이면 매번 전체를 가져와도 부담이 작다. 사용자가 지워지면 다음 날짜의 기록에 없으므로 삭제도 드러난다. 이력 분석은 나중 요구지만 쌓기는 지금 시작해야 한다. 시작하기 전의 과거는 다시 만들 수 없기 때문이다.

### 이 단계에서 알려진 한계

- Airbyte 오픈소스판에는 레코드를 거르는 기능이 없다. 부서별로 거르는 일은 다음 단계로 넘긴다.
- 코드 호스팅 서버의 CSV는 원래 파일 그대로 받는 것이 이상적이지만, Airbyte가 HTTP 소스에서 파일 그대로 복사하는 기능을 확인하지 못했다. 그래서 레코드로 받고, 원본과 완전히 같지 않을 수 있으므로 모든 열을 문자열로 받는다.

### 갈림길

| 갈림길 | 지금 고른 것 | 대안 | 대안을 고르는 상황 | 상태 |
|---|---|---|---|---|
| 수집 도구 | Airbyte | 스케줄러 안에 직접 짠 수집 코드 | 소스가 더 늘지 않고, Airbyte 운영 작업(업그레이드, 장애)이 정한 한도를 넘을 때 | 한도 미정 |
| 원본 저장소 | S3 | PostgreSQL | 고르지 않는다. 원본을 고칠 수 있게 되고 디스크 압박이 돌아온다 | 결정 |
| 파일 형식 | 소스별 | 하나로 통일 | 고르지 않는다. 통일하면 정보가 사라진다 | 결정 |
| 사용자 테이블 | 매번 전체를 쌓기 | 변경분만 받기(CDC) | 하루 중간의 변경이나 삭제 시점까지 알아야 할 때 | Airbyte 지원 미확인 |

## 2단계: 데이터를 가공한다

### 언제 필요한가

모은 데이터에 업무 규칙을 적용해야 할 때다. 샘플 시스템에서는 부서별 접근 격리와 오래 쓰지 않은 사용자 찾기가 시작된다. 둘 다 브론즈를 그대로 쓸 수 없다. 로그 파일은 잘게 나뉘어 있어 합쳐야 하고, 부서마다 자기 리소스의 로그만 걸러야 한다. 이것은 업무 규칙이므로 수집 도구가 아니라 실버를 만드는 변환에서 한다.

### 변환 엔진: DuckDB와 SQL 파일

변환은 **DuckDB**로 한다. DuckDB는 서버 없이 실행되는 분석용 SQL 엔진이다. 명령 한 줄로 실행하고 끝나면 사라진다. 고른 이유는 세 가지다.

- **켜 둘 서비스가 없다.** 실행할 때만 뜨고 끝나면 종료된다. 운영할 것이 늘지 않는다.
- **S3의 압축 로그를 바로 읽는다.** gzip으로 압축된 JSONL을 풀지 않고 SQL로 읽는다. 모양이 조금씩 다른 파일도 열 이름 기준으로 합쳐 읽는다. 어느 파일에서 온 행인지도 함께 남길 수 있다.
- **SQL만 쓰면 된다.** 변환 로직을 SQL 파일로 두면 코드를 짤 필요가 없다. 코드는 외부 호출이 생기는 3단계부터 필요하다.

필요한 속도는 가장 많은 한 시간 분량(530만 건)을 15분 안에 처리하는 것이다. 초당 약 5,900건이다. 공개된 사례 중 가장 느린 값도 초당 약 4.6만 건이라 충분해 보이지만, 그 사례의 사양을 모르고 이 환경에서 직접 재지 않았다. 그래서 2코어 4GB 컨테이너 하나로 시작하되 실측 전까지는 미확인으로 둔다.

### 스케줄러: 내장 화면부터

변환은 정해진 시각에 돌아야 하고, 운영자가 화면에서 실패를 보고 다시 돌릴 수 있어야 한다. 그래서 스케줄러가 이 단계에서 필요하다. Airbyte에도 일정 기능이 있지만 수집 전용이고, 로그 수집기 경로는 Airbyte 밖에 있어 쓸 수 없다.

처음에는 **배치 앱 하나에 스케줄러 화면을 함께 넣는다.** db-scheduler-ui나 JobRunr 같은 도구는 앱 안에 라이브러리로 들어가 작업 목록, 실행 결과, 재실행 화면을 준다. 별도 서비스가 늘지 않는다. 반면 Dagster나 Airflow 같은 오케스트레이터는 기능이 많지만 웹 서버, 스케줄러, DB 등 켜 둘 서비스가 서너 개 늘어난다. 지금 요구에는 과하다.

두 내장 후보 중 무엇을 쓸지는 작은 작업 하나로 시험한 뒤 정한다. 날짜를 넣어 다시 돌릴 수 있는지, 서버를 다시 켰을 때 놓친 실행을 채우는지는 문서로 확인되지 않았기 때문이다.

### 로직과 스케줄러를 떼어 둔다

변환 로직은 "실행 명령 + SQL 파일"로 두고, 기준일 같은 값은 실행할 때 인자로 넘긴다. 진행 상태는 PostgreSQL에 둔다. 이렇게 하면 나중에 스케줄러를 오케스트레이터로 바꿔도 SQL과 명령은 그대로 쓴다. 3번 규칙(지금 고른 것은 끝까지 쓴다)을 지키는 방법이다.

### 순서는 시간 간격으로 지킨다

스케줄러는 변환만 맡고 수집은 Airbyte가 계속 맡는다. 그래서 "수집이 끝나야 변환이 시작된다"는 순서를 스케줄러가 보장하지 않는다. 대신 변환을 수집보다 충분히 늦게 돌리고, 입력이 없으면 빈 결과를 만들지 않고 실패하게 한다. 조용히 빈 결과를 만드는 것보다 실패가 눈에 띄는 편이 안전하다.

### 부서별 격리는 복사본으로 시작한다

부서마다 자기 데이터만 담은 복사본을 실버의 별도 경로에 만들고, S3의 경로 권한으로 다른 부서가 못 읽게 막는다. 부서 수가 적을 때는 가장 단순한 방법이다. 다만 사내 S3가 경로 단위 권한을 지원하는지는 아직 확인하지 않았다.

### 갈림길

| 갈림길 | 지금 고른 것 | 대안 | 대안을 고르는 상황 | 상태 |
|---|---|---|---|---|
| 스케줄러 | 앱 안의 내장 화면 | Dagster, Airflow | 날짜 구간을 한 번에 다시 돌리기, 작업 간 순서 의존, 놓친 실행 채우기 중 하나가 필요할 때 | 시험 전 |
| SQL 관리 | SQL 파일 | dbt | SQL 모델이 많아지거나, 운영자가 PR로 SQL을 고치기 시작할 때 | 결정 |
| 처리 규모 | 컨테이너 1개 | 사양 올리기 → 나눠 돌리기 → 분산 엔진 | 한 시간 분량이 15분을 넘을 때. 앞의 방법으로 안 풀릴 때만 다음으로 | 실측 전 |
| 부서별 격리 | 부서별 복사본 + 경로 권한 | 조회할 때 권한으로 거르기 | 부서가 많아져 복사 비용이 정책 관리 비용보다 커질 때 | 경로 권한 미확인 |

**dbt**는 SQL 변환을 모델 단위로 관리하는 도구다. 모델 간 의존을 자동으로 풀고, 데이터 테스트와 계보 문서를 만들어 주고, 엔진을 바꿀 때 어댑터만 바꾸면 된다. 운영자가 SQL을 고치기 시작하면 이 테스트가 안전망이 된다. 지금은 모델이 몇 개뿐이라 미룬다.

## 3단계: 결과를 밖으로 보낸다

### 언제 필요한가

분석 결과로 바깥에 행동을 해야 할 때다. 샘플 시스템에서는 오래 쓰지 않은 사용자에게 안내 메일을 보내고, 유예 기간이 지나면 처리한다. 대상은 2단계에서 찾았다. 이제 그 결과를 외부 메일 API로 보내야 한다.

### 활성화는 변환과 다르다

분석 결과를 외부 시스템으로 내보내는 일을 **활성화**(또는 리버스 ETL)라고 부른다. 변환은 데이터를 읽고 다른 데이터를 만든다. 실패하면 다시 돌리면 된다. 활성화는 바깥에 영향을 남긴다. 메일은 한 번 나가면 되돌릴 수 없다. 성격이 달라서 따로 다룬다.

그래서 일을 둘로 나눈다. 누구에게 보낼지는 2단계의 SQL이 고르고, 결과를 PostgreSQL의 대기 표에 넣는다. 실제 발송은 워커가 대기 표에서 한 건씩 꺼내 보낸다. 대기 표가 두 일의 경계다.

### 대기 표는 PostgreSQL에 둔다

대기 표의 각 행은 "대기 → 발송 중 → 완료 또는 실패"로 상태가 바뀐다. 상태를 바꾸려면 행을 고치고, 두 워커가 같은 행을 동시에 잡지 않게 잠가야 한다. PostgreSQL은 행 잠금으로 이것을 한다. S3의 파일은 고치거나 잠글 수 없으므로 대기 표에 맞지 않는다. 발송 결과의 기록은 고칠 일이 없으므로 S3에 추가만 한다.

### 중복 발송을 막는 방법

워커가 메일 API를 부른 직후, 결과를 저장하기 전에 멈추면 그 건은 다시 발송될 수 있다. 이것을 막기 위해 건마다 요청 ID(사용자, 안내 종류, 회차)를 만들어 API에 함께 보낸다. API가 같은 ID를 한 번만 처리해 주면 중복이 생기지 않는다. 메일 API가 이것을 지원하는지는 아직 확인하지 않았다. 지원하지 않으면 드문 중복 발송은 받아들이기로 했다.

추가 안전장치도 둔다. 대상 수가 정한 기준을 넘으면 발송을 멈추고 사람이 승인한다. 보내기 직전에 대상이 여전히 조건에 맞는지 다시 확인한다.

### 워커: Spring Batch

워커는 **Spring Batch**로 만든다. Spring Batch는 많은 건을 묶음 단위로 처리하는 Java 프레임워크다. 실패한 건만 다시 시도하기, 문제 있는 건 건너뛰기, 멈춘 지점부터 다시 시작하기를 이미 제공한다. 메일 발송은 건마다 실패할 수 있어 이 기능이 그대로 필요하다. 직접 만들면 만든 사람이 계속 고쳐야 하므로 검증된 도구를 쓴다. 개발자에게 익숙하지 않다는 점은 배우는 비용이지 직접 만들 이유는 아니다.

Spring Batch는 변환에는 쓰지 않는다. 변환은 SQL을 한 번 실행하는 일이라 건 단위 재시도가 필요 없다.

### 갈림길

| 갈림길 | 지금 고른 것 | 대안 | 대안을 고르는 상황 | 상태 |
|---|---|---|---|---|
| 워커 | Spring Batch | 직접 구현 | 고르지 않는다. 재시도와 재시작을 직접 만들면 유지보수가 커진다 | 재실행 시험 전 |
| 대기 표 | PostgreSQL | Kafka 등 메시지 큐 | 데이터가 도착하자마자 반응해야 하거나, 같은 결과를 여러 곳이 받아야 하거나, 워커를 늘려도 대기 표 처리가 밀리고 원인이 DB일 때 | 지금은 요구 없음 |
| 중복 방지 | 요청 ID | 중복 허용 | 메일 API가 요청 ID를 지원하지 않을 때 | 미확인 |
| Spring Batch 사용 범위 | 건마다 외부 호출하고 실패분만 다시 보내는 곳 | 일반 실행 | 하루 한 번 요약 알림, 파일 내보내기, 하루 몇 건 등록처럼 실패하면 통째로 다시 하면 되는 곳 | 가정 |

## 4단계: 사용자에게 보여 준다

### 언제 필요한가

운영자가 아닌 최종 사용자가 결과를 직접 봐야 할 때다. 샘플 시스템에서는 최종 사용자가 자기 팀과 프로젝트의 지표를 직접 본다. 관리자는 어떤 지표를 보여 줄지 정하고, 사용자는 정해진 화면을 본다. 사용자는 권한이 있는 데이터만 보고, 권한이 없으면 기본적으로 거부된다.

### 처음에는 집계 표와 조회 앱

정해진 지표만 보여 준다면 미리 계산해 둔 집계 표(골드)와, 그 표를 권한에 맞춰 읽어 주는 **조회 앱**이면 충분하다. 아무 SQL이나 받는 서비스를 만들 필요가 없다. 조회 앱은 계속 켜 두는 서비스이므로 이 단계에서 서비스가 하나 늘어난다. 조회 앱이 집계 표를 어디서 어떻게 읽을지(S3 직접, PostgreSQL 집계 표, Trino)는 아직 정하지 않았다.

### Trino는 SQL을 서비스로 열 때

**Trino**는 여러 사용자가 동시에 SQL을 실행할 수 있는 분산 SQL 서버다. 사용자별 권한, 행 단위 필터, 열 가리기를 서버에서 적용할 수 있다. 관리자나 사용자가 직접 SQL을 쓰고, 여럿이 동시에 쓰거나 쿼리를 공유하고, 권한을 서버에서 강제해야 할 때 들인다. 그 전에는 신뢰하는 운영자가 DuckDB와 DBeaver 같은 개인 도구로 직접 조회한다. 이 방법은 S3 접근 키가 필요하므로 신뢰하는 사람에게만 허용한다.

### Iceberg는 읽는 쪽이 생길 때

**Iceberg**는 S3의 파일 묶음을 DB의 표처럼 다루게 해 주는 표 형식이다. 행 단위 수정과 삭제, 표 통째 교체, 과거 시점 조회를 지원한다. 사용자가 실버와 골드를 읽기 시작하면, 읽는 도중에 파일을 바꾸는 일이 위험해진다. 그때 Iceberg로 바꾼다. 그 전에는 일반 파일로 충분하다.

Iceberg는 형식이지 서비스가 아니지만, 표 목록을 관리하는 **카탈로그**가 필요하다. 카탈로그 종류에 따라 DuckDB와 Trino가 함께 쓸 수 있는지가 달라지는데, 이 조합은 아직 확인하지 않았다. 또 작은 파일 합치기, 오래된 스냅샷 지우기 같은 정비 작업을 정기적으로 돌려야 한다.

### 오케스트레이터

2단계의 교체 조건(날짜 구간 재실행, 작업 순서 의존, 놓친 실행 채우기)이 생기면 스케줄러를 Dagster나 Airflow로 바꾼다. Dagster는 Airbyte 연결과 dbt 모델을 그대로 불러와 한 화면에서 관리할 수 있다. 로직은 이미 스케줄러와 떨어져 있으므로 바꿔도 SQL은 그대로다.

### 갈림길

| 갈림길 | 지금 고른 것 | 대안 | 대안을 고르는 상황 | 상태 |
|---|---|---|---|---|
| 사용자 서빙 | 집계 표 + 조회 앱 | Trino | SQL 분석을 서비스로 열어야 할 때(동시 사용, 서버 권한, 쿼리 공유) | 읽는 방식 미정 |
| 표 형식 | 일반 파일 | Iceberg | 읽는 쪽이 생긴 뒤 표 교체, 행 수정, 증분 병합이 필요할 때 | 카탈로그 호환 미확인 |
| 부서별 격리 | 복사본 | Trino 행 필터 | 팀과 프로젝트 단위처럼 격리 단위가 많아질 때 | 정책 서버 필요 여부 미확인 |
| 스케줄러 | 내장 화면 | Dagster, Airflow | 2단계의 교체 조건과 같다 | 시험 전 |

## 완성 기준

4단계까지 오면 수집, 가공, 내보내기, 보여 주기가 모두 갖춰진다. 이후 위 여섯 요구는 워크로드나 서비스를 더하지 않고 받는다. 새 분석은 SQL 모델 추가로, 새 소스는 Airbyte 커넥터 추가로, 새 지표는 집계 표 추가로 받기 때문이다.

예외는 둘이다. 데이터가 도착하는 즉시 반응해야 하는 요구는 메시지 큐가 필요하다. 그래프와 표로 탐색하는 BI 대시보드는 별도 도구가 필요하다. 둘 다 지금은 요구가 없어 범위 밖 후보로 둔다.

## 아직 확인하지 않은 것

아래 여섯이 확인되기 전에는 관련 선택을 확정하지 않는다.

1. DuckDB 컨테이너 하나가 가장 많은 한 시간 분량을 15분 안에 처리하는지
2. Iceberg 카탈로그를 DuckDB와 Trino가 함께 쓸 수 있는지
3. 내장 스케줄러가 날짜를 넣어 다시 돌리고, 재기동 때 놓친 실행을 채우는지
4. Spring Batch가 같은 값으로 작업을 다시 실행할 수 있는지
5. 사내 S3가 경로 단위 접근 권한을 지원하는지
6. 메일 API가 요청 ID로 중복을 막는지, 호출 한도는 얼마인지
