# 워크로드를 한 칸씩 더해 데이터 분석 서브시스템을 완성하기

> 이 글은 읽기용이다. 판단 근거와 검증 기록은 [transform-layer.md](transform-layer.md)에 있다.

## 이 글이 다루는 것

서비스를 운영하다 보면 데이터로 답해야 하는 질문이 생긴다. 사용자는 얼마나 늘고 있는가. 오래 쓰지 않은 계정은 누구이고, 언제 정리해야 하는가. 각 부서는 자기 데이터만 보고 있는가. 이런 질문에 답하고, 그 답으로 계정 정리나 접근 제한 같은 정책을 실행하려면 데이터 분석이 필요하다. 특별한 시스템만의 이야기가 아니다. 사용자가 있는 시스템이라면 대부분 겪는다.

그런데 필요한 기술과 범위는 시스템마다 다르다. 데이터가 적고 개발자가 직접 운영하는 시스템은 DB에 쿼리 하나를 날리는 것으로 충분하다. 데이터가 서버 디스크를 압박할 만큼 늘고, 개발하는 사람과 운영하는 사람이 나뉘면 이야기가 달라진다. 별도 저장소, 수집 도구, 실행 일정을 관리할 스케줄러, 운영자가 쓸 화면이 필요해진다. 처음부터 큰 구성을 들이면 쓰지 않는 서비스를 운영하느라 비용이 든다. 반대로 지금 편한 도구로 시작했다가 나중에 버리면 같은 일을 두 번 한다.

이 글은 하나의 샘플 시스템을 예로 들어, 시스템이 커지는 단계마다 어떤 도구와 구성이 필요한지 알아본다. 단계마다 왜 그 기술을 골랐는지, 어떤 상황이 오면 다른 기술로 바꾸는지를 함께 적는다. 상황이 다르면 답도 다르므로, 대안은 그 대안이 맞는 상황과 함께 읽어야 의미가 있다. 마지막 단계의 구성은 워크로드나 서비스를 더 늘리지 않고 대부분의 분석 요구를 받는다.

자기 시스템에 적용하려면 아래 표에서 지금 어느 단계에 있는지 먼저 찾고, 그 단계의 갈림길 표에 적힌 조건을 자기 상황과 비교하면 된다.

| 단계 | 이 단계가 필요해지는 때 | 더하는 것 |
|---|---|---|
| 1. 수집 | 데이터가 여러 곳에 흩어져 있고, 서버 디스크로 감당하기 어려울 만큼 늘어날 때 | S3 저장소, Airbyte 수집 도구 |
| 2. 변환 | 모은 데이터에 부서별 필터나 휴면 판정 같은 업무 규칙을 적용해야 할 때 | DuckDB 변환, 스케줄러가 든 배치 앱 |
| 3. 사용: 내보내기 | 분석 결과로 메일 발송 같은 바깥 행동을 해야 할 때 | 대기 표, Spring Batch 워커 |
| 4. 사용: 분석 조회 | 운영자 외에 최종 사용자가 직접 결과를 봐야 할 때 | 조회 앱(조건이 생기면 Trino, Iceberg, 오케스트레이터) |

## 기본 개념: 메달리온 구조

이 글은 모던 데이터 아키텍처의 흔한 방식인 **메달리온 구조(Medallion Architecture)**를 따른다. 데이터를 세 층으로 나눠 쌓는 방식이다.

- **브론즈(Bronze):** 소스에서 받은 원본을 그대로 둔다. 고치지 않는다. 나중에 가공 규칙이 틀린 것을 알았을 때 원본에서 다시 만들 수 있어야 하기 때문이다.
- **실버(Silver):** 브론즈를 합치고 거르고 정리한 데이터다. 업무 규칙은 여기서 적용한다.
- **골드(Gold):** 실버를 집계해 바로 보여 줄 수 있게 만든 데이터다.

층을 나누면 각 층의 책임이 분명해진다. 수집 도구는 브론즈까지만 책임지고, 업무 규칙은 실버 이후에서만 다룬다.

## 기본 개념: 모던 데이터 아키텍처

메달리온 구조가 "데이터를 어떻게 쌓는가"라면, 모던 데이터 아키텍처(Modern Data Architecture)는 "데이터가 어떤 흐름을 거쳐 쓰이는가"를 레이어로 나눈 것이다. 레이어마다 하는 일이 다르므로 도구도 따로 고른다. 이 글의 단계는 이 레이어를 하나씩 채워 가는 과정이다.

흐름을 따라 데이터가 지나가는 레이어는 넷이다.

1. **수집(Ingestion):** 소스에서 데이터를 읽어 저장소로 옮긴다. 가공하지 않는다. → 1단계, Airbyte와 로그 수집기
2. **저장(Storage):** 원본과 가공 결과를 오래, 싸게 보관한다. 메달리온의 세 층이 여기에 있다. → 1단계 S3, 4단계 Iceberg
3. **변환(Transformation):** 브론즈를 합치고 걸러 실버와 골드를 만든다. 업무 규칙이 여기에 있다. → 2단계, DuckDB와 SQL(나중에 dbt)
4. **사용(Uses, Serving):** 가공한 결과를 쓰는 곳으로 넘긴다. 쓰는 방식에 따라 둘로 나뉜다.
   1. **분석 조회(Analytics):** 사람이나 앱이 결과를 읽는다. 대시보드, 지표 화면, SQL 조회가 여기에 속한다. → 4단계, 조회 앱과 Trino
   2. **내보내기(Reverse ETL):** 결과를 외부 시스템으로 내보내 행동으로 바꾼다. 메일 발송, 외부 도구에 데이터 넣기가 여기에 속한다. → 3단계, Spring Batch 워커

흐름에 끼지 않고 모든 레이어에 걸치는 일도 둘 있다.

- **오케스트레이션(Orchestration):** 각 레이어의 작업을 정해진 때와 순서로 돌리고, 실패를 보여 주고, 다시 돌린다. → 2단계 내장 스케줄러, 4단계 Dagster나 Airflow
- **거버넌스(Data Governance):** 데이터를 믿고 쓸 수 있게 규칙을 정하고 지킨다. 어디서 왔는지(계보), 어떤 표가 있는지(카탈로그), 값이 맞는지(품질), 얼마나 보관하는지(보존), 누가 볼 수 있는지(접근 권한)를 다룬다. → 1단계 Airbyte 추적 정보, 2단계 경로 권한과 dbt 테스트, 4단계 Iceberg 카탈로그와 행 단위 권한

보안(Security)은 거버넌스와 따로 부르기도 한다. 암호화, 네트워크, 계정 관리까지 넓게 다룰 때다. 이 글에서 다루는 보안은 "누가 어떤 데이터를 볼 수 있는가" 하나뿐이고, 이것은 거버넌스가 정하는 규칙이므로 함께 묶는다.

## 샘플 시스템

샘플 시스템은 개발 조직이 쓰는 플랫폼이다. 데이터는 서버 디스크로 감당하기 어려울 만큼 많고, 개발하는 사람과 운영하는 사람이 나뉘어 있다. 앞에서 말한 "이야기가 달라지는" 규모다. 선택의 이유를 구체적으로 따지기 위해 숫자까지 정해 둔다.

**데이터 소스는 네 가지다.**

- **로그:** 서버마다 사용자 활동 로그가 쌓인다. 주 4.2억 건, 가장 많은 시간에는 시간당 530만 건이다. 지금은 각 서버의 디스크에 쌓이고, 로그 수집기(서버의 로그를 모아 다른 곳으로 보내는 에이전트)가 이미 설치되어 있다.
- **코드 리뷰 시스템:** API로 레코드를 준다.
- **코드 호스팅 서버:** 사용자 목록을 CSV 파일로 준다.
- **사용자 DB:** PostgreSQL에 있는 사용자 테이블이다. 약 5만 건으로 예상한다.

로그 외의 데이터는 각 시스템 안에만 있다. 분석하려면 시스템마다 따로 조회해야 한다.

**사람은 둘로 나뉜다.** 개발자가 파이프라인을 만들고, 운영자가 구성과 운영과 분석을 맡는다. 운영자는 코드를 쓰지 않으므로 웹 화면에서 설정을 바꾸고, 실행 상태를 보고, 실패한 작업을 다시 돌릴 수 있어야 한다.

**요구는 아홉 가지다.** 앞의 데이터 아키텍처 레이어로 나누면 어느 단계에서 무엇을 풀어야 하는지 보인다. 흐름 레이어의 요구는 그 레이어를 채우는 단계에서 풀고, 모든 레이어에 걸치는 요구는 단계마다 조금씩 풀린다.

| 레이어 | 요구 | 왜 필요한가 |
|---|---|---|
| 수집 | 흩어진 시스템의 데이터를 한곳으로 가져온다 | 사용자 테이블과 활동 로그를 함께 봐야 분석할 수 있다 |
| 저장 | 늘어나는 데이터를 원본 그대로 보관한다 | 서버 디스크로는 감당이 안 되고, 가공 규칙이 틀렸을 때 원본에서 다시 만들어야 한다 |
| 저장 | 사용자 테이블을 주기마다 쌓아 이력을 남긴다 | 쌓기 전의 과거는 다시 만들 수 없다 |
| 변환 | 오래 쓰지 않은 사용자를 찾는다 | 이미 하고 있는 업무다 |
| 변환 | 이력으로 사용자 추이를 비교한다 | 기준일을 바꿔 가며 비교하고 예측해야 한다 |
| 사용: 내보내기 | 찾은 사용자에게 안내 메일을 보내고, 유예 뒤 처리한다 | 찾기, 안내, 유예, 처리 순서로 진행하는 업무다 |
| 사용: 분석 조회 | 최종 사용자에게 분석 결과를 보여 준다 | 사용자가 자기 권한 범위의 지표를 직접 봐야 한다 |
| 오케스트레이션 | 운영자가 웹 화면으로 실행 상태를 보고 다시 돌린다 | 운영자와 개발자가 다른 사람이다 |
| 거버넌스 | 부서별로 데이터 접근을 나눈다 | 부서는 자기 리소스의 데이터만 봐야 한다 |

## 선택 규칙

모든 단계에서 같은 규칙으로 고른다.

1. **필요가 생겼을 때만 더한다.** 미리 만든 서비스는 쓰이기 전까지 비용만 든다.
2. **검증된 도구가 있으면 직접 만들지 않는다.** 직접 만든 것은 만든 사람이 계속 고쳐야 한다.
3. **지금 고른 것은 끝 구성에서도 쓰여야 한다.** 버릴 임시 구현은 만들지 않는다.
4. **확인하지 못한 것은 확정하지 않는다.** 확인 전까지는 "미확인"으로 표시하고 시험할 항목으로 남긴다.

## 1단계 수집: 데이터를 모은다

### 언제 필요한가

두 문제 중 하나가 생기면 이 단계가 필요하다.

- **분석 문제:** 데이터가 여러 시스템에 흩어져 있어 함께 볼 수 없다. 사용자 테이블과 활동 로그를 같이 봐야 오래 쓰지 않은 사용자를 찾을 수 있다.
- **저장 문제:** 데이터가 서버 디스크로 감당하기 어려울 만큼 늘어난다. 디스크가 차면 서비스가 멈춘다.

샘플 시스템은 둘 다 겪는다. 그래서 이 단계는 "모을 곳"과 "모으는 방법"을 함께 정한다.

### 저장소: S3

모든 원본은 **S3**에 쌓는다. S3는 파일을 객체 단위로 저장하는 저장소다. AWS의 서비스 이름이지만 같은 방식으로 동작하는 사내 저장소(S3 호환 스토리지)도 많아, 사실상 표준 방식이 되었다.

후보는 셋이었다. 서버 디스크를 늘리기, DB에 넣기, S3에 넣기다.

- **서버 디스크를 늘리면** 흩어진 문제가 그대로 남는다. 서버가 늘 때마다 디스크도 따로 늘려야 한다.
- **DB에 넣으면** 한곳에 모이지만, 같은 용량을 두는 비용이 높다. 로그처럼 계속 쌓이기만 하는 데이터에는 DB의 수정·검색 기능이 대부분 필요 없다. 그 기능에 비용을 내는 셈이다.
- **S3에 넣으면** 두 문제가 함께 풀린다. 용량을 미리 정하지 않고 필요한 만큼 늘리고, 모든 데이터가 한곳에 모인다.

S3를 고른 이유가 하나 더 있다. 데이터가 들어오는 길이 둘인데 S3는 둘 다 받는다. 로그 수집기처럼 데이터를 직접 밀어 넣는 방식(push)은 파일을 S3에 쓰기만 하면 된다. 다른 시스템에서 데이터를 가져오는 방식(pull)도 수집 도구가 S3에 쓰면 된다. 뒤 단계에서 쓰는 DuckDB, Trino, Iceberg도 모두 S3를 바로 읽는다. 들어오는 길과 읽는 쪽이 모두 S3를 중심으로 모인다.

주의할 점이 있다. S3도 파일을 덮어쓰거나 지울 수 있다. S3에 넣는다고 원본이 저절로 지켜지지는 않는다. 그래서 브론즈 경로에는 수집 도구만 쓰게 하고, 쓸 때는 항상 새 파일로 쓰게 한다. DB는 행을 고치는 것이 기본 동작이라 이 규칙을 지키기 더 어렵다. 사내 저장소가 버전 관리나 삭제 잠금을 지원하는지는 아직 확인하지 않았다.

### 수집 도구: 로그는 기존 경로, 나머지는 Airbyte

로그는 로그 수집기가 이미 서버마다 설치되어 있으므로, 보낼 곳만 S3로 바꾼다. 새 도구가 필요 없다.

나머지 세 소스는 누군가 가서 가져와야 한다(pull). 이 일은 **Airbyte**로 한다. Airbyte는 소스에서 데이터를 읽어 목적지에 쓰는 오픈소스 수집 도구다. 고른 이유는 세 가지다.

- **소스를 늘리기 쉽다.** 커넥터는 특정 소스를 읽는 부품이다. PostgreSQL처럼 흔한 소스는 오픈소스 커넥터를 그대로 쓴다. 커넥터가 없는 소스는 두 방법으로 만든다. 단순한 HTTP API는 화면에서 설정만 해서 만드는 Connector Builder를 쓰고, 복잡한 소스는 Python 개발 도구(CDK)로 만든다. 어느 쪽이든 만든 뒤에는 다른 커넥터와 똑같이 운영한다.
- **운영자 화면이 있다.** 소스 추가, 실행 일정, 실행 이력, 재실행을 웹 화면에서 한다. 코드를 쓰지 않는 운영자도 수집을 직접 운영할 수 있다.
- **추적 정보를 자동으로 붙인다.** 레코드마다 고유 ID, 가져온 시각, 실행 ID를 붙인다. 데이터가 이상할 때 어느 실행에서 왔는지 따라가 그 부분만 다시 가져올 수 있다.

대가도 있다. Airbyte는 여러 서비스로 이루어져 이 글에 나오는 도구 중 운영이 가장 무겁다. 게다가 샘플 시스템에서 기존 커넥터를 그대로 쓰는 소스는 PostgreSQL 하나뿐이고, 나머지 둘은 직접 만든다. 지금 소스만 보면 장점이 크지 않다. 그래도 고르는 이유는 운영자 화면이 첫날부터 필요하고, 앞으로 소스가 늘 때마다 도구를 늘리지 않기 위해서다. 가져오는 도구는 Airbyte 하나로 정한다. 소스가 더 늘지 않는다면 이 판단은 다시 본다(아래 갈림길).

### 파일 형식은 소스마다 다르게 둔다

브론즈에는 원본을 둔다. 형식을 하나로 맞추려면 어느 소스든 변환을 거쳐야 하고, 변환하는 순간 그것은 원본이 아니다. 예를 들어 로그는 겹겹이 들어간 JSON이라 CSV로 바꾸면 구조가 사라진다. 반대로 모두 JSONL로 맞추면 DB 행의 숫자와 날짜가 문자열로 바뀐다. 그래서 형식은 소스의 원래 모양을 따르고, 일관성은 "모두 S3에 둔다"와 "경로와 추적 정보 규칙을 지킨다"로 맞춘다.

| 소스 | 브론즈에 남는 것 | 추적 정보 |
|---|---|---|
| 로그 | 수집기가 보낸 압축 JSONL 파일 그대로 | 파일 경로와 객체 정보(방식 미정) |
| 코드 리뷰 시스템 | Airbyte가 받은 레코드(JSONL) | Airbyte가 붙인 열 |
| 코드 호스팅 서버 | 원래 CSV 파일이 이상적이나, 지금은 레코드(JSONL) | Airbyte가 붙인 열 |
| 사용자 DB | Airbyte가 받은 행 | Airbyte가 붙인 열 |

사람이 바로 열어 볼 수 있는 JSONL(한 줄에 JSON 하나)과 CSV를 우선한다. 분석용으로 압축한 형식(Parquet 등)은 실버 이후에 쓴다. 사용자 DB의 행을 어떤 형식으로 받을지, 그때 타입을 어떻게 지킬지는 아직 정하지 않았다.

### 이력은 지금부터 쌓는다

사용자 테이블은 정해진 주기(일 또는 시간)마다 전체를 가져와 쌓는다. 5만 건이면 매번 전체를 가져와도 부담이 작다. 사용자가 지워지면 다음 기록에 없으므로 삭제도 드러난다. 이력 분석은 나중 요구지만 쌓기는 지금 시작해야 한다. 시작하기 전의 과거는 다시 만들 수 없기 때문이다. 오래 쓰지 않은 사용자를 찾으려면 이 이력과 함께 로그의 활동 기록이 필요하다. 둘 다 이 단계부터 쌓인다.

### 이 단계에서 남는 빈칸

- **부서별로 거르기:** Airbyte 오픈소스판에는 레코드를 거르는 기능이 없다. 거르기는 업무 규칙이기도 해서 다음 단계의 변환에서 한다.
- **원본 보존의 예외:** 코드 호스팅 서버의 CSV는 원래 파일 그대로 받아야 원칙에 맞다. 그러나 Airbyte가 HTTP 소스에서 파일을 그대로 복사하는 기능을 확인하지 못해 레코드로 받는다. 원본과 완전히 같지 않을 수 있으므로 모든 열을 문자열로 받아 손실을 줄인다. 원칙을 어긴 것을 알고 받아들인 예외다.
- **로그 경로의 추적 정보와 운영 화면:** 로그는 Airbyte를 거치지 않으므로 Airbyte의 추적 정보와 화면을 쓸 수 없다. 원본 파일을 고치지 않고 추적 정보를 붙이려면 파일 경로나 객체 정보에 넣어야 하는데, 방식은 아직 정하지 않았다. 로그 경로를 운영자가 어떤 화면으로 볼지도 정하지 않았다.

### 갈림길

| 갈림길 | 지금 고른 것 | 대안 | 대안을 고르는 상황 | 상태 |
|---|---|---|---|---|
| 저장소 | S3 | 서버 디스크, DB | 고르지 않는다. 서버 디스크는 흩어진 문제가, DB는 비용과 원본 수정 위험이 남는다 | 결정 |
| 가져오는 도구 | Airbyte | 스케줄러 안에 직접 짠 수집 코드 | 소스가 더 늘지 않고, Airbyte 운영 작업(업그레이드, 장애)이 정한 한도를 넘을 때 | 한도 미정 |
| 파일 형식 | 소스별 | 하나로 통일 | 고르지 않는다. 통일하면 변환을 거쳐 원본이 아니게 된다 | 결정 |
| 사용자 테이블 | 주기마다 전체를 쌓기 | 변경분만 받기(CDC) | 주기 사이의 변경이나 삭제 시점까지 알아야 할 때 | Airbyte 지원 미확인 |

## 2단계 변환: 데이터를 가공한다

### 언제 필요한가

수집한 브론즈는 가공 전 원본이다. 업무에 쓰려면 먼저 실버로 정제하고, 정제된 데이터 위에 업무 규칙을 적용해야 한다. 이 변환은 밀어 넣는 길(로그)과 가져오는 길(Airbyte) 두 경로 모두에 필요하다.

### 변환이 하는 일

요구마다 변환이 하는 일은 이렇다.

- **정제:** 로그는 S3에 쌓일 때 시간이나 크기 단위로 잘려 작은 파일로 나뉜다. 작은 파일이 많으면 읽기가 느려지므로, 한 시간 단위로 합친다. 가져온 데이터는 기준 시각을 붙여 정리한다.
- **오래 쓰지 않은 사용자 찾기:** 사용자 테이블과 활동 로그를 합쳐 마지막 활동 시점을 계산하고 대상 목록을 만든다. 이 목록이 3단계 메일 발송의 입력이 된다.
- **이력:** 주기마다 받은 사용자 테이블을 기준 시각별로 실버에 쌓는다. 추이 비교는 이 실버를 조회해서 한다.
- **부서별 격리:** 부서별 리소스 목록으로 로그를 걸러 부서 경로에 복사본을 만든다. 이 단계에는 행 단위 권한을 걸 엔진이 없고 S3 권한은 경로 단위뿐이기 때문이다. 리소스 목록은 PostgreSQL 표에 두어, 바뀌어도 SQL을 고치지 않게 한다.

### 로직과 엔진: SQL과 DuckDB

위의 일은 모두 합치고, 거르고, 세는 일이라 SQL로 충분하다. 그래서 로직은 SQL 파일에 둔다.

엔진은 네 조건을 만족해야 한다. 켜 둘 서버가 없어야 하고, Java 앱 안에 넣을 수 있어야 하고, S3의 gzip 압축 JSONL을 바로 읽어야 하고, 나중에 dbt와 Iceberg로 이어져야 한다. 이 조건을 모두 만족하는 **DuckDB**를 쓴다. DuckDB는 별도 서버 없이 라이브러리로 돌아가는 분석용 SQL 엔진이다.

처리 기준은 가장 많은 한 시간 분량(530만 건)을 15분 안에 끝내는 것이다. 아직 실측하지 않았으므로 작은 사양(2코어, 4GB)으로 시작한다.

### 실행: 경량 Java 앱

변환은 정해진 시각에 두 경로 모두를 대상으로 돌아야 하고, 운영자가 화면에서 실패를 보고 다시 돌려야 한다. Airbyte의 일정 기능은 가져오는 경로만 다루므로 쓸 수 없다. 그래서 스케줄러가 필요하다.

스케줄러는 경량 Java 앱 하나로 둔다. 앱 안에 스케줄러 화면(db-scheduler-ui 또는 JobRunr)과 DuckDB를 함께 넣는다. 새로 켜 두는 서비스는 이 하나다. Dagster나 Airflow는 서비스가 서너 개 늘어서 지금은 과하다. 앱은 SQL을 실행만 하므로, 나중에 스케줄러를 바꿔도 SQL은 남는다. DuckDB는 기본으로 장비 메모리의 80%까지 쓰므로, 앱과 메모리를 나눠 쓰도록 한도를 정해 둔다.

규모가 커지면 먼저 사양을 올린다. 그래도 부족하면 같은 SQL을 시간대나 부서별로 입력 범위만 나눠 별도 컨테이너에서 동시에 돌린다. 나눠 돌린 실행끼리는 데이터를 주고받지 않는다. 그래서 전 기간에 걸친 집계는 부분 결과를 다시 합쳐야 한다. 이것으로도 안 될 때만 분산 엔진으로 바꾼다.

스케줄러는 수집이 끝났는지 모른다. 그래서 변환을 충분히 늦게 돌리고, 입력이 없으면 실패하게 한다.

### 갈림길

| 갈림길 | 지금 고른 것 | 대안 | 대안을 고르는 상황 | 상태 |
|---|---|---|---|---|
| 처리 규모 | 앱 안의 DuckDB(2코어, 4GB) | 사양 올리기 → 별도 컨테이너로 나눠 돌리기 → 분산 엔진 | 한 시간 분량이 15분을 넘을 때, 이 순서로 | 실측 전 |
| 스케줄러 | 앱 안의 내장 화면 | Dagster, Airflow | 날짜 구간 재실행, 작업 순서 의존, 놓친 실행 채우기가 필요할 때 | 시험 전 |
| SQL 관리 | SQL 파일 | dbt | 모델이 늘거나 운영자가 PR로 SQL을 고칠 때 | 결정 |
| 부서별 격리 | 복사본 + 경로 권한 | 조회할 때 권한으로 거르기 | 복사 비용이 정책 관리 비용보다 커질 때 | 경로 권한 미확인 |

## 3단계 사용(내보내기): 결과를 밖으로 보낸다

### 언제 필요한가

분석 결과로 바깥에 행동을 해야 할 때다. 샘플 시스템에서는 오래 쓰지 않은 사용자에게 안내 메일을 보내고, 유예 기간이 지나도 쓰지 않으면 휴면 처리한다. 대상은 2단계에서 찾았다. 이제 그 결과를 외부 메일 API와 처리 API로 보내야 한다.

이 단계는 새로 켜 두는 서비스 없이 2단계 앱에 기능을 더한다.

### 내보내기는 변환과 다르다

분석 결과를 외부 시스템으로 내보내는 일을 **리버스 ETL(Reverse ETL)**이라고 부른다. 보통의 ETL이 소스에서 데이터를 가져와 저장소에 넣는다면, 리버스 ETL은 반대로 저장소의 결과를 바깥 시스템으로 보낸다. 변환은 데이터를 읽고 다른 데이터를 만든다. 실패하면 다시 돌리면 된다. 내보내기는 바깥에 영향을 남긴다. 메일은 한 번 나가면 되돌릴 수 없다. 성격이 달라서 따로 다룬다.

그래서 일을 둘로 나눈다. 누구에게 보낼지는 2단계의 SQL이 고르고, 결과를 PostgreSQL의 대기 표에 넣는다. 실제 발송은 워커가 대기 표에서 한 건씩 꺼내 보낸다. 대기 표가 두 일의 경계다.

### 대기 표는 PostgreSQL에 둔다

대기 표의 각 행은 "대기 → 발송 중 → 완료 또는 실패"로 상태가 바뀐다. 상태를 바꾸려면 행을 고치고, 두 워커가 같은 행을 동시에 잡지 않게 잠가야 한다. PostgreSQL은 행 잠금으로 이것을 한다. S3는 파일 단위로만 쓰고 지우므로, 행 하나의 상태를 바꾸거나 잠글 수 없다.

각 행은 요청 ID로 구분한다. 요청 ID는 사용자, 안내 종류(안내 메일 또는 처리), 회차를 묶은 값이다. 회차는 같은 사용자가 나중에 다시 대상이 될 때 이전 건과 구분하려고 둔다.

발송 결과는 S3에도 추가만 한다. 누구에게 언제 무엇을 보냈는지는 나중에 분석하고 확인할 기록이고, 고칠 일이 없기 때문이다.

### 대상을 대기 표에 넣는 방법

DuckDB는 PostgreSQL 확장으로 PostgreSQL 표에 바로 쓸 수 있다. 그래서 대상을 고르는 SQL이 결과를 대기 표에 바로 넣는다. 고르기와 넣기가 SQL 하나에 있어 로직이 SQL에 남는다. 이미 있는 요청 ID는 넣지 않으므로, SQL을 다시 돌려도 대기 표에 중복이 생기지 않는다. 이 확장은 아직 시험하지 않았다. 안 되면 앱이 DuckDB 결과를 읽어 직접 넣는다.

### 유예 뒤 처리도 같은 길로

처리도 바깥에 하는 행동이라 메일과 같은 길을 쓴다. 2단계 SQL이 "안내를 보낸 지 유예 기간이 지났고, 그 뒤 활동이 없는 사용자"를 골라 같은 대기 표에 "처리" 종류로 넣는다. 안내를 보낸 시각은 대기 표에 남아 있으므로 SQL이 그것을 읽는다. 유예는 SQL 조건일 뿐이라 따로 기다리는 부품이 필요 없다.

### 중복 발송을 막는 방법

워커가 API를 부른 직후, 결과를 저장하기 전에 멈추면 그 건은 다시 발송될 수 있다. 이것을 막기 위해 요청 ID를 API에 함께 보낸다. API가 같은 ID를 한 번만 처리해 주면 중복이 생기지 않는다. 메일 API와 처리 API가 이것을 지원하는지는 아직 확인하지 않았다. 지원하지 않으면 드문 중복 발송은 받아들이기로 했다.

안전장치도 둘 둔다. 첫째, 대상 수가 정한 기준을 넘으면 발송을 멈추고 사람이 승인한다. SQL이 잘못되면 전원을 고를 수 있는데, 메일은 되돌릴 수 없기 때문이다. 둘째, 보내기 직전에 대상이 여전히 조건에 맞는지 다시 확인한다. 대기 표에 넣은 뒤 보내기 전에 사용자가 다시 활동했을 수 있기 때문이다.

### 워커: 2단계 앱 안의 Spring Batch

워커는 **Spring Batch**로 만든다. Spring Batch는 많은 건을 묶음 단위로 처리하는 Java 프레임워크다. 실패한 건만 다시 시도하기, 문제 있는 건 건너뛰기, 멈춘 지점부터 다시 시작하기를 이미 제공한다. 발송은 건마다 실패할 수 있어 이 기능이 그대로 필요하다. 직접 만들면 만든 사람이 계속 고쳐야 하므로 검증된 도구를 쓴다.

워커는 2단계 앱 안에 넣는다. Spring Batch는 따로 켜 두는 서버가 아니라 라이브러리이고, 앱이 이미 Java이기 때문이다. 스케줄러가 정해진 시각에 발송 작업을 시작하고, 작업 기록은 PostgreSQL에 남는다. 발송이 변환과 메모리를 다투거나 두 기능의 배포 시기가 달라지면 그때 앱을 나눈다.

Spring Batch는 변환에는 쓰지 않는다. 변환은 SQL을 한 번 실행하는 일이라 건 단위 재시도가 필요 없다.

### 운영: 2단계 스케줄러 화면

운영자는 2단계의 스케줄러 화면을 그대로 쓴다. 발송 작업이 성공했는지 실패했는지 보고 다시 돌린다. 다시 돌리면 실패했거나 남은 건만 보낸다. 대상 수가 기준을 넘어 멈춘 작업은, 운영자가 대상을 확인한 뒤 승인 값을 넣어 다시 돌린다. 화면에서 값을 넣어 다시 돌릴 수 있는지는 2단계 스케줄러 시험에서 함께 확인한다. 사용자 한 명씩 다루는 화면은 그런 요구가 생길 때 더한다.

## 4단계 사용(분석 조회): 사용자에게 보여 준다

### 언제 필요한가

운영자가 아닌 최종 사용자가 결과를 직접 봐야 할 때다. 샘플 시스템에서는 최종 사용자가 자기 팀과 프로젝트의 지표를 직접 본다. 관리자는 어떤 지표를 보여 줄지 정하고, 사용자는 정해진 화면을 본다. 사용자는 권한이 있는 데이터만 보고, 권한이 없으면 기본적으로 거부된다.

이 단계의 최소 구성은 조회 앱 하나를 더하는 것이다. Trino, Iceberg, 오케스트레이터는 각자의 조건이 생길 때 들어오며, 모두 들어온 모습이 끝 구성이다.

### 최소 구성: 집계 표와 조회 앱

정해진 지표만 보여 준다면 미리 계산해 둔 집계 표(골드)와, 그 표를 권한에 맞춰 읽어 주는 **조회 앱**이면 충분하다. 아무 SQL이나 받는 서비스를 만들 필요가 없다. 조회 앱은 계속 켜 두는 서비스이므로 이 단계에서 서비스가 하나 늘어난다.

**골드는 PostgreSQL에 쓴다.** 브론즈와 실버는 양이 많아 S3에 두지만, 골드는 팀, 프로젝트, 날짜 단위로 줄인 작은 표다. S3를 고른 이유인 데이터양이 골드에는 맞지 않는다. 그래서 2단계 변환이 골드를 3단계와 같은 방법(DuckDB의 PostgreSQL 확장)으로 PostgreSQL에 쓰고, 조회 앱은 PostgreSQL을 읽는다. 이렇게 하면 좋은 점이 있다.

- 골드는 실버에서 언제든 다시 만들 수 있어, 원본처럼 S3에 보관할 필요가 없다.
- 표를 다시 만들 때 트랜잭션으로 한 번에 바꾸므로, 읽는 도중에 옛 값과 새 값이 섞이지 않는다.
- 웹 앱이 DB를 읽는 흔한 방식이고, 조회 앱이 S3 접근 키를 갖지 않아도 된다.
- PostgreSQL은 이미 있으므로 서비스가 늘지 않는다.

골드가 PostgreSQL이 감당할 만큼 작다는 것은 아직 확인하지 않은 가정이다.

**권한은 조회 앱이 건다.** 조회 앱은 요청한 사용자가 속한 팀과 프로젝트를 확인하고, 그 조건을 붙여서만 집계 표를 읽는다. 조건이 없으면 아무것도 돌려주지 않는다. 소속 정보는 플랫폼이 이미 가진 것을 쓴다. 조회 앱이 그 정보를 어떻게 읽을지는 아직 확인하지 않았다.

**지표는 개발자가 SQL로 더한다.** 관리자가 보여 줄 지표를 정하면, 개발자가 그 지표를 계산하는 SQL을 2단계 변환에 더한다. 관리자가 SQL을 직접 쓰지 않으므로 SQL을 서비스로 열 필요가 없다.

### 끝 구성으로 가는 길

아래 셋은 순서가 정해져 있지 않다. 조건이 먼저 생긴 것부터 들어온다.

**Trino: SQL을 서비스로 열 때.** **Trino**는 여러 사용자가 동시에 SQL을 실행할 수 있는 분산 SQL 서버다. 사용자별 권한, 행 단위 필터, 열 가리기를 서버에서 적용할 수 있다. 관리자나 사용자가 직접 SQL을 쓰기 시작하고, 여럿이 동시에 쓰거나 쿼리를 공유하고, 권한을 서버에서 강제해야 할 때 들인다. 그 전에는 신뢰하는 운영자가 DuckDB와 DBeaver 같은 개인 도구로 직접 조회한다. 이 방법은 S3 접근 키가 필요하므로 신뢰하는 사람에게만 허용한다.

**Iceberg: S3의 표를 여럿이 읽을 때.** **Iceberg**는 S3의 파일 묶음을 DB의 표처럼 다루게 해 주는 표 형식이다. 행 단위 수정과 삭제, 표 통째 교체, 과거 시점 조회를 지원한다. 일반 파일로 된 표를 변환이 다시 쓰는 동안 누가 읽으면, 반은 옛 파일이고 반은 새 파일인 결과를 읽을 수 있다. Iceberg는 바꾸기가 끝난 순간에 한 번에 새 표로 넘어가므로 이런 일이 없다. 최소 구성에서는 사용자가 PostgreSQL을 읽으므로 이 위험이 없다. Trino로 사용자가 S3의 표를 직접 읽기 시작하거나, 실버의 행을 고치거나 지워야 할 때 바꾼다. 이때 골드도 S3의 Iceberg로 옮겨 Trino가 읽게 하고, PostgreSQL은 화면용 사본으로 남긴다. 정해진 지표 화면은 계속 PostgreSQL을 읽으므로 버리는 것이 없다.

Iceberg는 형식이지 서비스가 아니지만, 표 목록을 관리하는 **카탈로그**가 필요하다. 카탈로그 종류에 따라 DuckDB와 Trino가 함께 쓸 수 있는지가 달라지는데, 이 조합은 아직 확인하지 않았다. 또 작은 파일 합치기, 오래된 스냅샷 지우기 같은 정비 작업을 정기적으로 돌려야 한다. 이 작업은 그때의 스케줄러가 돌린다.

**오케스트레이터: 스케줄러가 부족할 때.** 오케스트레이터는 최종 사용자에게 보여 주는 일과 관계없이, 2단계의 교체 조건(날짜 구간 재실행, 작업 순서 의존, 놓친 실행 채우기)이 생기면 들어온다. 다만 끝 구성에서는 작업이 늘어 이 조건이 생기기 쉬우므로 끝 구성에 포함한다. 그때 스케줄러를 Dagster나 Airflow로 바꾼다. Dagster는 Airbyte 연결과 dbt 모델을 그대로 불러와 한 화면에서 관리할 수 있다. 로직은 이미 스케줄러와 떨어져 있으므로 바꿔도 SQL은 그대로다.

| 갈림길 | 지금 고른 것 | 대안 | 대안을 고르는 상황 | 상태 |
|---|---|---|---|---|
| 조회 앱이 읽는 곳 | PostgreSQL 집계 표 | S3 직접, Trino | 집계 표가 PostgreSQL에 담기 어려울 만큼 커지거나, Trino가 들어왔을 때 | 크기 가정 미확인 |

| 표 형식 | 일반 파일 | Iceberg | 사용자가 S3의 표를 직접 읽거나, 행 수정·삭제가 필요할 때 | 카탈로그 호환 미확인 |
| 스케줄러 | 내장 화면 | Dagster, Airflow | 2단계의 교체 조건과 같다 | 시험 전 |

## 완성 기준

4단계의 조회 앱까지 오면 아홉 요구를 모두 받는다. 수집, 저장, 변환, 사용(내보내기와 분석 조회)이 갖춰지고, 운영자 화면과 접근 권한도 단계마다 풀렸다. 이것이 최소 구성이다.

끝 구성은 최소 구성에 Trino, Iceberg, 오케스트레이터가 조건에 따라 들어온 모습이다. 이 셋은 아홉 요구가 아니라 그 뒤에 생기는 요구를 받는다. 관리자나 사용자가 SQL을 직접 쓰면 Trino가, 사용자가 S3의 표를 직접 읽으면 Iceberg가, 작업이 늘어 순서와 재실행 관리가 어려워지면 오케스트레이터가 받는다.

| 구성 | 새로 켜 두는 서비스 |
|---|---|
| 최소 구성 | Airbyte, 배치 앱(스케줄러, DuckDB, 워커), 조회 앱 |
| 끝 구성 | 최소 구성 + Trino, Iceberg 카탈로그, 오케스트레이터(Dagster 또는 Airflow) |

S3와 PostgreSQL은 처음부터 있으므로 표에 넣지 않았다. 행 단위 권한을 별도 정책 서버(OPA)로 걸게 되면 끝 구성에 서비스가 하나 더 는다. 이 여부는 아직 확인하지 않았다.

끝 구성에서는 새 요구를 서비스를 더하지 않고 받는다. 새 분석과 지표는 SQL 추가로, 새 소스는 Airbyte 커넥터 추가로 받기 때문이다. 다만 데이터양이 2단계의 "나눠 돌리기"로 감당되는 범위여야 한다. 넘으면 분산 엔진이 필요하다.

예외는 둘이고, 둘 다 지금은 요구가 없어 범위 밖 후보로 둔다.

- **즉시 반응:** 데이터가 도착하는 즉시 반응해야 하면 메시지 큐가 필요하다. 지금 구성은 정해진 시각에 돌기 때문이다.
- **BI 대시보드:** 그래프와 표로 자유롭게 탐색하려면 별도 BI 도구가 필요하다. BI 도구는 SQL로 데이터를 읽는다. PostgreSQL의 골드만 본다면 지금도 붙일 수 있고, 실버까지 탐색하려면 Trino가 들어온 뒤에 붙인다.

## 아직 확인하지 않은 것

아래 일곱은 확인되기 전까지 관련 선택을 확정하지 않는 항목이다. 단계 순서로 놓았다.

1. (2단계) 앱 안의 DuckDB(2코어, 4GB)가 가장 많은 한 시간 분량을 15분 안에 처리하는지
2. (2단계) 사내 S3가 경로 단위 접근 권한을 지원하는지
3. (2·3단계) 내장 스케줄러가 날짜나 승인 값을 넣어 다시 돌리고, 재기동 때 놓친 실행을 채우는지
4. (3단계) Spring Batch가 같은 값으로 작업을 다시 실행할 수 있는지
5. (3단계) 메일 API와 처리 API가 요청 ID로 중복을 막는지, 호출 한도는 얼마인지
6. (3·4단계) DuckDB가 PostgreSQL 확장으로 대기 표와 집계 표에 바로 넣을 수 있는지
7. (4단계) Iceberg 카탈로그를 DuckDB와 Trino가 함께 쓸 수 있는지

이 밖의 미확인 항목은 확정을 막지 않으며, 각 단계의 본문과 갈림길 표에 적었다. 1단계의 Airbyte 변경분 받기(CDC) 지원, HTTP 소스의 파일 그대로 복사, S3의 버전 관리와 삭제 잠금, 4단계의 골드 크기와 소속 정보를 읽는 방법이 여기에 속한다.
