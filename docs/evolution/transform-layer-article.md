# 가장 작은 구성에서 시작해, 요구가 생길 때 한 칸씩 키운다

> 읽기용 글이다. 괄호 안 번호는 근거 문서 [transform-layer.md](transform-layer.md)의 항목이다. 전제가 바뀌면 그 번호를 인용한 결론만 다시 본다.

## 목적

모든 요구를 받는 모던 데이터 플랫폼을 만든다. 처음부터 다 짓지 않는다. 쓰지 않는 서비스는 운영 부담만 늘리기 때문이다. 그래서 요구가 생기는 순서대로 한 칸씩 키운다. 어느 칸에서든 앞 칸의 결과물을 버리지 않는다. 버리는 결과물은 처음부터 만들지 않는다는 뜻이다.

## 요구와 이유

| 요구 | 왜 필요한가 |
|---|---|
| 주 4.2억 건을 S3에 쌓는다 | 데이터가 늘어도 워크로드 디스크가 막히지 않아야 한다 (F1, F3) |
| 부서별로 접근을 나눈다 | 부서는 자기 리소스의 데이터만 봐야 한다 (R1) |
| 휴면 사용자를 찾아 안내하고 처리한다 | 이미 운영 중인 업무다 (R2, R3, R4) |
| 운영자(L2)가 웹 화면으로 운영한다 | 개발자(L3)와 운영자가 다른 사람이다 (R6, F5) |
| 최종 사용자에게 분석을 보여 준다 | 사용자가 권한이 있는 지표를 직접 봐야 한다 (R11) |

## 선택 규칙

필요가 생겼을 때만 서비스를 더한다. 이미 검증된 도구가 있으면 직접 만들지 않는다. 확인하지 못한 것은 확정하지 않고 질문으로 남긴다. 이 규칙이 있어야 갈림길마다 같은 기준으로 고를 수 있다.

---

## 1단계: 수집

**요구는 데이터를 S3로 모으는 일이다.** Airbyte 하나가 PG, Gerrit, GHES를 S3로 옮긴다. 도구를 하나로 두면 소스가 늘어도 운영할 도구가 늘지 않는다. 사용자 테이블은 이 단계부터 전체를 누적한다. 시작 전의 과거는 복구할 수 없어서, 이력 분석이 필요해지기 전에 쌓기 시작해야 한다.

| 갈림길 | 지금 고른 것 | 다른 선택지 | 바꾸는 조건 | 확인 여부 |
|---|---|---|---|---|
| 수집 도구 | Airbyte | 스케줄러 안의 직접 코드 | 소스가 더 늘지 않고 Airbyte 운영 작업이 한도를 넘을 때 | 한도 미정 (T8, Q13) |
| 원본 저장소 | S3 | PG | 바꾸지 않는다. PG는 수정이 가능해 원본 보존이 깨진다 | 결정됨 (C7) |
| 파일 형식 | 소스별로 다르게 | 하나로 통일 | 바꾸지 않는다. 통일하면 중첩 로그에 손실이 생긴다 | 결정됨 (C8) |
| PG 적재 | 전체 누적 | 변경 이벤트(CDC) | 삭제·중간 변경 이력이 필요할 때 | PG 지원 미확인 (T5, Q14) |

## 2단계: 변환

**요구는 부서별 접근 격리와 휴면 식별이다.** 병합과 필터는 업무 규칙이라 수집 도구 밖에서 한다. 배치 앱 하나가 DuckDB와 SQL 파일로 처리한다. SQL 한 번 실행에는 서버가 필요 없기 때문이다. 스케줄러는 운영자가 화면으로 재실행해야 하므로 처음부터 필요하다. 로직은 스케줄러와 분리한다. 스케줄러를 바꿔도 SQL이 그대로 남게 하기 위해서다.

| 갈림길 | 지금 고른 것 | 다른 선택지 | 바꾸는 조건 | 확인 여부 |
|---|---|---|---|---|
| 스케줄러 | 내장 화면(db-scheduler-ui, JobRunr) | Dagster, Airflow | 날짜 구간 재실행, 잡 순서 의존, 놓친 실행 보충 중 하나가 필요할 때 | 시험 전 (T9, Q9) |
| SQL 관리 | SQL 파일 | dbt | 모델이 늘거나 운영자가 PR로 SQL을 고치기 시작할 때 | 결정됨 (T7) |
| 처리 규모 | 컨테이너 1개 | 사양 올리기, 나눠 처리, 분산 엔진 | 한 시간 분량이 15분을 넘을 때, 이 순서로 | 미확인 (T3, A2) |
| 접근 격리 | 부서별 복사본 | 조회 시점 정책 | 복사 비용이 정책 비용보다 커질 때 | 경로 권한 미확인 (T2, A3) |

## 3단계: 활성화 (메일 발송)

**요구는 휴면 안내 메일과 처리다.** 메일 발송은 변환이 아니라 분석 결과를 밖으로 내보내는 일이다. 그래서 변환과 분리한다. 후보는 2단계의 SQL이 고르고, 워커가 건마다 보낸다. 건마다 실패와 재시도가 생기므로 검증된 Spring Batch를 쓴다. 진행 상태는 PG 표에 둔다. 외부 호출이 끝난 뒤 저장 전에 멈추면 중복 발송이 생길 수 있어서, 요청 ID를 표에 두어 막는다.

| 갈림길 | 지금 고른 것 | 다른 선택지 | 바꾸는 조건 | 확인 여부 |
|---|---|---|---|---|
| 워커 | Spring Batch | 직접 구현 | 바꾸지 않는다. 재시도와 재시작을 직접 만들면 유지보수가 늘어난다 | 재실행 시험 전 (C36, Q9) |
| 진행 상태 | PG 표 | Kafka | 즉시 반응이 필요하거나 받는 곳이 여럿이 될 때 | 현재 요구 없음 (T11, A4) |
| 메일 중복 | 요청 ID로 막기 | 중복 허용 | 메일 API가 중복 방지를 지원하지 않을 때 | 미확인 (A1, Q10) |

## 4단계: 최종 구성

**요구는 최종 사용자 분석이다.** 정해진 지표만 보여 주면 미리 계산한 집계 표와 조회 앱으로 충분하다. 임의 SQL 서비스를 지금 만들 이유가 없기 때문이다. 사용자가 SQL을 직접 쓰기 시작하면 그때 Trino를 들인다. 읽는 쪽이 생긴 뒤에는 표를 바꾸거나 행을 고치기 어려우므로, 그 시점에 Iceberg로 바꾼다.

| 갈림길 | 지금 고른 것 | 다른 선택지 | 바꾸는 조건 | 확인 여부 |
|---|---|---|---|---|
| 사용자 서빙 | 집계 표 + 조회 앱 | Trino | SQL 분석을 서비스로 제공해야 할 때(동시 사용, 권한, 쿼리 공유) | 읽는 방식 미정 (T1a, Q23) |
| 표 형식 | 일반 파일 | Iceberg | 읽는 쪽이 생긴 뒤 표 교체나 행 수정이 필요할 때 | 카탈로그 호환 미확인 (T1b, Q16) |
| 스케줄러 | 내장 화면 | Dagster, Airflow | 2단계의 교체 조건과 같다 | 시험 전 (T9) |
| 분석 화면 | SQL 직접 조회 | BI 대시보드 | SQL 접속 지점이 생길 때 | 범위 밖 후보 (Q20) |

## 아직 닫히지 않은 문

아래 여섯이 확인되기 전에는 해당 선택을 확정하지 않는다.

1. 컨테이너 1개가 피크 한 시간을 15분 안에 처리하는지 (A2)
2. Iceberg 카탈로그가 DuckDB와 Trino에서 모두 되는지 (Q15, Q16)
3. 내장 스케줄러의 날짜 재실행과 재기동 시 놓친 실행 보충 (A9, A10)
4. Spring Batch의 같은 파라미터 재실행 (C36)
5. S3 경로 단위 접근 정책 (A3)
6. 메일 API의 중복 방지와 호출 한도 (A1, Q10)
