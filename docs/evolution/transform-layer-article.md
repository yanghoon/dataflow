# 워크로드를 한 칸씩 더해 데이터 분석 서브시스템을 완성하기

> 이 글은 읽기용이다. 판단 근거와 검증 기록은 [transform-layer.md](transform-layer.md)에 있다.

## 이 글이 다루는 것

서비스를 운영하다 보면 데이터로 답해야 하는 질문이 생긴다. 사용자는 얼마나 늘고 있는가. 오래 쓰지 않은 계정은 누구이고, 언제 정리해야 하는가. 각 부서는 자기 데이터만 보고 있는가. 이런 질문에 답하고, 그 답으로 계정 정리나 접근 제한 같은 정책을 실행하려면 데이터 분석이 필요하다. 특별한 시스템만의 이야기가 아니다. 사용자가 있는 시스템이라면 대부분 겪는다.

그런데 필요한 기술과 범위는 시스템마다 다르다. 데이터가 적고 개발자가 직접 운영하는 시스템은 DB에 쿼리 하나를 날리는 것으로 충분하다. 데이터가 서버 디스크를 압박할 만큼 늘고, 개발하는 사람과 운영하는 사람이 나뉘면 이야기가 달라진다. 별도 저장소, 수집 도구, 실행 일정을 관리할 스케줄러, 운영자가 쓸 화면이 필요해진다. 처음부터 큰 구성을 들이면 쓰지 않는 서비스를 운영하느라 비용이 든다. 반대로 지금 편한 도구로 시작했다가 나중에 버리면 같은 일을 두 번 한다. 그래서 레이어는 요구가 생길 때 하나씩 더하고, 도구는 최종 구성에서도 쓰일 것으로 고른다.

이 글은 하나의 샘플 시스템을 예로 들어, 시스템이 커지는 단계마다 어떤 도구와 구성이 필요한지 알아본다. 단계마다 왜 그 기술을 골랐는지, 어떤 상황이 오면 다른 기술로 바꾸는지를 함께 적는다. 상황이 다르면 답도 다르므로, 대안은 그 대안이 맞는 상황과 함께 읽어야 의미가 있다. 최종 구성에서는 새 분석과 지표를 SQL로, 새 소스를 커넥터로 받는다. 컴포넌트는 갈림길 표의 조건이 생길 때만 바뀐다.

자기 시스템에 적용하려면 아래 표에서 지금 갖춘 단계를 먼저 찾고, 그 단계의 갈림길 표에 적힌 조건을 자기 상황과 비교하면 된다. 1·2단계는 차례로 한다. 3·4단계는 필요한 것만 해도 되고, 어느 쪽을 먼저 해도 된다.

| 단계 | 이 단계가 필요해지는 때 | 더하는 것 |
|---|---|---|
| 1. 수집 | 데이터가 여러 곳에 흩어져 있거나, 서버 디스크로 감당하기 어려울 만큼 늘어날 때 | S3 저장소, Airbyte 수집 도구 |
| 2. 변환 | 모은 데이터에 부서별 필터나 휴면 판정 같은 업무 규칙을 적용해야 할 때 | DuckDB 배치 앱, 실행 도구(내장 스케줄러 또는 Kestra) |
| 3. 사용: 분석 조회 | 바깥 시스템이 골드를 읽어 자기 기능에 써야 할 때 | PostgreSQL 집계 표, 읽기 전용 계정과 뷰 |
| 4. 사용: 내보내기 | 분석 결과로 메일 발송처럼 되돌릴 수 없는 바깥 행동을 해야 할 때 | 대기 표, Spring Batch 워커 |

데이터 자체를 서비스로 내놓아야 할 때, 예를 들어 플랫폼 안에서 사용자가 직접 데이터를 조회해야 할 때는 마지막의 "데이터 플랫폼으로 확장"에서 Trino와 Iceberg를 더한다.

## 기본 개념: 메달리온 구조

이 글은 모던 데이터 아키텍처의 흔한 방식인 **메달리온 구조(Medallion Architecture)**를 따른다. 데이터를 세 층으로 나눠 쌓는 방식이다.

- **브론즈(Bronze):** 소스에서 받은 원본을 그대로 둔다. 고치지 않는다. 나중에 가공 규칙이 틀린 것을 알았을 때 원본에서 다시 만들 수 있어야 하기 때문이다.
- **실버(Silver):** 브론즈를 합치고 거르고 정리한 데이터다. 업무 규칙은 여기서 적용한다.
- **골드(Gold):** 실버를 집계해 바로 보여 줄 수 있게 만든 데이터다.

층을 나누면 각 층의 책임이 분명해진다. 수집 도구는 브론즈까지만 책임지고, 업무 규칙은 실버 이후에서만 다룬다.

## 기본 개념: 모던 데이터 아키텍처

메달리온 구조가 "데이터를 어떻게 쌓는가"라면, 모던 데이터 아키텍처(Modern Data Architecture)는 "데이터가 어떤 흐름을 거쳐 쓰이는가"를 레이어로 나눈 것이다. 레이어마다 하는 일이 다르므로 도구도 따로 고른다. 이 글의 단계는 이 레이어를 하나씩 채워 가는 과정이다.

흐름을 따라 데이터가 지나가는 레이어는 넷이다.

1. **수집(Ingestion):** 소스에서 데이터를 읽어 저장소로 옮긴다. 가공하지 않는다.
2. **저장(Storage):** 원본과 가공 결과를 오래, 싸게 보관한다. 메달리온의 세 층이 여기에 있다. 저장은 따로 단계를 두지 않고, 수집(1단계)과 함께 채운다.
3. **변환(Transformation):** 브론즈를 합치고 걸러 실버와 골드를 만든다. 업무 규칙이 여기에 있다.
4. **사용(Serving):** 가공한 결과를 쓰는 곳으로 넘긴다. 바깥에 되돌릴 수 없는 영향을 남기는지에 따라 둘로 나뉜다.
   1. **분석 조회(Analytics):** 사람이나 앱이 결과를 읽는다. 대시보드, 지표 화면, SQL 조회가 여기에 속한다. 읽기만 하므로 결과가 틀리면 고쳐서 다시 보여 주면 된다.
   2. **내보내기(Reverse ETL):** 결과를 외부 시스템으로 내보내 행동으로 바꾼다. 메일 발송, 외부 도구에 데이터 넣기가 여기에 속한다. 바깥에 남은 영향은 되돌릴 수 없다.

흐름에 끼지 않고 모든 레이어에 걸치는 일도 둘 있다.

- **오케스트레이션(Orchestration):** 각 레이어의 작업을 정해진 때와 순서로 돌리고, 실패를 보여 주고, 다시 돌린다.
- **거버넌스(Data Governance):** 데이터를 믿고 쓸 수 있게 규칙을 정하고 지킨다. 어디서 왔는지(계보), 어떤 표가 있는지(카탈로그), 값이 맞는지(품질), 얼마나 보관하는지(보존), 누가 볼 수 있는지(접근 권한)를 다룬다.

보안(Security)은 거버넌스와 따로 부르기도 한다. 암호화, 네트워크, 계정 관리까지 넓게 다룰 때다. 이 글에서 다루는 보안은 "누가 어떤 데이터를 볼 수 있는가" 하나뿐이고, 이것은 거버넌스가 정하는 규칙이므로 함께 묶는다.

## 샘플 시스템

샘플 시스템은 개발 조직이 쓰는 플랫폼이다. 데이터는 서버 디스크로 감당하기 어려울 만큼 많고, 개발하는 사람과 운영하는 사람이 나뉘어 있다. 앞에서 말한 "이야기가 달라지는" 규모다. 선택의 이유를 구체적으로 따지기 위해 숫자까지 정해 둔다.

**데이터 소스는 네 가지다.**

- **로그:** 서버마다 사용자 활동 로그가 쌓인다. 주 4.2억 건, 가장 많은 시간에는 시간당 530만 건이다. 지금은 각 서버의 디스크에 쌓이고, 로그 수집기(서버의 로그를 모아 다른 곳으로 보내는 에이전트)가 이미 설치되어 있다.
- **코드 리뷰 시스템:** API로 레코드를 준다.
- **코드 호스팅 서버:** 사용자 목록을 CSV 파일로 준다.
- **사용자 DB:** PostgreSQL에 있는 사용자 테이블이다. 약 5만 건으로 예상한다.

로그 외의 데이터는 각 시스템 안에만 있다. 분석하려면 시스템마다 따로 조회해야 한다.

**사람은 둘로 나뉜다.** 개발자가 파이프라인을 만들고, 운영자가 구성, 운영, 분석을 맡는다. 운영자는 코드를 쓰지 않으므로 웹 화면에서 설정을 바꾸고, 실행 상태를 보고, 실패한 작업을 다시 돌릴 수 있어야 한다.

**요구는 아홉 가지다.** 앞의 데이터 아키텍처 레이어로 나누면 어느 단계에서 무엇을 풀어야 하는지 보인다. 흐름 레이어의 요구는 그 레이어를 채우는 단계에서 풀리고, 모든 레이어에 걸치는 요구는 단계마다 조금씩 풀린다.

| 레이어 | 요구 | 왜 필요한가 |
|---|---|---|
| 수집 | 흩어진 시스템의 데이터를 한곳으로 가져온다 | 사용자 테이블과 활동 로그를 함께 봐야 분석할 수 있다 |
| 저장 | 늘어나는 데이터를 원본 그대로 보관한다 | 서버 디스크로는 감당이 안 되고, 가공 규칙이 틀렸을 때 원본에서 다시 만들어야 한다 |
| 저장 | 사용자 테이블을 주기마다 쌓아 이력을 남긴다 | 쌓기 전의 과거는 다시 만들 수 없다 |
| 변환 | 오래 쓰지 않은 사용자를 찾는다 | 이미 하고 있는 업무다 |
| 변환 | 이력으로 사용자 추이를 비교한다 | 기준일을 바꿔 가며 사용자 수가 어떻게 변했는지 봐야 한다 |
| 사용: 분석 조회 | 바깥 시스템이 집계 결과를 읽어 간다 | 예를 들어 바깥 시스템이 쿼터 변화를 읽어 직접 보정해야 한다 |
| 사용: 내보내기 | 찾은 사용자에게 안내 메일을 보내고, 유예 뒤 처리한다 | 찾기, 안내, 유예, 처리 순서로 진행하는 업무다 |
| 오케스트레이션 | 운영자가 웹 화면으로 설정을 바꾸고, 실행 상태를 보고, 다시 돌린다 | 운영자와 개발자가 다른 사람이다 |
| 거버넌스 | 부서별로 데이터 접근을 나눈다 | 부서는 자기 리소스의 로그 파일을 S3에서 직접 읽는다 |

## 선택 규칙

모든 단계에서 같은 규칙으로 고른다.

1. **레이어는 요구가 생겼을 때만 더한다.** 미리 만든 레이어는 쓰이기 전까지 비용만 든다.
2. **도구는 최종 구성에서도 쓰일 것을 고른다.** 최종 구성의 도구가 지금 규모에 과하면 효율을 따져 차선을 고른다. 차선은 교체 조건을 갈림길에 적고, 교체해도 로직(SQL)과 데이터가 남게 한다.
3. **검증된 도구가 있으면 직접 만들지 않는다.** 직접 만든 것은 만든 사람이 계속 고쳐야 한다.
4. **확인하지 못한 것은 확정하지 않는다.** 확인 전까지는 "미확인"으로 표시하고 시험할 항목으로 남긴다.

## 1단계 수집: 데이터를 모은다

### 언제 필요한가

두 문제 중 하나가 생기면 이 단계가 필요하다.

- **분석 문제:** 데이터가 여러 시스템에 흩어져 있어 함께 볼 수 없다. 사용자 테이블과 활동 로그를 같이 봐야 오래 쓰지 않은 사용자를 찾을 수 있다.
- **저장 문제:** 데이터가 서버 디스크로 감당하기 어려울 만큼 늘어난다. 디스크가 차면 서비스가 멈춘다.

샘플 시스템은 둘 다 겪는다. 그래서 이 단계는 "모을 곳"과 "모으는 방법"을 함께 정한다.

### 저장소: S3

모든 원본은 **S3**에 쌓는다. S3는 파일을 객체 단위로 저장하는 저장소다. AWS의 서비스 이름이지만 같은 방식으로 동작하는 사내 저장소(S3 호환 스토리지)도 많아, 사실상 표준 방식이 되었다.

후보는 셋이었다. 서버 디스크를 늘리기, DB에 넣기, S3에 넣기다.

- **서버 디스크를 늘리면** 흩어진 문제가 그대로 남는다. 서버가 늘 때마다 디스크도 따로 늘려야 한다.
- **DB에 넣으면** 한곳에 모이지만, 같은 용량을 두는 비용이 높다. 로그처럼 계속 쌓이기만 하는 데이터에는 DB의 수정·검색 기능이 대부분 필요 없다. 쓰지 않는 기능에 비용을 내는 셈이다.
- **S3에 넣으면** 두 문제가 함께 풀린다. 용량을 미리 정하지 않고 필요한 만큼 늘리고, 모든 데이터가 한곳에 모인다.

S3를 고른 이유가 하나 더 있다. 데이터가 들어오는 길이 둘인데 S3는 둘 다 받는다. 로그 수집기처럼 데이터를 직접 밀어 넣는 방식(push)은 파일을 S3에 쓰기만 하면 된다. 다른 시스템에서 데이터를 가져오는 방식(pull)도 수집 도구가 S3에 쓰면 된다. 뒤 단계에서 쓰는 DuckDB, Trino, Iceberg도 모두 S3를 바로 읽는다. 들어오는 길과 읽는 쪽이 모두 S3를 중심으로 모인다.

주의할 점이 있다. S3도 파일을 덮어쓰거나 지울 수 있다. S3에 넣는다고 원본이 저절로 지켜지지는 않는다. 그래서 브론즈 경로에는 수집 도구만 쓰게 하고, 쓸 때는 항상 새 파일로 쓰게 한다. DB는 행을 고치는 것이 기본 동작이라 이 규칙을 지키기 더 어렵다. 사내 저장소가 버전 관리나 삭제 잠금을 지원하는지는 아직 확인하지 않았다.

### 수집 도구: 로그는 기존 경로, 나머지는 Airbyte

로그는 로그 수집기가 이미 서버마다 설치되어 있으므로, 보낼 곳만 S3로 바꾼다. 새 도구가 필요 없다.

나머지 세 소스는 누군가 가서 가져와야 한다(pull). 이 일은 **Airbyte**로 한다. Airbyte는 소스에서 데이터를 읽어 목적지에 쓰는 오픈소스 수집 도구다. 고른 이유는 세 가지다.

- **소스를 늘리기 쉽다.** 커넥터는 특정 소스를 읽는 부품이다. PostgreSQL처럼 흔한 소스는 오픈소스 커넥터를 그대로 쓴다. 커넥터가 없는 소스는 두 방법으로 만든다. 단순한 HTTP API는 화면에서 설정만 해서 만드는 Connector Builder를 쓰고, 복잡한 소스는 Python 개발 도구(CDK)로 만든다. 어느 쪽이든 만든 뒤에는 다른 커넥터와 똑같이 운영한다.
- **운영자 화면이 있다.** 소스 추가, 실행 일정, 실행 이력, 재실행을 웹 화면에서 한다. 코드를 쓰지 않는 운영자도 수집을 직접 운영할 수 있다.
- **추적 정보를 자동으로 붙인다.** 레코드마다 고유 ID, 가져온 시각, 실행 ID를 붙인다. 데이터가 이상할 때 어느 실행에서 왔는지 따라가 그 부분만 다시 가져올 수 있다.

Airbyte는 여러 서비스로 이루어져 이 글에 나오는 도구 중 운영이 가장 무겁다. 샘플 시스템에서도 기존 커넥터를 그대로 쓰는 소스는 PostgreSQL 하나뿐이고, 나머지 둘은 직접 만든다. 그럼에도 Airbyte를 쓰는 것은 운영자가 코드 없이 수집을 운영해야 하기 때문이다. 운영 부담은 있지만, 새 수집 경로는 오픈소스 커넥터나 Connector Builder로 바로 반영하고, 연결 정보와 실행 일정과 받을 표는 운영자가 관리 화면에서 직접 바꾼다. 스케줄러 화면은 실행을 보고 다시 돌리는 데 그치고 설정은 바꾸지 못하며, 2단계의 Kestra도 Airbyte의 연결 설정 화면을 대신하지 못한다(비교는 근거 문서의 부록 C). Airbyte는 소스가 늘어도 바꿀 필요가 없는 최종 구성의 도구이기도 하다(규칙 2). 가져오는 도구는 Airbyte 하나로 정한다. 소스가 더 늘지 않는다면 이 판단은 다시 본다(아래 갈림길).

### 파일 형식은 소스마다 다르게 둔다

브론즈에는 원본을 둔다. 형식을 하나로 맞추려면 어느 소스든 변환을 거쳐야 하고, 변환하는 순간 그것은 원본이 아니다. 예를 들어 로그는 겹겹이 들어간 JSON이라 CSV로 바꾸면 구조가 사라진다. 반대로 모두 JSONL로 맞추면 DB 행의 숫자와 날짜가 문자열로 바뀐다. 그래서 형식은 소스의 원래 모양을 따르고, 일관성은 "모두 S3에 둔다"와 "경로와 추적 정보 규칙을 지킨다"로 맞춘다.

| 소스 | 브론즈에 남는 것 | 추적 정보 |
|---|---|---|
| 로그 | 수집기가 보낸 압축 JSONL 파일 그대로 | 파일 경로와 객체 정보(방식 미정) |
| 코드 리뷰 시스템 | Airbyte가 받은 레코드(JSONL) | Airbyte가 붙인 열 |
| 코드 호스팅 서버 | 원래 CSV 파일이 이상적이나, 지금은 레코드(JSONL) | Airbyte가 붙인 열 |
| 사용자 DB | Airbyte가 받은 행 | Airbyte가 붙인 열 |

사람이 바로 열어 볼 수 있는 JSONL(한 줄에 JSON 하나)과 CSV를 우선한다. 분석용으로 압축한 형식(Parquet 등)은 실버 이후에 쓴다. 사용자 DB의 행을 어떤 형식으로 받을지, 그때 타입을 어떻게 지킬지는 아직 정하지 않았다.

### 이력은 지금부터 쌓는다

사용자 테이블은 정해진 주기(일 또는 시간)마다 전체를 가져와 쌓는다. 5만 건이면 매번 전체를 가져와도 부담이 작다. 사용자가 지워지면 다음 기록에 없으므로 삭제도 드러난다. 이력 분석은 나중에 생길 요구지만 쌓기는 지금 시작해야 한다. 시작하기 전의 과거는 다시 만들 수 없기 때문이다. 오래 쓰지 않은 사용자를 찾으려면 이 이력과 함께 로그의 활동 기록이 필요하다. 둘 다 이 단계부터 쌓인다.

### 이 단계에서 남는 빈칸

- **부서별로 거르기:** Airbyte 오픈소스판에는 레코드를 거르는 기능이 없다. 거르기는 업무 규칙이기도 해서 다음 단계의 변환에서 한다.
- **원본 보존의 예외:** 코드 호스팅 서버의 CSV는 원래 파일 그대로 받아야 원칙에 맞다. 그러나 Airbyte가 HTTP 소스에서 파일을 그대로 복사하는 기능을 확인하지 못해 레코드로 받는다. 원본과 완전히 같지 않을 수 있으므로 모든 열을 문자열로 받아 손실을 줄인다. 원칙을 어긴 것을 알고 받아들인 예외다.
- **로그 경로의 추적 정보와 운영 화면:** 로그는 Airbyte를 거치지 않으므로 Airbyte의 추적 정보와 화면을 쓸 수 없다. 원본 파일을 고치지 않고 추적 정보를 붙이려면 파일 경로나 객체 정보에 넣어야 하는데, 방식은 아직 정하지 않았다. 로그 경로를 운영자가 어떤 화면으로 볼지도 정하지 않았다.

### 갈림길

| 갈림길 | 지금 고른 것 | 대안 | 대안을 고르는 상황 | 상태 |
|---|---|---|---|---|
| 저장소 | S3 | 서버 디스크, DB | 고르지 않는다. 서버 디스크는 흩어진 문제가, DB는 비용과 원본 수정 위험이 남는다 | 결정 |
| 원본 보존 수단 | 권한 규칙(브론즈 경로는 수집 도구만, 항상 새 파일로) | 저장소 기능(버전 관리, 삭제 잠금)을 더하기 | 사내 S3가 지원하면 더한다. 지원하지 않으면 권한 규칙만으로 지킨다 | 저장소 기능 미확인 |
| 가져오는 도구 | Airbyte | 배치 앱 안에 직접 짠 수집 코드 | 소스가 더 늘지 않고, Airbyte 운영 작업(업그레이드, 장애)이 정한 한도를 넘을 때 | 한도 미정 |
| 파일 형식 | 소스별 | 하나로 통일 | 고르지 않는다. 통일하면 변환을 거쳐 원본이 아니게 된다 | 결정 |
| 사용자 테이블 | 주기마다 전체를 쌓기 | 변경분만 받기(CDC) | 주기 사이의 변경이나 삭제 시점까지 알아야 할 때 | Airbyte 지원 미확인 |

## 2단계 변환: 데이터를 가공한다

### 언제 필요한가

수집한 브론즈는 가공 전 원본이다. 업무에 쓰려면 먼저 실버로 정제하고, 정제된 데이터 위에 업무 규칙을 적용해야 한다. 이 변환은 밀어 넣는 길(로그)과 가져오는 길(Airbyte) 두 경로 모두에 필요하다.

### 변환이 하는 일

요구마다 변환이 하는 일은 이렇다.

- **정제:** 로그는 S3에 쌓일 때 시간이나 크기 단위로 잘려 작은 파일로 나뉜다. 작은 파일이 많으면 읽기가 느려지므로, 한 시간 단위로 합친다. 가져온 데이터는 기준 시각을 붙여 정리한다.
- **오래 쓰지 않은 사용자 찾기:** 사용자 테이블과 활동 로그를 합쳐 마지막 활동 시점을 계산하고 대상 목록을 만든다. 이 목록이 4단계 메일 발송의 입력이 된다.
- **집계:** 바깥 시스템이 읽을 결과를 골드로 만든다. 예를 들어 활동 로그에서 쿼터에 영향을 주는 변화를 찾는다. 이 골드가 3단계의 입력이 된다.
- **이력:** 주기마다 받은 사용자 테이블을 기준 시각별로 실버에 쌓는다. 추이 비교는 이 실버를 조회해서 한다.
- **부서별 격리:** 부서별 리소스 목록으로 로그를 걸러 부서 경로에 복사본을 만든다. 각 부서는 이 파일을 자기 도구로 S3에서 직접 읽는다. 부서가 어떤 도구로 읽는지는 알지 못한다. 이 시스템은 데이터 플랫폼이 아니므로 조회 기능은 주지 않고 변환한 파일만 넘긴다. 이 단계에는 행 단위 권한을 걸 엔진이 없고 S3 권한은 경로 단위뿐이어서, 경로를 나눠 복사한다. 리소스 목록은 PostgreSQL 표에 두어, 바뀌어도 SQL을 고치지 않게 한다.

### 로직과 엔진: SQL과 DuckDB

위의 일은 모두 합치고, 거르고, 세는 일이라 SQL로 충분하다. 그래서 로직은 SQL 파일에 둔다.

엔진은 네 조건을 만족해야 한다. 켜 둘 서버가 없어야 하고, Java 앱 안에 넣을 수 있어야 하고, S3의 gzip 압축 JSONL을 바로 읽어야 하고, 나중에 dbt와 Iceberg로 이어져야 한다. 이 조건을 모두 만족하는 **DuckDB**를 쓴다. DuckDB는 별도 서버 없이 라이브러리로 돌아가는 분석용 SQL 엔진이다. Iceberg 표는 REST 카탈로그를 붙이면 만들고, 넣고, 고치고, 지울 수 있다(공식 문서 확인). 수정과 삭제는 기존 파일을 다시 쓰지 않고 삭제 기록을 덧붙이는 방식(merge-on-read)만 지원한다.

SQL은 파일로 Git에 두고 개발자가 고친다. SQL이 많아지거나, 운영자가 교육을 받아 PR로 SQL을 고치게 되면 **dbt**로 옮긴다. dbt는 SQL 사이의 의존을 읽어 실행 순서를 정하고, 결과를 시험한다(빈 값, 중복 등). 고친 SQL을 합치기 전에 시험할 수 있어, 개발자가 아닌 사람이 SQL을 고칠 때의 안전장치가 된다. SQL은 그대로 옮겨 쓴다. dbt가 이 구성에 맞는 이유는 셋이다. DuckDB 공식 조직이 관리하는 어댑터(dbt-duckdb)가 S3 읽기와 PostgreSQL 붙이기를 지원하고, 확장할 때는 Trino 어댑터(dbt-trino)로 이어진다. Kestra는 dbt 작업을 컨테이너에서 돌리고 모델별 실행·시험 결과를 화면에 보여 준다. Airflow로 옮겨도 오픈소스 Cosmos가 dbt 모델 하나하나를 Airflow 작업으로 펼쳐 준다. 실행 도구를 바꿔도 dbt 프로젝트는 남는다.

대신 dbt는 Python 도구라 자기 DuckDB를 따로 띄운다. 그래서 dbt로 옮기면 변환은 Java 배치 앱을 떠나 실행 도구가 부르는 dbt 컨테이너에서 돌고, 배치 앱에는 4단계 워커만 남는다. 내장 스케줄러로는 컨테이너를 부르기 어려우므로 Kestra나 Airflow가 있어야 한다. dbt 오픈소스판에는 실행 기록 화면이 없고, 실행 현황은 실행 도구의 화면에서 본다. dbt 문서 사이트(dbt docs)는 표 설명과 열 단위 계보를 보여 준다. Kestra 오픈소스판에 dbt 작업이 들어 있는지와, S3에 파일로 쓰는 모델에서 증분 처리가 안 되는 제약은 옮길 때 확인한다.

처리 기준은 가장 많은 한 시간 분량(530만 건)을 15분 안에 끝내는 것이다. 15분은 뒤 단계(휴면 판정, 조회 화면)가 결과를 기다려도 되는 한도로 잡은 임의의 상한이며, 시스템의 조건에 따라 달라질 수 있다. 아직 실측하지 않았으므로 작은 사양(2코어, 4GB)으로 시작한다.

### 실행: 배치 앱과 실행 도구

변환은 정해진 시각에 두 경로 모두를 대상으로 돌아야 하고, 운영자가 화면에서 실패를 보고 다시 돌려야 한다. Airbyte의 일정 기능은 가져오는 경로만 다루므로 쓸 수 없다. 그래서 실행 도구가 필요하다.

DuckDB는 경량 Java 앱(배치 앱) 하나에 넣는다. 앱은 SQL을 실행만 하므로, 실행 도구를 바꿔도 SQL은 남는다. DuckDB는 기본으로 장비 메모리의 80%까지 쓰므로, 앱과 메모리를 나눠 쓰도록 한도를 정해 둔다.

실행 도구는 요구에 따라 셋 중 하나를 고른다.

| 실행 도구 | 고르는 때 | 새로 켜 두는 것 |
|---|---|---|
| 내장 스케줄러(db-scheduler-ui 또는 JobRunr) | 실행을 보고 다시 돌리기만 하면 될 때 | 없음(배치 앱 안) |
| Kestra + oauth2-proxy | 작업 순서 의존, 시간 구간 다시 돌리기, 놓친 실행 채우기, 화면에서 설정 바꾸기 중 하나라도 필요할 때 | Kestra 하나(단일 프로세스, PostgreSQL 사용)와 프록시 |
| Airflow | 위에 더해 운영자별 권한이나 설정 변경 기록이 필요할 때 | 서비스 서너 개 |

내장 스케줄러 화면은 실행을 보고 다시 돌리는 데 그치고, 설정은 바꾸지 못한다. Kestra는 서비스 하나로 작업 순서, 구간 재실행, 설정 저장소, 실행할 때 값 넣기를 화면에서 한다. 인증은 앞단의 oauth2-proxy로 사내 SSO 로그인만 통제한다. 들어온 사람은 모두 Kestra의 같은 계정으로 동작하므로, 사람별 권한과 변경 기록은 없다. 그것까지 필요하면 Airflow를 고른다. 오픈소스판 중 역할별 권한을 가진 것은 Airflow뿐이다(비교는 근거 문서의 부록 D).

샘플 시스템은 운영자가 화면에서 설정(휴면 기준일, 유예 기간, 승인 기준)을 바꿔야 하므로 Kestra를 고른다. 기준값은 Kestra 설정 저장소에 두고 SQL에 넘긴다. 부서 리소스 목록처럼 표 형태인 설정은 PostgreSQL 표에 둔다. 운영자는 Kestra 화면에서 실행 입력에 부서와 리소스를 넣고 작업을 돌려 이 표를 고친다. 표 전체를 보며 고치는 화면이 꼭 필요하면 NocoDB 같은 설정 관리 도구를 더할 수 있다. 하지만 Kestra로 설정을 바꿀 수 있으므로 별도 도구가 필요한 경우는 적다. Kestra 오픈소스판이 설정 저장소, 실행 입력(표 형태 값 포함), Airbyte 연동을 제공하는지는 시험으로 확인한다.

규모가 커지면 먼저 사양을 올린다. 그래도 부족하면 같은 SQL을 시간대나 부서별로 입력 범위만 나눠 별도 컨테이너에서 동시에 돌린다. 나눠 돌린 실행끼리는 데이터를 주고받지 않는다. 그래서 전 기간에 걸친 집계는 부분 결과를 다시 합쳐야 한다. 동시에 돌리는 일은 실행 도구(Kestra의 병렬 실행)가 맡고, 합치기는 부분 결과를 읽는 SQL 한 단계로 한다. 늘어나는 것은 SQL뿐이고, 나누고 합치는 코드를 따로 짜지 않는다(규칙 3). 내장 스케줄러를 쓰고 있다면 병렬 실행을 직접 짜야 하므로, 이때가 Kestra로 옮길 때다. Kestra의 병렬 실행이 이 용도에 맞는지는 시험으로 확인한다. 이것으로도 안 될 때만 분산 엔진으로 바꾼다.

가져오는 경로는 Kestra가 Airbyte sync가 끝난 뒤 변환을 시작하므로 순서가 맞는다. 내장 스케줄러는 수집이 끝났는지 모르므로 변환을 충분히 늦게 돌리고, 입력이 없으면 실패하게 한다.

로그는 수집기가 S3에 밀어 넣으므로, 어느 실행 도구도 한 시간 분량이 다 들어왔는지 알 수 없다. 그래서 변환을 30분마다 돌리고, 정각 실행이 지난 한 시간을 처음부터 다시 계산한다. 예를 들어 11시 35분에는 11시~11시 30분의 임시 결과를 만들고, 12시 5분에는 11시대 전체의 최종 결과로 덮어쓴다. 임시 결과 뒤에 늦게 온 파일도 최종 결과에 들어간다. 다시 돌려도 결과가 겹치지 않으므로 덮어써도 안전하다. 5분 대기는 임의로 정한 값이며, 수집기가 얼마나 늦을 수 있는지는 확인하지 않았다. 대기보다 늦게 온 파일은 운영자가 그 시간을 다시 돌려 반영한다. 휴면 판정은 최종 결과만 읽는다. 임시 결과로 판정하면 기록이 빠진 사용자를 휴면으로 잡을 수 있고, 4단계에서 되돌릴 수 없는 메일과 처리로 이어지기 때문이다.

## 3단계 사용(분석 조회): 사용자에게 보여 준다

### 언제 필요한가

바깥 시스템이 이 시스템의 집계 결과를 읽어 자기 기능에 써야 할 때다. 샘플 시스템에서는 활동 로그에서 쿼터에 영향을 주는 변화를 찾아 골드로 만들고, 바깥의 별도 작업이 이를 읽어 쿼터를 직접 보정한다. 결과를 읽는 앱은 이 시스템 밖에 있고, 읽은 결과로 무엇을 할지도 바깥 시스템이 정한다. 이 시스템이 직접 바깥에 행동을 남기는 4단계와 다른 점이다.

"사용자가 지표를 직접 본다"는 말에는 두 뜻이 있다. 바깥 시스템이 골드를 읽어 자기 화면으로 보여 주는 것은 이 단계에 속한다. 플랫폼 안에서 사용자가 데이터를 직접 조회하는 것은 데이터 자체를 서비스로 내놓는 일이므로 "데이터 플랫폼으로 확장"에서 다룬다.

이 단계는 집계 표와, 바깥 시스템이 그 표를 읽을 통로를 더한다. 2단계만 있으면 되고, 4단계와는 관계없다.

### 집계 표와 읽기 통로

정해진 집계만 내어 준다면 미리 계산해 둔 집계 표(골드)를 열어 주면 충분하다. 아무 SQL이나 받는 서비스나 읽기 API를 따로 만들 필요가 없다.

**골드는 PostgreSQL에 쓴다.** 브론즈와 실버는 양이 많아 S3에 두지만, 골드는 팀, 프로젝트, 날짜 단위로 줄인 작은 표다. S3를 고른 이유였던 데이터양 문제가 골드에는 해당하지 않는다. 좋은 점은 넷이다.

- 골드는 실버에서 언제든 다시 만들 수 있어, 원본처럼 S3에 보관할 필요가 없다.
- 표를 다시 만들 때 트랜잭션으로 한 번에 바꾸므로, 읽는 도중에 옛 값과 새 값이 섞이지 않는다.
- 앱이 DB를 읽는 흔한 방식이고, 바깥 시스템이 S3 접근 키를 갖지 않아도 된다.
- PostgreSQL은 이미 있으므로 서비스가 늘지 않는다.

골드가 PostgreSQL이 감당할 만큼 작다는 것은 아직 확인하지 않은 가정이다.

**골드는 2단계의 DuckDB가 PostgreSQL에 바로 쓴다.** DuckDB는 PostgreSQL 확장으로 PostgreSQL 표에 직접 쓸 수 있다. 그래서 집계하는 SQL이 결과를 PostgreSQL 표에 바로 넣고, 로직은 SQL에 남는다. 이 SQL은 2단계 배치 앱이 다른 변환과 함께 돌린다. 이 확장은 아직 시험하지 않았다. 안 되면 앱이 DuckDB 결과를 읽어 직접 넣는다.

**권한은 PostgreSQL이 건다.** 바깥 시스템마다 읽기 전용 계정을 하나씩 주고, 그 계정은 정해진 뷰만 읽게 한다. 뷰가 바깥 시스템과의 약속이다. 안쪽 표를 고쳐도 뷰를 유지하면 바깥 시스템은 깨지지 않는다. DB 계정 권한은 검증된 기능이므로 따로 만들 것이 없다(규칙 3). 바깥 시스템이 자기 사용자별로 결과를 나누는 일은 바깥 시스템이 맡는다.

**지표는 개발자가 SQL로 더한다.** 바깥 시스템에 필요한 집계가 생기면, 개발자가 그 집계를 계산하는 SQL을 2단계 변환에 더하고 뷰를 연다.

### 갈림길

| 갈림길 | 지금 고른 것 | 대안 | 대안을 고르는 상황 | 상태 |
|---|---|---|---|---|
| 바깥이 읽는 곳 | PostgreSQL 집계 표 | S3 직접, Trino | 집계 표가 PostgreSQL에 담기 어려울 만큼 커지거나, Trino가 들어왔을 때 | 크기 가정 미확인 |
| 읽기 통로 | 읽기 전용 계정 + 뷰 | 읽기 API | 바깥 시스템이 많아지거나, 믿기 어려운 상대에게 열어야 하거나, DB 연결 수가 문제가 될 때 | 결정 |
| PostgreSQL에 쓰기 | DuckDB PostgreSQL 확장 | 앱이 결과를 읽어 넣기 | 확장이 시험을 통과하지 못할 때 | 시험 전 |
| 지표 정의 | 개발자가 SQL 추가 | Trino로 SQL 열기 | 플랫폼 안에서 사용자가 직접 SQL을 써야 할 때 | 결정 |

## 4단계 사용(내보내기): 결과를 밖으로 보낸다

### 언제 필요한가

분석 결과로 바깥에 행동을 해야 할 때다. 샘플 시스템에서는 오래 쓰지 않은 사용자에게 안내 메일을 보내고, 유예 기간이 지나도 쓰지 않으면 휴면 처리한다. 대상은 2단계에서 찾았다. 이제 그 결과를 외부 메일 API와 처리 API로 보내야 한다.

이 단계는 새로 켜 두는 서비스 없이 2단계 앱에 기능을 더한다. 2단계만 있으면 되고, 3단계와는 관계없다.

### 내보내기는 변환과 다르다

분석 결과를 외부 시스템으로 내보내는 일을 **리버스 ETL(Reverse ETL)**이라고 부른다. 보통의 ETL이 소스에서 데이터를 가져와 저장소에 넣는다면, 리버스 ETL은 반대로 저장소의 결과를 바깥 시스템으로 보낸다. 변환은 데이터를 읽고 다른 데이터를 만든다. 실패하면 다시 돌리면 된다. 내보내기는 바깥에 영향을 남긴다. 메일은 한 번 나가면 되돌릴 수 없다. 성격이 달라서 따로 다룬다.

그래서 일을 둘로 나눈다. 누구에게 보낼지는 2단계의 SQL이 고르고, 결과를 PostgreSQL의 대기 표에 넣는다. 실제 발송은 워커가 대기 표에서 한 건씩 꺼내 보낸다. 대기 표가 두 일의 경계다.

### 대기 표는 PostgreSQL에 둔다

대기 표의 각 행은 "대기 → 발송 중 → 완료 또는 실패"로 상태가 바뀐다. 상태를 바꾸려면 행을 고치고, 두 워커가 같은 행을 동시에 잡지 않게 잠가야 한다. PostgreSQL은 행 잠금으로 이것을 한다. S3는 파일 단위로만 쓰고 지우므로, 행 하나의 상태를 바꾸거나 잠글 수 없다.

대기 표는 작은 작업 큐를 직접 만드는 것처럼 보이지만, 직접 만드는 부분은 상태 열 하나와 그 열을 바꾸는 SQL뿐이다. 행을 잠그고 잠긴 행을 건너뛰는 일은 PostgreSQL의 `FOR UPDATE SKIP LOCKED`가, 같은 요청 ID가 두 번 들어가지 않게 막는 일은 고유 제약이 한다. 재시도와 재시작은 워커의 Spring Batch가 한다(규칙 3). 상태가 늘거나, 지연 실행이나 우선순위가 필요해지면 검증된 큐 도구를 검토한다.

| 후보 | 방식 | 고를 때 따질 단점 |
|---|---|---|
| PGMQ | PostgreSQL 확장. 메시지를 읽으면 정한 시간 동안 남에게 보이지 않는다 | 그 시간 안에 지우지 못하면 다른 워커가 다시 읽어 중복 처리가 생긴다. 사내 PostgreSQL에 확장을 설치할 수 있어야 한다(설치가 안 되면 SQL만으로 설치하는 방법이 있다). 넣기를 함수로 하므로 DuckDB가 대기 표에 바로 쓰는 지금 방식과 맞는지 확인해야 한다 |
| PgQ(SkyTools) | PostgreSQL 확장과 별도 데몬(pgqd)이 이벤트를 묶음으로 나눠 준다 | 데몬을 하나 더 켜 두어야 하고, 데몬이 멈추면 묶음이 만들어지지 않아 이벤트 표가 빠르게 커진다. 오래된 프로젝트라 공식 문서보다 미러 자료가 많다 |
| Namastack Outbox | Spring Boot 라이브러리. 업무 데이터와 같은 트랜잭션에 기록을 남기고, 재시도와 키별 순서를 맞춰 보낸다 | 앱 코드에서 기록을 남기는 구조라, SQL이 대상을 고르고 바로 넣는 지금 방식과 맞지 않을 수 있다. 앞으로의 버전은 Spring Boot 4만 지원한다는 관리자 답변이 있다. 판 번호 규칙을 엄격히 지키지 않는다고 밝힌다 |

셋 다 아직 시험하지 않았다.

각 행은 요청 ID로 구분한다. 요청 ID는 사용자, 요청 종류(안내 메일 또는 처리), 회차를 묶은 값이다. 회차는 같은 사용자가 나중에 다시 대상이 될 때 이전 건과 구분하려고 둔다.

발송 결과는 S3에도 추가만 한다. 누구에게 언제 무엇을 보냈는지는 나중에 분석하고 확인할 기록이고, 고칠 일이 없기 때문이다.

### 대상을 대기 표에 넣는 방법

대상을 고르는 SQL이 결과를 대기 표에 바로 넣는다. 3단계에서 골드를 PostgreSQL에 쓴 것과 같은 방법(DuckDB의 PostgreSQL 확장)이다. 고르기와 넣기가 SQL 하나에 있어 로직이 SQL에 남는다. 이미 있는 요청 ID는 넣지 않으므로, SQL을 다시 돌려도 대기 표에 중복이 생기지 않는다. 확장이 안 되면 앱이 DuckDB 결과를 읽어 직접 넣는다.

### 유예 뒤 처리도 같은 길로

처리도 바깥에 하는 행동이라 메일과 같은 길을 쓴다. 2단계 SQL이 "안내를 보낸 지 유예 기간이 지났고, 그 뒤 활동이 없는 사용자"를 골라 같은 대기 표에 "처리" 종류로 넣는다. 안내를 보낸 시각은 대기 표에 남아 있으므로 SQL이 그것을 읽는다. 유예는 SQL 조건일 뿐이라 따로 기다리는 부품이 필요 없다.

### 중복 발송을 막는 방법

워커가 API를 부른 직후, 결과를 저장하기 전에 멈추면 그 건은 다시 발송될 수 있다. 이것을 막기 위해 요청 ID를 API에 함께 보낸다. API가 같은 ID를 한 번만 처리해 주면 중복이 생기지 않는다. 메일 API와 처리 API가 이것을 지원하는지는 아직 확인하지 않았다. 지원하지 않으면 드문 중복 발송은 받아들이기로 했다.

안전장치도 둘 둔다. 첫째, 대상 수가 정한 기준을 넘으면 발송을 멈추고 사람이 승인한다. SQL이 잘못되면 전원을 고를 수 있는데, 메일은 되돌릴 수 없기 때문이다. 둘째, 보내기 직전에 대상이 여전히 조건에 맞는지 다시 확인한다. 대기 표에 넣은 뒤 보내기 전에 사용자가 다시 활동했을 수 있기 때문이다.

### 워커: 2단계 앱 안의 Spring Batch

워커는 **Spring Batch**로 만든다. Spring Batch는 많은 건을 묶음 단위로 처리하는 Java 프레임워크다. 실패한 건만 다시 시도하기, 문제 있는 건 건너뛰기, 멈춘 지점부터 다시 시작하기를 이미 제공한다. 발송은 건마다 실패할 수 있어 이 기능이 그대로 필요하다. 직접 만들면 만든 사람이 계속 고쳐야 하므로 검증된 도구를 쓴다.

워커는 2단계 앱 안에 넣는다. Spring Batch는 따로 켜 두는 서버가 아니라 라이브러리이고, 앱이 이미 Java이기 때문이다. 2단계의 실행 도구가 정해진 시각에 발송 작업을 시작하고, 작업 기록은 PostgreSQL에 남는다. 발송이 변환과 메모리를 다투거나 두 기능의 배포 시기가 달라지면 그때 앱을 나눈다.

Spring Batch는 변환에는 쓰지 않는다. 변환은 SQL을 한 번 실행하는 일이라 건 단위 재시도가 필요 없다.

### 운영: 2단계 실행 도구의 화면

운영자는 2단계에서 고른 실행 도구의 화면을 그대로 쓴다. 발송 작업이 성공했는지 실패했는지 보고 다시 돌린다. 다시 돌리면 실패했거나 남은 건만 보낸다. 대상 수가 기준을 넘으면 작업을 멈추고, 운영자가 대상을 확인한 뒤 승인하면 이어 간다. Kestra는 실행 멈춤(Pause)으로 이것을 한다. 내장 스케줄러는 승인 값을 넣어 다시 돌리는 방식이고, 화면에서 값을 넣을 수 있는지는 시험으로 확인한다. 사용자 한 명씩 다루는 화면은 그런 요구가 생길 때 더한다.

## 데이터 플랫폼으로 확장

여기까지는 시스템의 기능이다. 3·4단계까지 갖추면 아홉 요구를 모두 받는다. 다만 CSV 한 소스는 원본 대신 레코드로 보관하는 예외가 있다(1단계). 데이터 자체를 서비스로 내놓아야 하는 요구가 생기면 데이터 플랫폼으로 확장한다. 아래 둘은 각자를 필요로 하는 요구가 생길 때만 더하고, 요구가 없으면 더하지 않는다. 순서는 정해져 있지 않다.

### Trino: 플랫폼 안에서 사람이 직접 SQL로 조회해야 할 때

**Trino**는 여러 사용자가 동시에 SQL을 실행할 수 있는 분산 SQL 서버다. 바깥 시스템이 정해진 집계를 읽어 가는 것(3단계)이 아니라, 플랫폼이 조회 기능을 제공해 사용자가 데이터를 직접 SQL로 조회해야 할 때 들인다. 플랫폼 사용자나 분석가의 임의 조회, 여럿이 동시에 쓰거나 쿼리를 공유하는 경우가 여기에 속한다. Trino는 행 단위 필터와 열 가리기 같은 권한 기능을 서버에서 제공하지만, 이 시스템은 Trino가 들어와도 권한을 저장소의 권한(S3 경로 권한, PostgreSQL 계정 권한)으로 준다. 권한을 저장소 한곳에서만 관리하기 위해서다. Trino가 사용자마다 다른 저장소 자격 증명으로 읽게 하는 방법은 아직 확인하지 않았다. 그 전에는 신뢰하는 운영자가 DuckDB와 DBeaver 같은 개인 도구로 직접 조회한다. 이 방법은 S3 접근 키가 필요하므로 신뢰하는 사람에게만 허용한다.

### Iceberg: S3의 표를 여럿이 읽거나 행을 고쳐야 할 때

**Iceberg**는 S3의 파일 묶음을 DB의 표처럼 다루게 해 주는 표 형식이다. 행 단위 수정과 삭제, 표 통째 교체, 과거 시점 조회를 지원한다. 일반 파일로 된 표를 변환이 다시 쓰는 동안 누가 읽으면, 반은 옛 파일이고 반은 새 파일인 결과를 읽을 수 있다. Iceberg는 바꾸기가 끝난 순간에 한 번에 새 표로 넘어가므로 이런 일이 없다. 3단계에서는 바깥 시스템이 PostgreSQL을 읽으므로 이 위험이 없다. Trino로 사용자가 S3의 표를 직접 읽기 시작하거나, 실버의 행을 고치거나 지워야 할 때 실버를 Iceberg로 바꾼다. 골드는 PostgreSQL 한 곳에 그대로 두고, Trino는 PostgreSQL 커넥터로 읽는다. 같은 골드를 두 곳에 두면 쓰기가 두 번이고, 한쪽만 실패하면 Trino로 본 값과 바깥 시스템이 읽은 값이 달라진다. 한 곳에 두면 이런 어긋남이 없고, 권한도 PostgreSQL 계정 권한 하나로 준다. 바깥 시스템은 계속 PostgreSQL의 뷰를 읽으므로 버리는 것이 없다. 골드가 PostgreSQL에 담기 어려울 만큼 커질 때만 골드도 Iceberg로 옮긴다. Trino가 PostgreSQL을 읽는 속도가 충분한지와, 사용자별 PostgreSQL 계정 권한으로 이어지는지는 아직 확인하지 않았다.

Iceberg는 형식이지 서비스가 아니지만, 표 목록을 관리하는 **카탈로그**가 필요하다. 카탈로그 종류에 따라 DuckDB와 Trino가 함께 쓸 수 있는지가 달라지는데, 이 조합은 아직 확인하지 않았다. 또 작은 파일 합치기, 오래된 스냅샷 지우기 같은 정비 작업을 정기적으로 돌려야 한다. 이 작업은 2단계의 실행 도구가 돌린다.

### 갈림길

|---|---|---|---|---|
| 표 형식(실버) | 일반 파일 | Iceberg | 사용자가 S3의 표를 직접 읽거나, 행 수정·삭제가 필요할 때 | 카탈로그 호환 미확인 |
| 골드 위치 | PostgreSQL 한 곳(Trino는 PostgreSQL 커넥터로 읽기) | Iceberg로 옮기기 | 골드가 PostgreSQL에 담기 어려울 만큼 커질 때 | Trino의 PostgreSQL 읽기 속도·사용자별 권한 미확인 |

## 최종 구성

최종 구성은 시스템의 데이터 요구에 따라 서로 다른 방향으로 구성될 뿐이다. 아래 표는 요구가 생길 때마다 컴포넌트를 더해 가는 오픈소스 중심의 최종 구성이다. 어떤 요구가 생기느냐에 따라 표의 일부만 들어올 수 있다.

| 컴포넌트 | 들이게 하는 요구 | 들어오는 때 |
|---|---|---|
| Airbyte | 흩어진 시스템의 데이터를 한곳으로 가져온다 | 1단계 |
| 배치 앱(DuckDB SQL), 운영자가 PR로 SQL을 고치게 되면 dbt | 업무 규칙을 적용해 실버와 골드를 만든다 | 2단계(dbt로 옮기면 변환은 dbt 컨테이너에서 돌고, 배치 앱에는 워커만 남는다) |
| 실행 도구(Kestra + oauth2-proxy, 권한과 변경 기록이 필요하면 Airflow) | 작업 순서 의존, 시간 구간 재실행, 화면에서 설정 바꾸기 | 2단계(요구가 없으면 배치 앱 안의 내장 스케줄러) |
| 워커(Spring Batch, 배치 앱 안) | 결과로 메일을 보내고 처리한다 | 4단계 |
| Trino | 사람이 직접 SQL로 조회하고 공유한다 | 확장 |
| Iceberg 카탈로그 | S3의 표를 여럿이 읽거나, 행을 고치고 지운다 | 확장 |

S3와 PostgreSQL은 처음부터 있으므로 표에 넣지 않았다. 3단계의 읽기 통로(읽기 전용 계정과 뷰)도 PostgreSQL의 기능이라 컴포넌트가 늘지 않는다. 골드를 읽는 앱은 바깥 시스템에 있다. 권한은 Trino가 들어와도 저장소의 권한으로 주므로, 별도 정책 서버를 두지 않는다.

최종 구성에서는 새 분석과 지표를 SQL 추가로, 새 소스를 Airbyte 커넥터 추가로 받는다. 컴포넌트가 바뀌는 것은 각 단계의 갈림길 표에 적은 조건이 생겼을 때뿐이다.

받아들인 빈칸이 하나 있다. 로그 수집기가 어느 S3 경로로 보낼지는 Airbyte 화면에도 Kestra 화면에도 없으므로, 개발자가 서버 배포 설정으로 바꾼다. 로그 경로는 거의 바뀌지 않으므로 운영자 화면을 따로 두지 않는다.

예외는 셋이고, 모두 지금은 요구가 없어 범위 밖 후보로 둔다.

- **즉시 반응:** 데이터가 도착하는 즉시 반응해야 하면 메시지 큐가 필요하다. 지금 구성은 정해진 시각에 돌기 때문이다.
- **BI 대시보드:** 그래프와 표로 자유롭게 탐색하려면 별도 BI 도구가 필요하다. BI 도구는 SQL로 데이터를 읽는다. PostgreSQL의 골드만 본다면 지금도 붙일 수 있고, 실버까지 탐색하려면 Trino가 들어온 뒤에 붙인다.
- **분산 엔진:** 데이터가 2단계의 나눠 돌리기로도 감당되지 않으면 DuckDB 대신 분산 엔진이 필요하다.

## 아직 확인하지 않은 것

아래 여덟은 확인되기 전까지 관련 선택을 확정하지 않는 항목이다. 단계 순서로 놓았다.

1. (2단계) 앱 안의 DuckDB(2코어, 4GB)가 가장 많은 한 시간 분량을 15분 안에 처리하는지
2. (2단계) 사내 S3가 경로 단위 접근 권한을 지원하는지
3. (2·4단계) Kestra 오픈소스판이 설정 저장소, 실행 입력(표 형태 값 포함), 병렬 실행, 실행 멈춤, Airbyte 연동을 제공하고, oauth2-proxy 뒤에서 동작하는지
4. (2·4단계) 내장 스케줄러를 고른 경우, 날짜나 승인 값을 넣어 다시 돌리고 재기동 때 놓친 실행을 채우는지
5. (3·4단계) DuckDB가 PostgreSQL 확장으로 집계 표와 대기 표에 바로 넣을 수 있는지
6. (4단계) Spring Batch가 같은 값으로 작업을 다시 실행할 수 있는지
7. (4단계) 메일 API와 처리 API가 요청 ID로 중복을 막는지, 호출 한도는 얼마인지
8. (확장) 같은 Iceberg REST 카탈로그를 DuckDB와 Trino가 함께 쓸 수 있는지. 둘 다 REST 카탈로그를 지원한다는 것은 문서로 확인했지만, 함께 쓰는 조합은 시험하지 않았다.

이 밖의 미확인 항목은 확정을 막지 않으며, 각 단계의 본문과 갈림길 표에 적었다. 1단계의 Airbyte 변경분 받기(CDC) 지원, HTTP 소스의 파일 그대로 복사, S3의 버전 관리와 삭제 잠금, 2단계의 로그 수집기 전송 지연, 3단계의 골드 크기, 확장의 Trino가 사용자별 저장소 자격 증명으로 읽는 방법과 PostgreSQL 커넥터의 읽기 속도가 여기에 속한다.
