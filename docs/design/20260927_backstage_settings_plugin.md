# Backstage Settings 플러그인 프론트엔드 설계 스펙

## 목표
Config 스키마 구현 내용을 바탕으로, 관리자가 설정(Config)을 조회하고 값을 수정할 수 있는 별도의 Backstage Settings 플러그인을 구현한다. VSCode 설정 창처럼 그룹핑과 설명(Title/Description)이 예쁘게 렌더링되어야 하며, 백엔드의 JSON Schema를 기반으로 `@rjsf/core`를 활용해 동적으로 폼을 구성한다.

## 배경 / 기존 컨텍스트
- 참조한 기존 패턴: 기존 `spring-batch-dashboard`와 분리된 완전히 독립적인 신규 플러그인(`backstage/plugins/settings-plugin` 등)으로 구축.
- 신규로 가는 이유: 배치의 실행 이력/상태 관리(Dashboard)와 도메인 파라미터/스케줄러 설정(Settings)은 관심사와 사용 주기가 다르므로 플러그인 레벨에서 분리하는 것이 타당함.

## 설계 결정
| 항목 | 결정 | 근거 |
|---|---|---|
| 플러그인 스코프 | 별도의 Settings 플러그인 신규 생성 | Dashboard와 Settings의 역할 분리. |
| 렌더링/데이터 주도권 | 백엔드 JSON Schema 기반 렌더링 (`@rjsf/core`) | 어민이 백엔드 스키마를 수정하면 프론트엔드가 이를 즉시 반영할 수 있도록 프론트엔드 하드코딩을 배제함. |
| 동시성 제어 | 낙관적 락 (Optimistic Locking) 도입 예정 (TODO) | 다중 관리자 접속 시 덮어쓰기 방지. 단, 현재 백엔드 API에 버전 필드가 없으므로, 프론트엔드 화면에는 TODO 주석/메시지만 남겨두고 향후 백엔드 API 업데이트 시 연동하도록 함. |
| 실패/재시도 | 자동 재시도 없음, 화면에 에러 영구 노출 후 수동 재시도 | 네트워크나 락 충돌 오류 발생 시 에러 메시지를 사용자가 직접 확인(인지)하고 닫을 때까지 화면에서 사라지지 않게 하여 사고를 방지함. |
| 파라미터 시간 결합 | 프론트엔드 UI 컴포넌트이므로 해당 없음 | N/A |

## 완료 조건 (자가검증)
- [ ] 컴파일/빌드 통과 (Backstage 플러그인 빌드 `yarn tsc`, `yarn build`)
- [ ] 유닛테스트 (`SettingsPage.test.tsx` 등):
  - 백엔드에서 내려준 가상의 JSON Schema(그룹, 설명 포함) 데이터를 `msw`로 모킹하여, 폼과 기본값이 스키마 의도대로 정상 렌더링되는지 검증.
  - 저장 버튼 클릭 시 API 에러(예: 409 Conflict, 낙관적 락 실패 상황 모킹)가 발생했을 때, 에러 스낵바/메시지가 자동으로 사라지지 않고 화면에 유지되는지 검증.
- [ ] 통합테스트: MSW(Mock Service Worker)를 통한 API 모킹 연동 검증. 실제 백엔드 연동 대신 경계선(Mock) 검증 수행.
- [ ] 커버리지 기준: 80% 이상

## 미결 사항
