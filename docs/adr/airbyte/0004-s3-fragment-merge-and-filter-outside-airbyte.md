# Vector 파편 로그의 병합·필터는 Airbyte 밖의 실버 변환(DuckDB)으로 처리한다

Vector가 S3에 파편으로 적재한 압축 로그를 시간 단위로 병합하고 부서 소유 리소스만 걸러 별도 경로에 적재해야 한다.
Airbyte OSS에는 레코드 필터가 없고, 필터는 업무 규칙이라 EL 도구가 아닌 실버 변환 책임이다. 그래서 DuckDB CLI SQL로 실버 변환을 처리하고, 변환이 늘어나면 dbt로 옮긴다.
실행 주체(스케줄, 재실행, 관리 화면)는 이 ADR에서 정하지 않는다.

## Status

Proposed (1차 정리. 아래 "미확정 항목" 확인 후 확정)
2026-11-27: 처리 엔진을 DuckDB CLI로 확정했다. 실행 주체 후보에서 CronJob을 뺐고, 실행 주체는 별도로 정한다. 구현 상세(이미지, 시크릿, 배포)는 이 ADR에서 뺐다.

## Context

- 입력: Vector가 S3에 쓴 `jsonl.gz` 파편. 분 단위 또는 수백 MB 단위 적재를 계획 중.
- 물량: 주당 약 4.2억 건(일 약 6,000만, 평균 시간당 약 250만). 피크 3시간 약 1,600만 건(시간당 약 530만, 초당 약 1,500).
- 필터 조건: 필드는 고정. 값은 "특정 부서의 소유 리소스 목록"(메타데이터 테이블, 외부 조직이 변경)과 정규식.
- 원본은 재처리를 위해 브론즈로 전량 유지한다. 병합·필터 결과는 별도 경로에 `jsonl.gz`로 쓴다.
- 출력 경로와 파일명 패턴은 설정으로 둔다.
- 환경: 온프레미스, 배포는 GitHub Actions 예정.
- 운영 비용(개발·유지·관리자 화면)이 최대 관심사다.

## Decision

- 병합·필터는 **브론즈→실버 변환**으로 취급하고 Airbyte에서 하지 않는다.
- 처리 엔진은 **DuckDB CLI**로 한다. SQL이 매시 직전 윈도우의 파편을 읽어 소유 리소스 목록(Postgres 읽기 전용)과 조인·정규식으로 거른 뒤 결과 파일을 쓴다.
- SQL은 `lakehouse/pipeline` 규약([lakehouse ADR-0002](../lakehouse/0002-pipeline-sql-catalog-macros.md)의 카탈로그 macro)을 따른다. 이 규약은 dbt 전환을 목표로 설계되어 있다.
- 출력은 `jsonl.gz`로 쓴다. lakehouse의 CSV 규약([lakehouse ADR-0003](../lakehouse/0003-keep-csv-without-table-catalog.md))의 예외로 둔다.
- 변환이 늘어나면 dbt(dbt-duckdb)로 옮긴다.
- 경로, 파일명 패턴, 스케줄, 지연 시간은 설정으로 둔다.
- 목록 조회 실패 시 잡을 실패시킨다(빈 목록으로 진행하지 않음). 읽은 건수·통과 건수·목록 버전을 로그에 남긴다.
- 실행 주체는 이 ADR에서 정하지 않는다. [ADR-0006](./0006-airbyte-bounded-pull-and-vector-push-channel.md)의 비개발자 운영 요구를 이 단계에 적용할지와 함께 정한다. 후보는 부록 C.
- Airbyte는 데이터 이동에만 쓴다. 필요하면 메타데이터 테이블을 레이크로 복제하는 데 쓸 수 있다.

## Considered Options

| 안 | 결과 |
|---|---|
| **DuckDB CLI 실버 변환** | **채택**. 비용 낮고 레이어에 맞음. lakehouse 규약과 같음. 실행 주체는 별도 결정 |
| DuckDB + Python 스크립트 | 기각. lakehouse 규약과 다르고 코드·이미지가 늘어남 |
| Airbyte S3 소스 래퍼(필터 추가) | 대안. 관리 화면은 재사용하나 브론즈→브론즈에 업무 규칙이 섞임. 관리 화면이 필수가 되면 재검토 |
| Airbyte 설정만 | 기각. 레코드 필터 없음 |
| Spring Boot / Spring Batch | 기각. 스케줄러·입력 UI·관리 화면을 직접 개발·운영해야 함 |
| Trino | 기각. 클러스터 운영 비용이 과함. 파편(분할 불가 `.gz`)을 직접 읽는 것도 비효율 |
| Vector 쪽 필터 | 기각. 조건이 외부 조직 소유 메타데이터라 변경 때 재배포 필요 |

## Consequences

- 디버깅과 재실행 방식은 실행 주체에 따라 달라진다. 로컬 재현은 `compose.yaml`의 MinIO·Postgres로 한다.
- 목록은 순방향만 적용한다. 과거 재처리는 브론즈 구간을 지정해 수동 실행한다.
- 출력 파티션은 이벤트 시각이 아닌 파일 도착(`LastModified`) 기준 윈도우이며, 늦게 오는 파일을 위해 윈도우 종료 후 지연을 둔다. 출력 파일명은 결정적으로 정해 재실행이 덮어쓰기가 되게 한다.
- 필터 오류는 데이터의 조용한 유실로 이어진다. fail-closed와 건수 기록이 필수 완화책이다.

## 미확정 항목

- 실행 주체. ADR-0006의 비개발자 운영 요구를 이 단계에 적용할지에 따라 정한다.
- 물량 수치(로그 1건 크기, 시간당 파편 파일 수)와 DuckDB 단일 프로세스 처리 시간 실측.
- 빈 목록 실패 처리. 목록이 비면 모든 로그가 걸러지는데 오류 없이 끝나 유실을 알아채지 못한다. `duckdb -bail`은 SQL 오류에서만 멈추므로, 목록 건수가 0이면 `error()`로 직접 실패시키는 검사가 필요하다. 이 방식은 실행해서 확인하지 않았다.
- dbt 전환 시 파티션 쓰기. 출력은 시간 단위 폴더(`dt=`, `hr=`)로 나눠 쓴다. dbt-duckdb에서 `external`과 `partition_by`를 함께 쓰면 실패한다는 보고(dbt-duckdb issue #232, lakehouse ADR-0003)가 있어, 전환할 때 다시 확인한다.
- 운영 환경 상세(K8s, 사내 컨테이너 레지스트리).
- 필터 목적은 **접근 격리**로 확정. 물리 복사본(실버 부서별 경로)으로 격리할지, 골드의 뷰·행 단위 권한으로 격리할지 결정 필요. 물리 복사본이면 경로·버킷 단위 권한으로 격리를 강제해야 한다.
- 필터 대상은 저장소 경로 필드(예). 부서별 저장소 목록과 정규식은 수정 가능한 조건. 정확 일치와 정규식의 결합 방식(가정: OR).
- 설치된 Airbyte 버전의 Mappers 노출 여부(공식 문서상 Core·Standard는 미지원).
- 실버 포맷은 고정하지 않는다. 변환은 여러 갈래로 분기할 수 있으므로 병합·필터 단계와 포맷 변환 단계를 분리해 둔다.

## 부록 A. 메달리온 아키텍처 기준 검토

| 레이어 | 이번 작업의 대응 |
|---|---|
| 브론즈 | Vector가 쓴 파편 원본. 불변, 전량 보존 |
| 실버 | 병합·부서 소유 리소스 필터 결과. 업무 규칙은 여기 속한다 |
| 골드 | 업무 집계, 서빙. 부서별 접근 통제는 뷰·행 단위 권한으로 여기서 처리 |

- Airbyte는 EL(소스→브론즈)까지가 역할이다. S3→S3 병합·필터는 브론즈→브론즈라 레이어 이동이 아니며 업무 규칙이 커넥터 코드·DB 접속 정보에 묻힌다.
- 작은 파일 병합(compaction)은 변환이 아닌 저장소 유지보수다. 실버를 Iceberg 같은 테이블 포맷으로 전환하면 표준 기능(`OPTIMIZE` 등)으로 해결된다.
- Vector의 배치 크기·타임아웃 조정으로 파편화를 수집 단계에서 줄이는 것은 병행 가능하다(필터는 하지 않음).

## 부록 B. Airbyte OSS 조사 결과 (2026-10 기준)

- Mappers(행 필터): 공식 문서상 Plus·Pro·Enterprise Flex 전용. Core·Standard는 미지원. 필터 대상은 string·number 필드. 목록 조회·정규식 지원 여부는 문서에 없다.
- S3 소스 4.16.1: 레코드 필터 없음. 파일 단위 필터만 있다(`path_pattern` glob, `start_date`, `days_to_sync_if_history_is_full`). `jsonl` 포맷과 Gzip 압축을 지원한다. 레코드 복제와 원문 복사(`delivery_method`) 모드가 있으며 필터는 레코드 복제 모드에서만 의미가 있다.
- S3 목적지 1.9.11: `S3 Path Format`(`${YEAR}`, `${HOUR}`, `${SYNC_ID}` 등)과 `File Name Pattern`(`{date}`, `{part_number}` 등)을 설정으로 지원. JSONL 기본 GZIP. 파일 크기 설정 필드가 없고 압축 200MB 이하 목표로 분할되어, "윈도우당 파일 1개"를 강제할 수 없다.
- 확장 지점: 커넥터 코드 확장뿐이다. Connector Builder의 레코드 필터는 HTTP 소스 전용이라 S3에 쓸 수 없다.
- 래퍼 방식 유지보수: 목적지 포크(Kotlin/Java, 구조상 부적합)보다 소스 확장(Python, file-based CDK)이 낫고, 포크보다 업스트림 `airbyte-source-s3`를 의존성으로 고정한 래퍼가 드리프트가 작다. 단 CDK 내부 API에 의존하며 이미지 빌드·배포 비용이 든다.

## 부록 C. 실행 주체 후보 비교 (관리 화면)

| 도구 | 특징 | 운영 비용 |
|---|---|---|
| Kestra | 이미 도입([ADR-0005](./0005-kestra-pull-ingestion-instead-of-airbyte.md)). 화면 기반 흐름 정의, 입력 폼, 재실행·백필 | 추가 없음(기존 서비스) |
| Argo Workflows | K8s 기본. CronWorkflow, 이력·로그, 파라미터 재제출 UI. 기존 컨테이너 재사용 | 낮음(컨트롤러·UI, DB 불필요) |
| Dagster | 시간 파티션 백필 화면, 레이어를 자산으로 표현 | 중간(웹서버·데몬·DB) |
| Airflow | 널리 쓰임. 날짜별 백필, 파라미터 실행 | 중간~높음 |

## 부록 D. 트랜스폼 기술 선택 조건표

핵심 요건: **R1** 레코드 필터(목록 조회 + 정규식), **R2** 파편을 시간 윈도우 파일로 병합, **R3** 스케줄 + 윈도우 지정 재실행, **R4** 추가 인프라 최소(온프레미스).
○ 충족 / △ 부분 / ✗ 불가. "설정만 운영"은 배포 후 코드 수정 없이 런타임 구성만으로 운영 가능한지를 뜻한다.

| 기술 | R1 | R2 | R3 | R4 | 유지보수 | 설정만 운영(화면) |
|---|---|---|---|---|---|---|
| Airbyte 설정만 | ✗ | △ 파일 크기 제어 불가 | ○ | ○ 기존 | 낮음 | ○ Airbyte UI |
| Airbyte 래퍼 소스 | ○ | △ 동일 | ○ | ○ 기존 | 중간 (CDK 추종, 이미지 빌드) | ○ spec 폼에서 목록·정규식 수정 |
| DuckDB + Kestra | ○ | ○ | ○ | ○ 기존 | 낮음 | ○ 입력 폼, 이력, 재실행 |
| DuckDB + Argo | ○ | ○ | ○ | △ 서비스 1개 추가 | 중간 | ○ 파라미터 폼, 이력, 재제출 |
| Spring Boot | ○ | ○ | ○ | ✗ 앱 개발·운영 | 높음 | ✗ 화면 직접 개발 |
| Trino | ○ | △ | △ 별도 스케줄러 필요 | ✗ 클러스터 | 높음 | ✗ |

선택 기준:
- 처리 엔진은 DuckDB로 고정한다.
- 실행 주체는 운영 요구로 고른다. 실행 주체를 바꿔도 DuckDB SQL은 그대로다.
- 처리량 병목이 없고 Airbyte UI 중심 운영이 필요하면 Airbyte 래퍼를 재검토한다.
