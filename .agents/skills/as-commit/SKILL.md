# Git Commit 가이드

당신은 팀의 엄격한 커밋 메시지 컨벤션을 준수하여 쉘에서 `git add`와 `git commit` 명령을 수행하는 역할을 합니다. 사용자가 `as-commit`을 요청하면 다음 규칙을 따르세요.

## 0. 사용자 승인 규칙 (필수)
- 모든 코드 커밋(`git commit`) 및 스킬 실행은 **반드시 사용자의 명시적인 승인(Approval)을 받은 이후**에만 수행해야 합니다.
- 임의로 명령을 실행하지 말고, 커밋할 파일 목록과 작성된 커밋 메시지 초안을 먼저 사용자에게 제시하여 컨펌을 요청하세요.

## 1. 파일 스테이징 규칙 (중요)
`git add .`과 같이 워크스페이스의 모든 변경사항을 무작정 포함해서는 안 됩니다.
1. 현재 대화 세션(문맥) 내에서 에이전트가 직접 수정/생성했거나, 사용자와 논의하여 변경된 파일들만 리스트업합니다.
2. `git status -s`를 실행하여 워크스페이스의 변경점과 비교 및 교차 검증합니다.
3. 세션과 무관한 파일(예: 개인 설정 파일, 다른 작업 중이던 파일)은 철저히 배제하고, 문맥과 관련된 파일만 선별하여 `git add <file1> <file2>...` 명령어로 명시적으로 스테이징합니다.

## 2. 커밋 제목 (Subject) 규칙
- **형식:** Conventional Commits (`type(scope): subject` 또는 `type: subject`)
- **언어 및 어조:** 반드시 **영문 명령형(Imperative mood)**으로 작성 (예: `add`, `refactor`, `fix`, `chore`)
- **길이 제한:** 최대 50자 이내

## 3. 커밋 본문 (Body) 규칙
- **길이 제한:** 최대 200자 이내
- **필수 구조 (Why & What):** 코드가 어떻게(How) 변했는지 나열하지 마세요. 반드시 아래 형식처럼 구분하여 작성하세요.
  - `[Why]` 왜 이 변경을 했는지, 어떤 문제를 해결하려 했는지 (비즈니스/아키텍처적 사유)
  - `[What]` 그 결과로 무엇이 추가/제거/변경되었는지
- **이슈 링크:** 세션 중 다뤄진 GitHub 이슈가 있다면 본문 마지막에 `Resolves #XX` 또는 `Related #XX`를 반드시 포함하세요.

## 4. 실행 방법
1. 위 '파일 스테이징 규칙'에 따라 문맥에 맞는 파일들만 `git add` 합니다.
2. `run_command` 도구를 사용하여 아래와 같이 두 개의 `-m` 플래그를 사용해 제목과 본문을 분리하여 커밋을 실행하세요.
   - 명령어 예시: `git commit -m "feat(workflow): add dynamic routing" -m "[Why] 멀티 테넌트 환경에서 정적 설정의 한계를 극복하기 위함. [What] 라우팅 엔진을 동적으로 주입하는 팩토리 클래스 추가. Resolves #25"`
3. 커밋 완료 후 성공 메시지와 함께 작성된 커밋 메시지를 사용자에게 보고합니다.
