# design

목적: 코드 작성 전에 값싼 문서 왕복으로 설계를 끝낸다. 코드가 만들어진 뒤 왕복하는 것보다 훨씬 싸다.

## 절차

1. **요구사항 원문 확보** — 사용자가 준 요구사항을 그대로 스펙 템플릿 "목표" 항목에 옮긴다. 지어내지 않는다.
2. **기존 컨텍스트 조사** — 코드베이스에서 관련 기존 패턴(유사 클래스, 스키마, 컨벤션)을 찾아 대조한다. 없으면 사용자에게 참조 경로를 묻는다.
3. **끈질기게 질문** — 아래 체크리스트의 각 항목을 순서대로 검증한다. 답이 "아직 안 정함"이면 다음으로 넘어가지 말고 사용자에게 구체적으로 되묻는다. 한 번에 다 묻지 말고, 답변에 따라 후속 질문을 이어간다 (예: "이 값 어디서 온 건가요, 도메인 규칙인가요 설정인가요?").
4. **기존 코드/패턴과 대조 검증** — 각 결정이 기존 아키텍처(이미 확립된 유사 컴포넌트, 스케줄러, 큐, 도메인 모델)와 충돌하지 않는지 확인한다. 충돌하면 사용자에게 알리고 병합 여부를 묻는다. 특히: "이미 있는 메커니즘으로 될 일을 새로 만드는 건 아닌가?" (YAGNI 질문)를 반드시 던진다.
5. **완료 조건 충족 시까지 반복** — 아래 "완료 판정" 기준을 모두 통과할 때까지 3~4를 반복한다.
6. **스펙 문서 산출** — 템플릿에 맞춰 최종본을 파일로 작성한다.

질문은 사용자의 terse한 스타일에 맞춰 키워드 위주로 짧게. 장황한 설명 없이 핵심만 찌른다.

## 완료 판정 (프론티어 개발자 수준 체크리스트)

스펙이 아래를 전부 답하지 못하면 미완성으로 간주하고 질문을 계속한다.

- [ ] **의도/스코프**: 목표, 누가/무엇이 트리거하는지, 핵심 동작 1문장
- [ ] **필요 값 정의**: 로직에 필요한 값을 모두 추출한다. 각 값이 상수/설정값/계산값 중 무엇에서 기원하는지 밝힌다. 이름이 값의 성격(절대/상대, 단위)을 정확히 드러내는지 검증한다. 유효 범위와 적용 조건(언제 확정되는가 포함)을 명시한다.
- [ ] **파라미터 시간 결합**: 파라미터가 실행 시점(상대 시간)을 기준으로 하는지 고정 시점(절대 시간)을 기준으로 하는지 확인하여 시스템의 시간 의존성 문제를 방지한다.
- [ ] **배달/일관성 보장**: at-least-once / exactly-once / at-most-once 중 무엇, idempotency 전략
- [ ] **동시성 제어**: 병렬 실행 시 충돌 방지 방식 (예: locking 전략)
- [ ] **실패 처리**: 재시도 횟수/백오프, 최종 실패 시 행선지(DLQ 등)
- [ ] **기존 패턴과의 정합성**: 유사 기존 컴포넌트와 왜 통합하지 않고 신규로 가는지 근거
- [ ] **데이터 모델**: 스키마 또는 이벤트 계약, 상태 전이
- [ ] **자가검증 조건**: 완료를 어떻게 기계적으로 판별하는지 (컴파일/테스트/커버리지 기준)
- [ ] **테스트 전략**: 유닛/통합 범위, 외부 의존성 mock 여부

## 스펙 템플릿

```markdown
# [기능명] 설계 스펙

## 목표
(요구사항 원문 그대로 또는 최소 편집)

## 배경 / 기존 컨텍스트
- 참조한 기존 패턴: (경로/이름)
- 신규로 가는 이유 (기존 걸로 안 되는 이유):

## 설계 결정
| 항목 | 결정 | 근거 |
|---|---|---|
| 배달 보장 | | |
| 동시성 제어 | | |
| 실패/재시도 | | |
| 데이터 모델 | | |

## 완료 조건 (자가검증)
- [ ] 컴파일/빌드 통과
- [ ] 유닛테스트: (시나리오 나열)
- [ ] 통합테스트: (범위, mock 대상)
- [ ] 커버리지 기준: N%

## 미결 사항 (있다면 명시, 없으면 "없음")
```

## 종료 후

산출물 파일 경로를 사용자에게 제시하고, `implement` 스킬로 넘어갈 수 있다고 안내한다. 문서 하나로 끝나야 하며, 이 스킬 안에서 코드를 작성하지 않는다.
