# implement

목적: 설계가 끝난 스펙만 코드로 옮긴다. 설계를 이 스킬 안에서 하지 않는다.

## 절차

### 1. 스펙 문서 확인
- 사용자가 스펙 문서를 지정하지 않았으면: 구현을 시작하지 말고 스펙 문서 경로/내용을 요구한다.
- 스펙이 있으면 읽는다.

### 2. 스펙 품질 게이트
스펙이 `design` 스킬의 완료 판정 체크리스트를 만족하는지 검증한다:

- [ ] 의도/스코프 명시
- [ ] 배달/일관성 보장 결정됨
- [ ] 동시성 제어 결정됨
- [ ] 실패 처리(재시도/DLQ) 결정됨
- [ ] 기존 패턴과의 정합성 근거 있음
- [ ] 데이터 모델/스키마 명시
- [ ] 파라미터 시간 결합(절대/상대) 명시 — 스케줄 실행 로직이면 특히 필수
- [ ] 자가검증 조건(완료 판정 기준) 명시
- [ ] 테스트 전략 명시
- [ ] Mock 경계 검증 항목 포함 (mock 처리된 협력 객체가 있으면 통합테스트로 실제 배선 확인)
- [ ] 테스트 파일 분리 명시 (유닛/통합 별도 파일, 실행 단계 구분)

**하나라도 빠지거나 "TBD"/모호하면 구현을 시작하지 않는다.** 빠진 항목을 나열하고, `design` 스킬을 먼저 돌릴 것을 제안한다. 사용자가 "그냥 진행"을 명시적으로 요구하면, 빠진 항목을 가정으로 못박아 스펙 문서 상단에 "가정" 섹션으로 기록한 뒤에만 진행한다 — 침묵 속에 임의로 채우지 않는다.

### 3. 구현 및 리뷰
구현은 subagent에 위임하고, 현재 에이전트는 결과물을 리뷰한다. 단, 리뷰는 코드를 읽는 정적 검토만으로 완료로 보지 않는다 — 다음 두 가지를 모두 한다:
1. **체크리스트 대조**: 완료 조건 각 항목을 코드와 1:1로 대조한다.
2. **실행 기반 확인**: Mock 경계 검증 항목처럼 실행해야만 드러나는 항목은 실제로 실행해서 통과를 확인한다. 코드가 관용적이고 읽기에 문제없어 보인다는 것은 통과 근거가 되지 않는다 — 관용적인 코드도 프레임워크의 암묵적 런타임 계약(리플렉션, 프록시, 파라미터 이름 등)에 의해 조용히 깨질 수 있다.

그 외 원칙:
- 스펙의 "완료 조건"을 그대로 작업의 종료 기준으로 삼는다.
- 스펙의 "설계 결정" 표를 코드 구조에 1:1로 반영한다 (즉흥적으로 다른 방식을 택하지 않는다). 구현 중 스펙과 다르게 가야 할 이유가 생기면, 먼저 사용자에게 알리고 스펙을 수정한 뒤 진행한다 — 조용히 이탈하지 않는다.
- 테스트를 먼저 또는 구현과 함께 작성한다 (스펙의 테스트 전략에 따름).
- **테스트가 통과한다는 사실과 문제를 잡는다는 사실은 다르다.** 협력 객체를 mock 처리한 테스트라면, 그 mock이 감춘 실제 배선(쿼리, 이벤트 라우팅, 프레임워크 어댑터 등)이 맞는지 최소 한 번은 실제 경로로 확인한다. 확인 못 하면 완료 조건에 "미검증"으로 명시하고 보고에 남긴다.
- 완료 조건 체크리스트를 전부 통과할 때까지 자가검증 후 보고한다.

### 4. 완료 보고
스펙의 "완료 조건" 각 항목에 대해 pass/fail을 명시적으로 보고한다. 임의로 "잘 됐다"고 뭉뚱그리지 않는다. 각 테스트가 **실제로 무엇을 검증했는지**(실경로 vs mock 경계 안쪽)를 함께 밝힌다 — "테스트 통과"만으로는 그 항목이 실질적으로 충족됐는지 알 수 없다.
