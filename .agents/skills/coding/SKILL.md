# implement

목적: 설계가 끝난 스펙만 코드로 옮긴다. 설계를 이 스킬 안에서 하지 않는다.

## 절차

### 1. 스펙 문서 확인
- 사용자가 스펙 문서를 지정하지 않았으면: 구현을 시작하지 말고 스펙 문서 경로/내용을 요구한다.
- 스펙이 있으면 읽는다.

### 2. 스펙 품질 게이트
스펙이 `design` 스킬의 완료 판정 체크리스트를 만족하는지 검증한다:

- [ ] 의도/스코프 명시
- [ ] 배달/일관성 보장 결정됨
- [ ] 동시성 제어 결정됨
- [ ] 실패 처리(재시도/DLQ) 결정됨
- [ ] 기존 패턴과의 정합성 근거 있음
- [ ] 데이터 모델/스키마 명시
- [ ] 자가검증 조건(완료 판정 기준) 명시
- [ ] 테스트 전략 명시

**하나라도 빠지거나 "TBD"/모호하면 구현을 시작하지 않는다.** 빠진 항목을 나열하고, `design` 스킬을 먼저 돌릴 것을 제안한다. 사용자가 "그냥 진행"을 명시적으로 요구하면, 빠진 항목을 가정으로 못박아 스펙 문서 상단에 "가정" 섹션으로 기록한 뒤에만 진행한다 — 침묵 속에 임의로 채우지 않는다.

### 3. 구현
게이트를 통과했으면:
- 스펙의 "완료 조건"을 그대로 작업의 종료 기준으로 삼는다.
- 스펙의 "설계 결정" 표를 코드 구조에 1:1로 반영한다 (즉흥적으로 다른 방식을 택하지 않는다). 구현 중 스펙과 다르게 가야 할 이유가 생기면, 먼저 사용자에게 알리고 스펙을 수정한 뒤 진행한다 — 조용히 이탈하지 않는다.
- 테스트를 먼저 또는 구현과 함께 작성한다 (스펙의 테스트 전략에 따름).
- 완료 조건 체크리스트를 전부 통과할 때까지 자가검증 후 보고한다.

### 4. 완료 보고
스펙의 "완료 조건" 각 항목에 대해 pass/fail을 명시적으로 보고한다. 임의로 "잘 됐다"고 뭉뚱그리지 않는다.
